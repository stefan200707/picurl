# Анализ проблемы: нераспознанные критерии в парсере

## Описание инцидента
При обработке пользовательского запроса `хочу двушку у метро Варшавская, до 15 млн, с отделкой, 15 минут до метро пешком, с выходом на солнечную сторону, раздельным санузлом` система выдала следующие предупреждения (warnings):
1. `«у метро Варшавская»: не удалось распознать, не попало в ссылку`
2. `«15 минут до метро пешком, с выходом на солнечную сторону, раздельным санузлом»: не удалось распознать, не попало в ссылку`

*Примечание: в недавнем коммите часть проблемы (склеивание текста) была исправлена, и парсер научился разбивать нераспознанный текст по запятым и обрабатывать время до метро. Однако концептуальные проблемы остались.*

## Корневые причины (Root Causes)

### 1. Зависимость справочников от активных проектов (Проблема "Варшавской")
Наш механизм `app/reference/refresh.py` собирает базу `metro.json` на основе ответа API `api.pik.ru/v2/block`. Этот эндпоинт возвращает только те станции метро, рядом с которыми у застройщика ПИК **в данный момент есть активные проекты**. Если станция (например, "Варшавская") временно или вообще не имеет строящихся объектов ПИК, она отсутствует в `metro.json`. Из-за этого алгоритм `rapidfuzz` в `match_entities` не находит эту станцию, и она попадает в `warnings` как нераспознанный текст. 

### 2. Отсутствие семантики для неподдерживаемых фильтров
Такие пожелания, как "выход на солнечную сторону" и "раздельный санузел", физически отсутствуют в фильтрах на сайте ПИК. Система работает технически корректно, следуя инварианту: всё, что не удалось связать с URL, отправляется в `warnings`. Однако сообщение вида `"не удалось распознать"` вводит пользователя в заблуждение — он думает, что алгоритм не справился с задачей (ошибка парсера), хотя на самом деле проблема в ограничениях самого сайта ПИК (отсутствие таких фильтров).

## Пути решения (чтобы проблема не возникала в будущем)

Для полного устранения подобного класса проблем необходимо внедрить следующие архитектурные улучшения:

### 1. Независимый мастер-справочник топонимов (Решение проблемы №1)
Вместо того чтобы полагаться исключительно на API застройщика для составления списка станций метро, необходимо использовать полный статический справочник (например, спарсенный с mos.ru, Яндекс Метро или другого открытого источника). 
- **Реализация**: В проекте должен лежать полный справочник станций метрополитена. Скрипт `refresh.py` должен только дополнять его, проставляя `id` и `slug` тем станциям, где сейчас есть проекты ПИК.
- **Результат**: Парсер сможет распознавать любую станцию метро (даже ту, где нет ЖК). В этом случае `url_builder` добавит её в Criteria, а `validator.py` честно проверит через API и вернет результат "Найдено 0 квартир", что является правильным продуктовым ответом.

### 2. Расширение модуля `extract_unsupported` (Решение проблемы №2)
В модуле `app/parsing/rules.py` уже есть функция `extract_unsupported`, которая сейчас отлавливает только слово "вторичка".
- **Реализация**: Необходимо составить и добавить регулярные выражения для широкого пула популярных пожеланий, которые не поддерживаются ПИКом: `солнечная сторона`, `раздельный санузел`, `балкон / лоджия`, `панорамные окна`, `окна во двор`, `кирпичный дом` и т.д.
- **Результат**: Вместо безликого "не удалось распознать", пользователь увидит конкретное сообщение: `«с выходом на солнечную сторону»: фильтр не поддерживается сайтом ПИК`. Это кардинально повысит доверие к боту.

### 3. Fallback-шаблоны для гео-маркеров
Для защиты от новых топонимов, которых нет даже в полных словарях (например, строящиеся станции метро или новые районы), можно добавить регулярные выражения с привязкой к предлогам.
- **Реализация**: Добавить в `rules.py` правило `(?i)у\s+метро\s+([а-яА-ЯёЁ-]+)`. Если оно срабатывает, но станция не находится в справочнике, возвращать специализированный warning: `Станция метро "..." не найдена в базе, пропущена`.

## Вывод
Проблема вызвана архитектурным компромиссом (справочники ограничены текущей выдачей ПИК) и скудным словарем "заведомо неподдерживаемых" фичей. Внедрение **Полного независимого справочника метро** и **Расширенной базы Unsupported-правил** полностью исключит возникновение аналогичных ошибок в будущем.
