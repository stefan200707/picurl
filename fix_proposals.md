# 🛠️ Предложения по улучшению парсинга

Анализ проблемы с запросом: 
> *«хочу двушку у метро Варшавская, до 15 млн, с отделкой, до 20 минут до метро, солнечная сторона»*

В текущей версии системы важные критерии попадают в массив `warnings` и отбрасываются из итогового URL. Ниже представлен разбор каждой утерянной сущности и варианты решения.

---

## 🚇 1. Станция метро «Варшавская»

**Почему не распознано?**
Механизм `entity_match.py` ищет совпадения только по эталонному словарю `app/reference/metro.json`. В текущей версии словаря содержится ограниченное количество станций (45), и станции «Варшавская» среди них нет. Без знания точного `GUID` станции, `url_builder` не сможет сформировать правильный URL (так как ПИК использует GUID для метро).

### Варианты решения:
1. **[Рекомендуемый] Расширение словаря:**
   * Дополнить файл `metro.json` недостающими станциями (включая Варшавскую) и их валидными `GUID` с сайта ПИК.
   * *Плюс*: Сохраняется консистентность и строгая валидация. 
   * *Минус*: Требует ручного сбора GUID (или обхода Qrator для автоматического парсинга API ПИКа).
2. **Мягкое извлечение (Soft-parsing):**
   * Изменить логику в `parser.py`: если найдено регулярное выражение `у метро <название>`, но станции нет в словаре, добавлять её в `warnings` с более понятным текстом (например, *"Станция метро 'Варшавская' не найдена в базе ПИК"*), а не просто *"не удалось распознать"*.

---

## ⏱️ 2. Фильтр «до 20 минут до метро»

**Почему не распознано?**
В текущих правилах структурных фактов (`app/parsing/rules.py`) и схеме (`schema.py`) не реализована поддержка фильтров удалённости от метро.

### Варианты решения:
1. **[Рекомендуемый] Добавление регулярного правила:**
   * **Шаг 1:** Расширить Pydantic-модель `Criteria` (`app/parsing/schema.py`), добавив поля `time_on_foot: int | None = None` и `time_on_transport: int | None = None`.
   * **Шаг 2:** Создать функцию `extract_time_to_metro(text)` в `app/parsing/rules.py`, которая будет искать паттерны вроде `r"(?:до|не более)\s+(\d+)\s*(?:мин|минут)?\s*до\s*метро"`.
   * **Шаг 3:** Обновить фасад `parser.py` для вызова нового правила.
   * **Шаг 4:** Внедрить логику в `url_builder.py` для трансляции в query-параметры `timeOnFoot=20` (согласно `docs/pik-url-schema.md`).

---

## ☀️ 3. Фильтр «солнечная сторона»

**Почему не распознано?**
Фильтра «солнечная сторона» не существует в поисковой системе на сайте ПИК. Система работает корректно, отправляя этот запрос в `warnings`, так как мы не можем отразить его в URL.

Однако текущий фасад `parser.py` сливает рядом стоящие нераспознанные токены в один общий кусок. В итоге пользователь видит нечитаемое сообщение: 
`"«до 20 минут до метро, солнечная сторона»: не удалось распознать..."`

### Варианты решения:
1. **[Рекомендуемый] Улучшение гранулярности предупреждений (warnings):**
   * В `parser.py`, при вычислении `unconsumed_spans`, разбивать оставшийся текст не только на непрерывные блоки, но и по запятым / союзам.
   * Итог: Пользователь получит два изолированных ворнинга:
     - `«до 20 минут до метро»: не удалось распознать` *(если не применён пункт 2)*
     - `«солнечная сторона»: этот фильтр не поддерживается сайтом ПИК` (если обучить парсер списку известных неподдерживаемых фич).
2. **Маппинг в опции (Options):**
   * Если у ПИК появится `options=sunnySide`, добавить маппинг через `options.json`. На данный момент таких опций нет.

3. **[UX/Warnings]** Доработать функцию разделения нераспознанного текста в `parser.py` по знакам препинания для формирования более аккуратных предупреждений.
