# CLAUDE.md

Проект: picurl (GitHub: stefan200707/picurl).

## Цель проекта

pik-url-builder
Сервис принимает свободный текст на русском языке о желаемой квартире ("хочу двушку у метро, до 15 млн, с отделкой") и возвращает рабочую ссылку на pik.ru с уже применёнными фильтрами и сортировкой — чтобы не тыкать вручную по чекбоксам на сайте.

Парсинг полностью детерминированный: регулярные выражения (regex) и нечёткий поиск (rapidfuzz) по локальным JSON-справочникам. Никаких LLM или медленных внешних API в рантайме — единственный сетевой вызов на запрос делает валидатор выдачи (проверочный запрос к backend `api.pik.ru`).

## Декомпозиция и промпты для сборки

В `prompts/` лежит готовая декомпозиция задачи — набор пронумерованных `.md`
промптов для пошаговой сборки сервиса (по одному на агента/шаг). Порядок и обзор —
в `prompts/README.md`; общие конвенции (стек, инварианты, структура) — в
`prompts/_conventions.md`; открытые вопросы — в `prompts/_open-questions.md`.

Порядок применения: 00 (каркас) → 01 (URL-схема pik.ru) → 02 (Criteria) →
03 (справочники) → 04 (regex-правила) → 05 (rapidfuzz-матчинг) → 06 (фасад parse)
→ 07 (url_builder) → 08 (валидатор) → 09 (POST /build-url) → 10 (интеграционные
тесты). Применять последовательно; после каждого шага гонять линт + тесты.
Сверх основной последовательности в `prompts/` лежат ещё два прикладных
фикс-промпта, применённые постфактум: `11-fix-price-and-warnings.md`
(парсинг «не более»/«не менее» в цене + расширение стоп-слов) и
`12-fix-missing-ids.md` (докурация отсутствующих `id` округов/метро). Оба
фикса подробно описаны в разделе «Стресс-тестирование парсера» ниже — это те
же исправления, зафиксированные как промпты.

Ключевые инварианты (детали в `prompts/_conventions.md`): никаких LLM/внешних API
в рантайме; единственный сетевой вызов на запрос — валидация выдачи через backend
API pik.ru; нераспознанное всегда уходит в `warnings`, ничего не отбрасывается
молча; справочники — отдельный локальный JSON-слой, обновляемый скриптом.

## URL-схема pik.ru — источник правды

**`docs/pik-url-schema.md`** — единственный источник правды по схеме фильтров
`pik.ru/search` (промпт 01, выполнен). На него опираются справочники (03),
`url_builder` (07) и `validator` (08). Центральное правило схемы —
**single-путь / multi-query**: одно значение фильтра → слаг в пути URL,
два и больше → query-параметр с id/GUID через запятую.

Решённые открытые вопросы (из `prompts/_open-questions.md`):

- **№1 (дефолтная сортировка):** если пользователь не указал сортировку,
  `sortBy`/`orderBy` не добавляются вовсе — действует дефолтная выдача сайта
  («рекомендуемые»).
- **№2 (Одиночные optionGroups):** одиночные `optionGroups` всегда добавляются
  в query-параметры (как и `options`), а не в путь URL.

## Контракт Criteria и модели API (промпт 02 — выполнен, с доработками)

- **`app/parsing/schema.py`** — внутренний контракт критериев: pydantic-модель
  `Criteria` (+ `Rooms`, `Finish`, `Sort`, `HousingType`, `MatchedEntity`). На
  неё опираются парсинг (промпты 04–06) и `url_builder` (07). «Пустой»
  `Criteria()` валиден: скаляры — `None`, списки — пустые. `rooms` — всегда
  список (single vs multi решает url_builder по длине); `sort` — строковый
  ключ `price_asc|price_desc|area_asc|area_desc` с properties `field`/`order`
  для `sortBy`/`orderBy`.
- **`finish` — по факту кода `list[Finish]`, а не `bool | None`.** `Finish` —
  `IntEnum` с 4 значениями: `NONE` (без отделки → слаг `bez-otdelki`),
  `READY` (готовая отделка → слаг `finish`), `WHITE_BOX` (предчистовая →
  слаг `predchistovaya-otdelka`), `FURNISHED` (с мебелью → query-параметр
  `hasFinish`). При одном выбранном значении `url_builder` кладёт
  READY/NONE/WHITE_BOX в путь, а FURNISHED — всегда в `hasFinish`; при
  нескольких выбранных значениях все уходят в `hasFinish` через запятую
  (`app/pik/url_builder.py`). Экстрактор `extract_finish`
  (`app/parsing/rules/finish.py`) при противоречивых упоминаниях сохраняет
  все уникальные запрошенные варианты, а не только последний.
- Помимо базовых фильтров, `Criteria` содержит поля `time_on_foot` /
  `time_on_transport` (время до метро), `settlement_year_from/to` и
  `settlement_month_from/to` (срок сдачи), `required_tags` (теги выгодных
  предложений вида `zos`/`cashback`/`crossed`/`outlet`), `current_benefit`,
  `view` — расширения контракта поверх исходного промпта 02, подтверждённые
  кодом и используемые `url_builder`/`validator` через общий метод
  `Criteria.to_query_dict()`.
- **Модели API** `BuildUrlRequest`/`BuildUrlResponse` по факту вынесены в
  **`app/api/schemas.py`** (не в `app/main.py`, как было в исходном плане
  промпта 02 и как всё ещё написано в докстринге `app/parsing/schema.py` —
  это устаревший комментарий в коде, ориентируйтесь на реальное расположение
  файла). `app/main.py` лишь создаёт FastAPI-приложение и подключает роутер
  `app.api.endpoints.router`. Ответ: `{url, criteria, result_count,
  warnings}`; человекочитаемое представление критериев для поля `criteria` даёт
  `Criteria.to_public_dict()` (пример: `{"rooms": "2", "price_max": 15000000,
  "metro": ["Аэропорт Внуково"], "finish": "готовая", "sort": "price_asc"}`).
  Поле `text` запроса имеет `examples` — Swagger-форма открывается
  предзаполненной. Тесты контракта — `tests/parsing/test_schema.py`.

## Справочники (промпт 03 — выполнен)

Локальный JSON-слой для матчинга сущностей (метро/округа/районы/ЖК/программы/
опции). Лежат в `app/reference/*.json`: `metro.json`, `counties.json`,
`districts.json`, `complexes.json`, `benefits.json`, `option_groups.json`,
`options.json`.

- **Формат записи** (единый для всех файлов): `{"name": "...", "slug": "...",
  "id": "...", "aliases": [...]}` — pydantic-модель `RefEntry` в
  `app/reference/loader.py`. Из-за правила single-путь/multi-query на сущность
  нужны **обе URL-формы**: `slug` (одиночный выбор → путь) и `id`/GUID
  (multi-выбор → query). `slug`/`id` опциональны — недостающую форму
  `parser`/`url_builder` обязаны отправлять в `warnings`, а не отбрасывать
  молча (на практике проверка вынесена в фасад `parse()`, см. ниже).
  `id` хранится строкой (единый формат для GUID метро и числовых id).
- **Загрузка**: `app/reference/loader.py` — функции `load_metro()`,
  `load_counties()`, …, агрегат `load_all() -> ReferenceData` (точка входа для
  матчера, промпт 05). Кэш через `functools.cache`; сброс — `clear_cache()`.
  Точный поиск по имени/алиасу — `find_by_name()` (нормализация: casefold,
  ё→е, схлопывание пробелов — `normalize()`); fuzzy — задача промпта 05.
  **Рантайм читает справочники только с диска, в сеть за ними не ходит.**
- **Обновление**: `uv run python -m app.reference.refresh` — единственное
  (кроме валидатора) место с сетевым доступом; тянет открытый backend
  `api.pik.ru/v2/block` и перезаписывает `complexes/counties/metro/districts`.
  Мёрж не затирает ручную докурацию (кураторские `slug`/`id`/`aliases`
  сохраняются), сортировка стабильная — диффы читаемы. Этот же refresh
  доступен и через HTTP: скрытый эндпоинт `POST /internal/refresh-dicts`
  (`app/api/endpoints.py`) запускает `run_refresh()`, сбрасывает кэш
  `loader.clear_cache()` и кэш матчера `entity_match.build_choices`.
- **Ограничение**: GUID-ы станций (`metroStations`) и числовые id округов
  (`districtCounties`) отдаёт только front-API `www.pik.ru` (закрыт бот-защитой
  Qrator) — эти поля докуриваются **вручную**; `benefits/option_groups/options`
  скрипт не трогает.
- Тесты: `tests/reference/test_loader.py`, `tests/reference/test_refresh.py`
  (сеть замокана через `httpx.MockTransport`).

## Regex-правила структурных фактов (промпт 04 — выполнен)

По факту кода это не файл, а **пакет `app/parsing/rules/`** из модулей
`core.py` (нормализация текста, `Span`, вспомогательные функции), `rooms.py`,
`price.py`, `area.py`, `floor.py`, `finish.py`, `time.py`, `misc.py`
(сортировка, срок заселения, требуемые теги, тип жилья, доступность,
неподдерживаемое, fallback-метро) и агрегатор `apply_rules()` в
`rules/__init__.py`. Каждая `extract_*` — чистая функция (regex + словари
синонимов, без сети/LLM/состояния), возвращает `(значение,
consumed_spans)` — список полуинтервалов `(start, end)` «понятых» кусков
исходного текста (для вычисления нераспознанного в фасаде `parse`, промпт
06). Матчинг — по нормализованной копии текста (lowercase + ё→е, длина
сохраняется — индексы валидны для исходной строки); regex скомпилированы
один раз на уровне модуля.

Поддерживаемые фильтры:

- **комнатность** (`extract_rooms`, `rooms.py`) — «студия», «однушка/двушка/трёшка»,
  «2к», «2-комнатную», «2-х комнатная», перечисления («1-2 комнатные»,
  «1, 2 и 3 …»), чип «3+» (и «2+» → `[two, three_plus]`); ≥3 комнат → чип `3+`;
- **цена** (`extract_price`, `price.py`) — «до/от/за X», диапазоны «10-15 млн», «бюджет
  15м», слитные суффиксы «800к», единицы млн/тыс/руб; нормализация в рубли;
  голые числа ≥ 100 000 → рубли (порог отсекает этажи/метры);
- **площадь** (`extract_area`, `area.py`) — общая («от 70 м²», «70-100 метров»,
  «площадь от 40») и кухня («кухня от 8», «с кухней от 10 метров») — различаются
  ключевыми словами, кухня извлекается первой;
- **время до метро** (`extract_time_to_metro`, `time.py`) — «10 минут до метро
  пешком», «метро в 15 минутах на машине» и т.п. → `time_on_foot` /
  `time_on_transport`. Реализовано чистым regex (словари предлогов/единиц),
  без внешних NLP-библиотек — в коде и в `pyproject.toml` нет зависимости
  Yargy или другого NLP-парсера;
- **этаж** (`extract_floor`, `floor.py`) — «с 5 по 20 этаж» → `floor_min/max`; «не первый»,
  «высокий этаж» → `not_first_floor`; «последний» → `last_floor`;
  «не последний» → `not_last_floor` (добавляет `notLastFloor=1`);
- **отделка** (`extract_finish`, `finish.py`) — четыре состояния `Finish`
  (список, не булево): «без отделки»/«черновая» → `NONE`; «с отделкой»/
  «чистовая»/«под ключ»/«ремонт» → `READY`; «предчистовая отделка» →
  `WHITE_BOX`; «отделка с мебелью»/«с мебелью» → `FURNISHED`. При
  противоречивых упоминаниях в тексте сохраняются все уникальные
  запрошенные варианты (не только последний);
- **заселение** (`extract_ready`, `finish.py`) — «заселение сразу», «готовый дом», «сдан» →
  `ready=True`;
- **срок сдачи** (`extract_settlement_year`, `misc.py`) — «в этом году», «заселение с 2026
  по 2027», «сдача до 2027», «въезд после 2025» → `settlement_year_from/to`;
- **сортировка** (`extract_sort`, `misc.py`) — «подешевле» → `price_asc`, «подороже» →
  `price_desc`, «площадь побольше/поменьше» → `area_desc`/`area_asc`;
- **теги выгодных предложений** (`extract_required_tags`, `misc.py`) —
  «готовые квартиры», «ипотека по формуле 0,1%», «специальная цена»,
  «выгода до -15%» → `required_tags` (`zos`/`cashback`/`crossed`/`outlet`);
- **прочее** — «только квартиры»/«без апартаментов» →
  `housing_type=flats_only` (`extract_housing_type`); «не бронь»/«только
  свободные»/«доступные» → `only_available` (`extract_only_available`);
- **неподдерживаемое** (`extract_unsupported`, `misc.py`) — «вторичка/вторичный рынок»
  (pik.ru — только новостройки), а также «солнечная сторона», «раздельный
  санузел», «панорамные окна», «окна во двор», «кирпичный дом»: критерии не
  трогаются, фрагмент исходного текста возвращается маркером для warning;
- **fallback-метро** (`extract_fallback_metro`, `misc.py`) — гео-маркер «у
  метро X», который не нашёлся в справочнике/матчере, уходит отдельным
  предупреждением («Станция метро "X" не найдена в базе, пропущена»), а не
  теряется молча.

Агрегат `apply_rules(text) -> RulesOutcome(criteria, consumed, unsupported,
fallback_metro)` прогоняет все правила и собирает готовый `Criteria`. Тесты —
`tests/parsing/test_rules.py` (табличные, `pytest.mark.parametrize`).

## API

**Интерфейс пользователя — это Swagger-форма на `/docs`** (своего фронтенда нет). 
Пользовательский сценарий:
1. Запустить сервис (`uv run fastapi dev`).
2. Открыть в браузере `http://127.0.0.1:8000/docs`.
3. Раскрыть `POST /build-url`, нажать **Try it out**.
4. Вписать желание в поле `text` (например: `"хочу двушку у метро, до 15 млн, с отделкой"`).
5. Нажать **Execute**.
6. В ответ приходит JSON-документ:
   ```json
   {
     "url": "https://www.pik.ru/search/...",
     "criteria": { "rooms": "2", "price_max": 15000000, ... },
     "result_count": 47,
     "warnings": []
   }
   ```

**Поток обработки** (эндпоинт `POST /build-url` в `app/api/endpoints.py`):
1. Принимается запрос `BuildUrlRequest` со строкой `text`.
2. `parse(text)` извлекает `Criteria` и список предупреждений `warnings`.
3. `build_url(criteria)` строит ссылку `url` на основе собранных критериев.
4. `validate(criteria, client)` делает проверочный HTTP-запрос к
   `api.pik.ru/v2/filter`. Если результатов 0, в `warnings` добавляется:
   `"под критерии ничего не найдено"`; при сетевой ошибке/ошибке статуса/
   парсинга — best-effort деградация (`result_count=None`,
   `"выдача не проверена"`/`"выдача не проверена (ошибка сервиса)"`), сервис
   не падает.

Кроме основного эндпоинта есть скрытый служебный **`POST
/internal/refresh-dicts`** (`app/api/endpoints.py`) — обновляет справочники
(`run_refresh()`) и сбрасывает кэши (`loader.clear_cache()`,
`entity_match.build_choices.cache_clear()`) без перезапуска процесса.

- Линт: `uv run ruff check`; формат: `uv run ruff format` (проверка: `--check`)
- Обновление справочников: `uv run python -m app.reference.refresh` (или HTTP `POST /internal/refresh-dicts`)

Пользовательский интерфейс — Swagger-форма на `http://127.0.0.1:8000/docs`
(своего фронтенда нет).

В ruff включены наборы правил E, W, F, I, UP, B, SIM, C4, RUF
(`line-length = 100`, `target-version = "py312"`); отключены RUF001–RUF003
(ambiguous unicode): проект намеренно использует русский текст в строках,
докстрингах и комментариях.

## Стресс-тестирование парсера (`stress_test_queries.md`)

`stress_test_queries.md` — 10 объёмных запутанных запросов (противоречия,
сленг, опечатки, «вода») для ручной проверки устойчивости парсера. По итогам
прогона все 10 пунктов через `POST /build-url` найден и исправлен ряд багов:

- **Матчер сущностей** (`app/parsing/entity_match.py`) ложно матчил короткие/
  служебные слова на случайные сущности справочника («мы» → район «Мытищи»,
  «молодая» → метро «Молодежная», обрывок «Этаж … Ищем» → опция «Два и более
  санузла»), потому что заглавная буква (первое слово предложения — не
  признак имени собственного) или триггер-слово полностью отключали защитную
  проверку `QRatio`. Убрана привилегия по заглавной букве; «синтетические»
  окна эвристики союзов («и»/«или», склеивающие слова из разных мест текста)
  теперь всегда проверяются строго — это же убрало и ложную сущность/
  предупреждение об неоднозначности («Бульвар МЦК» → «Бульвар Адмирала
  Ушакова», «метро Строгино Мякинино» → мнимая неоднозначность с Мякинино).
- **regex-правила** (`app/parsing/rules/`, промпт 11): «высокий этаж»/«площадь
  общая» распознавались только в одном порядке слов (не в обратном — «этаж
  высокий»/«площадь общая»); ключевые слова «кухня»/«площадь» не допускали
  связку перед числом («кухня была от 12», «кухня чтоб большая от 12») — из-за
  этого площадь кухни могла попасть в общую площадь или потеряться целиком.
  Добавлена поддержка обратного порядка и типовых связок.
  Добавлена единица «лям/ляма/лямов» (разговорный синоним «миллион») и
  триггер «бабок/бабки» для цены; в `_PRICE_MAX`/`_PRICE_BUDGET` добавлено
  «не более», в `_PRICE_MIN` — «не менее» (стоимость «не более 25 000 000
  руб» раньше не распознавалась и падала в warnings).
- **Справочник округов** (`app/reference/counties.json`): в «Новомосковский
  АО» добавлен алиас «ТиНАО» — без него округ не распознавался вовсе.
  Отдельно (промпт 12) в `counties.json` и `metro.json` докурены
  недостающие `id`/GUID для округов и станций, которые правильно
  распознавались матчером, но молча выпадали из URL при multi-query
  (`districtCounties`/`metroStations`) из-за отсутствия `id`.
- **warnings-шум**: список стоп-слов в `app/parsing/stopwords.py`
  (`STOP_WORDS`, используется фасадом `app/parsing/parser.py`) расширен
  дискурсивными связками («может», «ну», «то», «хотя», сленг «кароче»/«шоб»/
  «хата», а также «желательно», «чтобы», «была», «обязательно»,
  «рассматриваю», «покупку», «недвижимости», «варианты», «сортировка»,
  «этаж», «метро», «м», «кв», «метров» и т.п.) — раньше они давали
  бессмысленные предупреждения о «нераспознанном» тексте. Также исправлено
  разбиение нераспознанных кусков по точке — оно резало и точку внутри
  дробных чисел («1.5» → «1» + «5м»). Добавлен триггер «район X» без
  предлога «в» (по аналогии с «округ X»/«жк X»).

**Известные ограничения (не исправлялись, задокументированы, не баги кода):**
справочники метро/районов/округов сильно неполны по GUID/id (обновляются
только вручную — см. раздел «Справочники» выше) и по составу (напр.
«Некрасовка», «Раменки»/«Солнцево» как районы отсутствуют) — заполнять их
нужно официальными данными, а не подбором, чтобы не создавать нерабочие
ссылки. Условные/эллиптические конструкции («если 3-комнатная, то 15 млн»,
«…с 5 по 10» без повторного «этаж») требуют NLU за пределами regex-парсера —
корректно уходят в warnings, а не додумываются.
