# Замер: аудит справочных id против настоящего эндпоинта (шаг J, вариант Б)

Дата: 2026-07-28. Инструмент: `scripts/reference_audit.py`.
Эндпоинт: `GET https://flat.pik-service.ru/api/v1/filter/block-with-flats`.

## Итог одной строкой

Из **176** справочных id живы **158**, мертвы **14**, ещё **4** — «мёртвый или
невалидный» (различить нечем). Все 10 id округов мертвы: `counties.json`
содержит **чужую номенклатуру**, и 9 из 10 замен выводятся из фасета
автоматически, 2 пустых записи заполняются, а 3 не чинятся ничем.

## Почему вариант Б, а не миграция рантайма

Из четырёх вариантов шага J выбран **Б: настоящий эндпоинт только для аудита
справочников**. Причина отказа от рантайм-миграции — ловушка с User-Agent,
которую два предыдущих шага описали **по-разному**:

| Шаг | Утверждение |
|---|---|
| J | отсекается подстрока `curl/`, честный `picurl/1.0` проходит |
| L | на `/flat` заглушку получают и `picurl/1.0`, и `python-httpx` |

Эвристика отбора UA не понята, а деградирует она **молча**: HTTP 200, валидный
JSON, неверные числа. Ставить такое в рантайм рано. Скрипт — уровня `refresh*`:
сеть есть, но это офлайн-инструмент, инвариант 6 не затронут.

## Метод

* Проверка — **сужением выдачи**, а не наличием в фасете. Методическое правило
  шага K: фасет перечисляет доступное *при текущем фильтре*, поэтому отсутствие
  id в фасете **не** доказывает невалидность (там три из четырёх расхождений
  оказались артефактами сверки). Членство в фасете печатается как справка и в
  вердикт не входит.
* Базис для metro/districts/counties — `types=1,2&location=2,3` (Москва+МО).
  Для `blocks` **`location` намеренно не задан**: он отсекал бы региональные ЖК,
  и 28 записей попали бы в «мёртвые» по нашей же вине.
* Браузерный UA + cache-buster `_` на каждом запросе.
* Нули и «невалидные» перепроверяются повтором; HTTP 5xx переспрашивается один
  раз, прежде чем считать id невалидным (5xx бывает транзиентным).

### Признак «невалидного» у каждого параметра свой — это главная ловушка

| параметр | мусорное значение | реакция бэкенда | как читать |
|---|---|---|---|
| `metroStations` | `deadbeef-…` | `count == baseline`, **не ошибка** | «не сузил» = невалидный |
| `districtLocations` | `999999` | HTTP 500 | ошибка = невалидный |
| `districtCounties` | `999999` | HTTP 500 | ошибка = невалидный |
| `blocks` | `999999` | `count = 0` | **неотличимо от мёртвого** |

Поэтому у `blocks` вердикт честно называется `мёртвый/невалидный`: через этот
эндпоинт эти два случая не различаются. Реестр `/api/v1/filter/block` содержит
только ЖК, которые **сейчас в продаже**, поэтому «был и распродан» от «не
существовал» он тоже не отделяет.

Перед прогоном каждого справочника скрипт шлёт это мусорное значение как
**контрольную пробу** и падает, если реакция не та, что в таблице.

## Детектор заглушки: два независимых рубежа

**Рубеж 1 — маркер стадии в `data.time`.** Маркер **у каждого маршрута свой**:

| маршрут | маркер настоящего ответа |
|---|---|
| `/api/v1/filter/block-with-flats` | `filter_block` |
| `/api/v1/filter/block` | `statsEmpty` |
| `/api/v1/filter/flat` | `statsEmpty` |

Замерено: браузерный UA → `data.time` = `['filter_block', 'filter', 'stats',
'statsEmpty']`; `curl/8.7.1` → `['filter', 'stats']`. Проверка детектора
намеренной подделкой UA:

```
$ uv run python scripts/reference_audit.py --stub-ua --kinds counties
ЗАГЛУШКА: ответ …/block-with-flats без маркера `filter_block` в data.time
(есть: ['filter', 'stats']) — это тихая заглушка с НЕПРИМЕНЁННЫМИ фильтрами.
Числам верить нельзя, аудит прерван.
EXIT=2
```

Ни одной цифры не напечатано — это и требовалось: молча объявить 158 живых id
мёртвыми хуже, чем не выдать отчёта вовсе.

**Рубеж 2 — контрольная проба.** Проверено отдельно: при **отключённом**
детекторе и заглушечном UA baseline становится 24088, и контрольная проба ловит
подделку самостоятельно:

```
детектор отключён, baseline с curl-UA = 24088
>>> ВТОРОЙ РУБЕЖ СРАБОТАЛ: districtCounties: мусор `999999` вернул count=24088
    без ошибки, а ожидался HTTP 500 (режим `error`). Классификация недостоверна.
```

Полезная деталь о форме отказа: под заглушкой вердикты выродились бы **не** в
нули, а в «не сузил (аномалия)» для всех id разом — то есть сбой шумный, а не
тихий, но полагаться на это нельзя, потому и рубежа два.

### Ловушка при проверке самого детектора

Первая попытка проверки была **некорректной**: `user_agent: str = BROWSER_UA` —
значение по умолчанию, связанное при определении функции, поэтому подмена
`ra.BROWSER_UA` на уровне модуля ничего не меняла, и «проверка» шла настоящим
браузерным UA (baseline 8186 вместо 24088). Признак подделки, которую не
заметили: baseline совпал с честным. Проверять подмену UA нужно, передавая UA
явным аргументом.

## Разбор округов

### Номенклатура действительно чужая

Все 10 id из `counties.json` дают `count=0`, при этом мусор `999999` даёт HTTP
500 — значит бэкенд наши id **распознаёт как синтаксически годные, но пустые**,
а не отвергает. Фасет отдаёт совсем другой ряд: `[2, 6, 9, 75, 88, 133, 134,
135, 136, 137, 514]`, и каждое из этих значений реально сужает выдачу.

### Имён в фасете нет — их пришлось выводить

Фасет `data.stats.district.districtCounties` — **голые int, без имён**.
Поэтому «сопоставить по именам» напрямую невозможно. Обходной путь скрипта: для
каждого id округа взять фасет `blocks` (какие ЖК доступны при этом фильтре) и
посмотреть поля `county`/`district` у этих ЖК в нашем `complexes.json`, а имена
самих ЖК подтянуть из реестра `/api/v1/filter/block`.

| id фасета | count | ЖК | `county` наших ЖК | вывод | как получен |
|---|---:|---:|---|---|---|
| 2 | 416 | 4 | ЮАО×3 | **ЮАО** | автоматически |
| 6 | 417 | 4 | ЗАО×3 | **ЗАО** | автоматически |
| 9 | 666 | 4 | ВАО×2 | **ВАО** | автоматически |
| 75 | 635 | 5 | СЗАО×2, САО×2 | **САО** | вручную (ничья) |
| 88 | 1265 | 4 | НАО×3, Щербинка×1 | **Новомосковский АО** | автоматически |
| 133 | 2652 | 8 | — не размечено | **Московская область** | вручную |
| 134 | 485 | 5 | СВАО×5 | **СВАО** | автоматически |
| 135 | 540 | 3 | ЮВАО×3 | **ЮВАО** | автоматически |
| 136 | 19 | 1 | ЮЗАО×1 | **ЮЗАО** | автоматически |
| 137 | 757 | 3 | СЗАО×1 | **СЗАО** | автоматически |
| 514 | 331 | 1 | — не размечено | **ЗелАО** | вручную |

Как разрешены три ручных случая:

* **75 — ничья СЗАО×2 / САО×2 создана нашей же ошибкой.** У «Кронштадтский 9» и
  «Нарвин» в `complexes.json` стоит `county=СЗАО` при `district=Головинский`, а
  Головинский район — это САО. Остальные ЖК группы (Бусиновский парк —
  Западное Дегунино, Большая Академическая 85 — Тимирязевский, Онежский вал —
  Головинский) тоже САО. Итог: **75 = САО**, а в `complexes.json` две записи
  размечены неверно. Это отдельный дефект данных, в этом шаге не правился.
* **137 = СЗАО** — Митинский лес, Строгино 360, Квартал Мит (Митино и Строгино).
  Снимает конфликт с 75.
* **133 = Московская область** — Восточное Бутово (Ленинский), Ярославский и
  Яуза парк (Мытищи), Ильинские луга (Красногорск), Белая Дача парк
  (Котельники), Кузьминский лес и Томилинский бульвар (Люберцы). Самый крупный
  округ фасета (2652) — и в `counties.json` «Московская область» единственная
  запись вообще без URL-форм.
* **514 = ЗелАО** — единственный ЖК «Зелёный парк», `district=Крюково`
  (Зеленоград).

### Что чинится автоматически, а что нет

**Чинится автоматически по фасету (7 замен):** ВАО 33→9, ЗАО 34→6, НАО 35→88,
СВАО 32→134, ЮАО 7→2, ЮВАО 38→135, ЮЗАО 36→136. Вывод получен большинством
голосов по полю `county` наших ЖК, единственным и непротиворечивым.

**Чинится, но требует ручной сверки (2 замены + 2 заполнения):**
САО 59→75 и СЗАО 37→137 (ничью разрешает `district`, а не `county`, потому что
`county` в двух записях `complexes.json` неверен); плюс безid'ные сейчас
**Московская область**→133 и **ЗелАО**→514.

**Не чинится ничем из имеющегося (3 записи):**

* **ЦАО** — id нет и в фасете его нет. ПИК сейчас ничего в ЦАО не продаёт, так
  что вывести id неоткуда: он не появится в фасете, пока не появится
  предложение.
* **Троицкий АО** — то же самое.
* **Щербинка** (66) — отдельного округа у этого бэкенда нет вовсе: её ЖК
  («Бунинская набережная») лежит под 88 = Новомосковский АО. Присвоить ей 88
  было бы семантически неверно — это решение человека, не скрипта.

### Почему это не противоречит правилу шага K

Правило «отсутствие в фасете ≠ невалидный id» здесь **соблюдено**: вывод об
округах сделан не по отсутствию наших id в фасете, а по тому, что каждый из них
при прямом запросе даёт `count=0`, тогда как мусор даёт HTTP 500 — то есть по
сужению выдачи. Фасет использован только как источник **кандидатов на замену**.

## Что этот замер не доказывает

* «Мёртвый» — состояние на дату замера, а не свойство id: распроданный ЖК
  сегодня даёт 0, а завтра при новом корпусе — не 0. Удалять id по одному
  прогону нельзя.
* Для `blocks` «мёртвый» и «невалидный» не разделены в принципе (см. выше).
* Проверялся **один** id за запрос. Совместное поведение (`blocks=a,b`,
  пересечение округа с метро) не проверялось.

## Как воспроизвести

```
uv run python scripts/reference_audit.py                       # полный аудит
uv run python scripts/reference_audit.py --counties-probe      # только округа
uv run python scripts/reference_audit.py --stub-ua --kinds counties   # детектор
uv run python scripts/reference_audit.py --json-out /tmp/refaudit.json
```
