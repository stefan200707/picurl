# Перемер пяти «игнорируемых» параметров против настоящего эндпоинта

**Дата прогона:** 2026-07-28, ветка `main`. **Код не менялся — это замер.**
Вход — шаг J (`2026-07-28-block-with-flats.md`): настоящий эндпоинт выдачи
pik.ru установлен и вызывается с нашего бэкенда.

**Повод.** Раздел «Потолок pik.ru» утверждал, что бэкенд игнорирует пять
параметров: `metroStations`, `districtLocations`, `districtCounties`, `finish`,
`settlementYearFrom/To`. Все замеры делались против `api.pik.ru/v2/filter` —
эндпоинта, которым сам pik.ru не пользуется. Здесь то же самое перемерено
против `https://flat.pik-service.ru/api/v1/filter/block-with-flats`.

## Итог одной строкой

Из пяти параметров **три работают** на настоящем эндпоинте, **один не работал
никогда ни на одном — потому что мы шлём неверное имя**, и **один действительно
не применяется нигде**. Плюс `rooms=3`, который валит `v2/filter` в 500, на
настоящем эндпоинте отрабатывает штатно.

## Методика

Та же, что применялась к `v2/filter`: сравнение `count` с baseline, реальный
идентификатор против заведомо несуществующего.

- Базис `v2/filter`: `types=1,2&rooms=2` → **2658**.
  (`rooms=3` там 500, поэтому базисом взята двушка — см. `2026-07-28-validator-500.md`.)
- Базис настоящего: `types=1,2&rooms=2&location=2,3` → **2659**.
  `location=2,3` (Москва+МО) обязателен, иначе в выдачу попадают регионы.
- Настоящий эндпоинт: браузерный User-Agent, уникальный cache-buster,
  **3 прогона на замер**, результат принимается только при согласии всех трёх.
- Отсев «тихой заглушки» (HTTP 200 с непримененными фильтрами) — по отсутствию
  `data.time.filter_block`. За все прогоны заглушек не поймано.

Скрипты прогона — в скратчпаде сессии, в репозиторий не берутся; воспроизведение
через `scripts/block_with_flats_poc.py` и `curl` (см. «Как воспроизвести»).

### Разбор по параметрам

**`metroStations` — работает.** Реальный GUID сужает 2659 → 39. Несуществующий
GUID не даёт ошибки и не меняет count: **невалидное значение здесь молчит**,
поэтому `count`, равный baseline, сам по себе не доказывает, что фильтр применён.

**`districtLocations` — работает.** 2659 → 84. В отличие от метро, мусорный id
даёт HTTP 500, а не тишину.

**`districtCounties` — работает, но наши id не из той номенклатуры.**
Параметр применяется (id `2` → 166), однако **все 10 id из `counties.json` дают
count=0**, а фасет эндпоинта возвращает `[2, 6, 9, 75, 88, 133, 134, 135, 136,
137, 514]` — пересечение с нашими `[7, 32, 33, 34, 35, 36, 37, 38, 59, 66]`
**пустое**. Подробнее — §3.

**`finish` — параметр назван неверно, и это не потолок эндпоинта.**
Имя `finish` не читает ни `v2/filter`, ни настоящий. Рабочее имя — `hasFinish`,
и оно **фильтрует на обоих эндпоинтах**, включая тот, куда ходит валидатор
сегодня. То есть «бэкенд игнорирует отделку» было ошибочным выводом из
неправильного имени параметра, а не свойством бэкенда.

Наш `url_builder` в пользовательской ссылке уже шлёт `hasFinish`
(`url_builder.py:45-56`), а валидатор в проверочный запрос — `finish="1"`
(`validator.py:167-168`). Имена разошлись; проверяется то, чего не существует.

Разница между эндпоинтами по этому параметру всё же есть: `v2/filter` понимает
только одиночные значения `1`/`2`/`3`, а `hasFinish=0` и мульти-форму
(`1,2`) молча роняет в baseline. Настоящий эндпоинт обрабатывает и ноль, и
списки, причём суммы сходятся точно (2153+430=2583).

**`settlementYearFrom/To` — действительно не применяется нигде.** Ни годы, ни
месяцы, ни `settlement=` с реальным значением из фасета `stats.settlements`, ни
`settlements=`. Единственный параметр из пяти, для которого исходное утверждение
остаётся верным **на обоих эндпоинтах**. При этом настоящий эндпоинт срок сдачи
**знает** — отдаёт фасет доступных дат и поле `settlementDate` в карточке
квартиры; недоступен именно фильтр, а не данные.

## 2. Комнатность

Базисы: `types=1,2` (v2) и `types=1,2&location=2,3` (настоящий).

| Случай | `v2/filter` | настоящий |
|---|---|---|
| без `rooms` | 8205 | 8209 |
| `rooms=-1` (студия) | 1089 | 1091 |
| `rooms=1` | 3446 | 3447 |
| `rooms=2` | 2658 | 2659 |
| **`rooms=3`** | **HTTP 500** | **1012** |
| **`rooms=2,3`** | **HTTP 500** | **3671** |
| `rooms=1,2,3` | HTTP 500 | 7118 |
| `rooms=4` | 3 | 8209 ← игнор |
| `rooms=0` | 8205 | 8209 ← игнор |
| `rooms=99` | HTTP 500 | 8209 ← игнор |

**`rooms=3` и `rooms=2,3` на настоящем эндпоинте отрабатывают штатно.** Дефект
HTTP 500 — свойство исключительно `v2/filter`. Списки тоже работают и
складываются осмысленно (1012 + 2659 = 3671 ровно).

Побочно: настоящий эндпоинт **молча игнорирует** нераспознанные значения
комнатности (`4`, `0`, `99` → полный baseline), тогда как `v2/filter` на `4`
отвечает осмысленным `3`, а на `99` падает. Нас это не задевает — `Rooms.id`
принимает только `-1|1|2|3` (`schema.py:59-67`), значения `4` мы не шлём. Но
правило то же, что с метро: **baseline-count не отличим от «фильтр не понят»**.

## 3. Побочная находка: `counties.json` — чужая номенклатура

Базис — Москва+МО, все комнатности: `count=8209`, `countBlocks=43`.
Поштучно все id из `counties.json`:

| Округ | наш id | `count` |
|---|---|---|
| ВАО | 33 | 0 |
| ЗАО | 34 | 0 |
| Новомосковский АО | 35 | 0 |
| САО | 59 | 0 |
| СВАО | 32 | 0 |
| СЗАО | 37 | 0 |
| Щербинка | 66 | 0 |
| ЮАО | 7 | 0 |
| ЮВАО | 38 | 0 |
| ЮЗАО | 36 | 0 |
| ЗелАО, Московская область, Троицкий АО, ЦАО | — | id отсутствует, в query не попадают |

Для сравнения — id из фасета самого эндпоинта: `2`→413, `6`→417, `9`→668,
`75`→636, `88`→1271, `133`→2659, `134`→489, `135`→541, `136`→19, `137`→760,
`514`→333. Все дают ненулевую выдачу.

**Десять из десяти наших id округов не дают ничего.** Раньше это было
невозможно заметить: `v2/filter` игнорировал `districtCounties` целиком, поэтому
дефект (если это дефект) был невидим по построению. Это отдельная задача —
здесь только фиксируется факт.

### Сверка остальных справочников с фасетами

| Справочник | id у нас | признаёт эндпоинт | расхождение |
|---|---|---|---|
| `metro.json` | 61 | 58 | 3 |
| `districts.json` | 34 | 31 | 3 |
| `counties.json` | 10 | **0** | **10** |
| `complexes.json` | 71 | 43 | 28 |

Три расхождения из четырёх при проверке оказались **не дефектами**:

- **`complexes.json`, 28 «непризнанных»** — региональные ЖК (Волга парк, Исеть
  парк, Зея парк, Витебский парк…), отсечённые `location=2,3`. Фасет перечисляет
  только доступное при текущем фильтре, так что это артефакт сверки.
- **`districts.json`, 3 «непризнанных»** — у двух записей id составные
  (`Чертаново Южное=528,208`, `Южное Бутово=215,516`), сверка множеств их не
  видит; прямой вызов работает: 7 и 1080. Реально пустой один — `Люберецкий=111` → 0.
- **`metro.json`, 3 «непризнанных»** — `Митино` и `Мякинино` уже помечены в
  `app/pik/id_trust.py::SUSPICIOUS_METRO_IDS`, живой замер это **подтверждает**
  (обе → 0). Третья — `Мичуринский проспект` → 0, статус неясен: GUID выглядит
  как настоящий (та же серия `1ee78b52-…`), рядом просто может не быть ЖК.

**Важно для будущих сверок:** отсутствие значения в фасете ≠ невалидный id.
Фасет — «что доступно при текущем фильтре», а не «что вообще существует».

## 4. Что из этого следует для кода

Правки не делались — перечень для отдельной задачи.

| Запись в `validator.py` | Статус после перемера |
|---|---|
| `UNVERIFIED_LOCATION_PARAMS`: `metroStations` | лишняя **после** перехода на настоящий эндпоинт |
| `UNVERIFIED_LOCATION_PARAMS`: `districtLocations` | то же |
| `UNVERIFIED_LOCATION_PARAMS`: `districtCounties` | то же |
| `UNVERIFIED_NON_LOCATION_PARAMS`: `finish` | **ошибочна уже сейчас** — верное имя `hasFinish`, работает и на `v2/filter` |
| `UNVERIFIED_NON_LOCATION_PARAMS`: `settlementYearFrom` | **верна на обоих эндпоинтах**, остаётся |
| `UNVERIFIED_NON_LOCATION_PARAMS`: `settlementYearTo` | то же |

Отдельно: `settlementMonthFrom/To` уходят в проверочный запрос
(`validator.py:160` через `to_query_dict()`), так же не применяются, и в списке
непроверяемых **их нет** — список неполон.

## Как воспроизвести

```bash
# метро: реальный GUID против несуществующего
for G in 1ee78b52-0be1-65de-bef4-d7f06b038fc5 deadbeef-0000-0000-0000-000000000000; do
  curl -sS -A 'Mozilla/5.0' \
    "https://flat.pik-service.ru/api/v1/filter/block-with-flats?types=1,2&rooms=2&location=2,3&metroStations=$G&_=$RANDOM$RANDOM" \
    | python3 -c 'import json,sys; print(json.load(sys.stdin)["data"]["stats"]["count"])'
done          # ожидание: 39, затем 2659 (baseline)

# отделка: наше имя против рабочего, на ОБОИХ эндпоинтах
for P in finish=1 hasFinish=1; do
  echo -n "v2  $P -> "; curl -sS "https://api.pik.ru/v2/filter?types=1,2&rooms=2&$P" \
    | python3 -c 'import json,sys; print(json.load(sys.stdin)["count"])'
done          # ожидание: 2658 (игнор), затем 2191 (фильтрует)

# комнатность: 500 только на v2
curl -sS -o /dev/null -w 'v2 rooms=3 -> HTTP %{http_code}\n' 'https://api.pik.ru/v2/filter?types=1,2&rooms=3'
curl -sS -A 'Mozilla/5.0' \
  "https://flat.pik-service.ru/api/v1/filter/block-with-flats?types=1,2&rooms=3&location=2,3&_=$RANDOM$RANDOM" \
  | python3 -c 'import json,sys; print("настоящий rooms=3 ->", json.load(sys.stdin)["data"]["stats"]["count"])'
```

Числа живые и будут дрейфовать; воспроизводится не значение, а **соотношение**:
сузилось против baseline или совпало с ним.
