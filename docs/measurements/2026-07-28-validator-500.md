# Замер: HTTP 500 на `api.pik.ru/v2/filter`, `result_count=null`

Дата прогона: **2026-07-28**. Ветка `main`. Код не менялся — это замер, не правка.

Повод: во всех прогонах за день `result_count=null`, причина названа как «api.pik.ru
отдаёт 500, отказ устойчивый». Задача — установить границу отказа фактами, а не
рассуждением по коду.

## Итог одной строкой

Эндпоинт **жив и здоров**. 500 даёт не он вообще, а **одно конкретное значение
параметра: `rooms=3`** (а также 6, 7, 8, 9, 10). Это `Rooms.THREE_PLUS` — «трёшка
и больше», самая частая комнатность в нашем корпусе сложных запросов. Дефект —
на стороне pik.ru, воспроизводится голым curl без нашего кода.

---

## 1. Отказ не универсален

```
$ curl -sS -o /tmp/a.json -w 'HTTP=%{http_code} size=%{size_download}\n' \
    'https://api.pik.ru/v2/filter'
HTTP=200 size=1777016
{"count":8216,"countBlocks":43,...}

$ curl -sS -o /tmp/b.json -w 'HTTP=%{http_code}\n' \
    'https://api.pik.ru/v2/filter?blocks=477'
HTTP=200
{"count":117,"countBlocks":1,...}
```

Минимальный набор (один `blocks`) отвечает 200 и осмысленным числом.

## 2. Граница: бисект по одиночным параметрам

Каждый параметр из «упавших» запросов — по одному, остальные убраны:

| Параметр | HTTP | count |
|---|---|---|
| `rooms=3` | **500** | `{"success":false,"data":{"error":"FATAL_ERROR"}}` |
| `finish=1` | 200 | 8216 |
| `floorFrom=7` | 200 | 5719 |
| `floorTo=20` | 200 | 6730 |
| `notFirstFloor=1` | 200 | 8120 |
| `notLastFloor=1` | 200 | 7578 |
| `status=free` | 200 | 7881 |
| `districtCounties=32` | 200 | 8216 |
| `optionGroups=manybathrooms` | 200 | 8216 |
| `areaKitchenFrom=15.0` | 200 | 5796 |
| `settlementYearFrom=2026` | 200 | 8216 |
| `settlementYearTo=2029` | 200 | 8216 |
| `timeOnFoot=10` | 200 | 2738 |
| `priceTo=18000000` | 200 | 4765 |

Единственный виновник — `rooms=3`.

## 3. Карта значений `rooms`

```
rooms=-2   HTTP=200  count=0
rooms=-1   HTTP=200  count=1093     <- студия, наш Rooms.STUDIO
rooms=0    HTTP=200  count=8216     (= baseline, значение игнорируется)
rooms=1    HTTP=200  count=3448     <- Rooms.ONE
rooms=2    HTTP=200  count=2664     <- Rooms.TWO
rooms=3    HTTP=500  FATAL_ERROR    <- Rooms.THREE_PLUS
rooms=4    HTTP=200  count=3
rooms=5    HTTP=200  count=0
rooms=6    HTTP=500  FATAL_ERROR
rooms=7    HTTP=500  FATAL_ERROR
rooms=8    HTTP=500  FATAL_ERROR
rooms=9    HTTP=500  FATAL_ERROR
rooms=10   HTTP=500  FATAL_ERROR
rooms=03   HTTP=500  FATAL_ERROR
rooms=3.0  HTTP=500  FATAL_ERROR
rooms=     HTTP=200  count=8216
```

Списки наследуют дефект от элемента: `1,2` → 200/6112; `2,3`, `3,4`, `1,2,3` → 500.

Косвенная арифметика: 1093 + 3448 + 2664 + 3 + 0 = 7208 при общем 8216. Недостающие
≈1008 — это и есть трёшки, которые бэкенд не может посчитать.

## 4. Дефект зависит от значения, не от данных

Сужение до заведомо пустой выборки не спасает — значит, падает построение запроса,
а не обработка найденных строк:

```
rooms=3&blocks=999999   HTTP=500  FATAL_ERROR     (заведомо 0 строк)
rooms=6&blocks=999999   HTTP=500  FATAL_ERROR
rooms=4&blocks=999999   HTTP=200  {"count":0,...} (контроль)
```

Сужение по ЖК и по цене — тот же 500: `rooms=3&blocks=477`, `rooms=3&blocks=411`,
`rooms=3&blocks=118`, `rooms=3&priceTo=10000000`, `rooms=3&priceFrom=50000000`.

Повторяемость: пять одинаковых запросов `rooms=3` подряд — пять раз 500.

## 5. Это не блокировка

Заголовки при 500:

```
HTTP/1.1 500 Internal Server Error
Server: QRATOR
Content-Type: application/json
X-Powered-By: Digital
Access-Control-Allow-Origin: *
Set-Cookie: qrator_msid2=...
```

Тело — `{"success":false,"data":{"error":"FATAL_ERROR"}}`, то есть JSON приложения,
а не страница фильтра. Qrator стоит фронтом и на успешных ответах тоже
(`Server: QRATOR` при 200), запрос он пропускает — падает origin за ним.

Как выглядит настоящая блокировка Qrator, для контраста:

```
$ curl 'https://api.pik.ru/v2/filter?rooms=три'
HTTP=403  <!doctype html><html><head><title>Access Blocked</title>...
```

403 + HTML. Ни одного такого ответа на легитимных запросах не получено.

Дополнительно: на 200 присутствует `X-NginxCacheUrl: PIK2:/v2/filter?rooms=2`,
на 500 его нет — отказ не закэширован, каждый раз свежий от origin.

## 6. Контракт не менялся

Замеры из `docs/external-facts.md` от 2026-07-27 повторены сегодня один в один:

| Запрос | Было 27.07 | Стало 28.07 |
|---|---|---|
| `blocks=477&rooms=1` | 54 | 55 (HTTP 200) |
| `blocks=477&rooms=1&finish=0` | 54 | 55 (HTTP 200) |
| `blocks=477&rooms=1&settlementYearFrom=2030&settlementYearTo=2031` | 54 | 55 (HTTP 200) |
| `blocks=411&timeOnFoot=12` | 0 | 0 (HTTP 200) |
| `blocks=999999` | 0 | 0 (HTTP 200) |

Формат тела, заголовки, обязательные поля, путь `/v2/filter`, метод GET, имена
параметров — прежние. Смена 54→55 показывает, что данные у них живые и обновляются.

Соседние версии пути:

```
/v1/filter?rooms=3           HTTP=422  {"error":"ERR_EMPTY_TYPE"}
/v1/filter?type=1&rooms=3    HTTP=200  ключи: districts, prices, blocks, settlements
                                       -> поля `count` НЕТ
/v3/filter?rooms=3           HTTP=200  Content-Type: text/html, тело пустое (0 байт)
```

`v3` не существует, `v1` — эндпоинт фасетов без `count`. Мигрировать некуда.

## 7. Влияние на корпус

Полный прогон `tests/corpus/complex_queries.txt` через реальный `validate()`:

```
запросов: 36
HTTP 500 (result_count=null): 14
HTTP 200 (count получен):     22
из 500-х содержат rooms с "3": 14 / 14
```

**14 из 14 отказов объясняются ровно этой причиной** — других источников 500 нет.
39 % корпуса теряет проверку выдачи; остальные 61 % проверяются как обычно.

## 8. Когда началось

Датировать по репозиторию нельзя, и это существенно: все замеры 27.07
(`docs/external-facts.md:22-23`) сделаны на `rooms=1`, который работает и сегодня.
Ни один сохранённый замер не содержит `rooms=3`, поэтому «последний прогон с
непустым `result_count`» ничего не говорит о моменте поломки — он просто не
задевал сломанное значение.

Что известно точно: `docs/measurements/step-a-baseline.md` (прогон 2026-07-28) —
первая фиксация `result_count=null` от HTTP 500 в репозитории. Запрос там —
«нужна трёшка…», то есть `rooms=3`. Начало дефекта — не позднее 2026-07-28,
нижняя граница неизвестна.

## Воспроизведение

```bash
curl -sS -o /dev/null -w 'HTTP=%{http_code}\n' 'https://api.pik.ru/v2/filter?rooms=3'   # 500
curl -sS -o /dev/null -w 'HTTP=%{http_code}\n' 'https://api.pik.ru/v2/filter?rooms=2'   # 200
```

Когда pik.ru починит — первая команда начнёт отдавать 200 с count ≈ 1000.
