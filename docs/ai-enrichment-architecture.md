# Архитектурное предложение: Внедрение ИИ и Базы Знаний (Knowledge Base)

## 1. Цели и Концепция
Текущая реализация сервиса `picurl` опирается на детерминированные regex-правила и алгоритмы нечеткого поиска (RapidFuzz) по статичным справочникам. Это работает очень быстро и предсказуемо для типовых запросов. 
Однако, для обработки сложных контекстных и гео-пространственных запросов (например: _"Нужна классная квартира в центре с детским садом неподалёку"_) требуется понимание семантики и доступ к внешней информации.

**Концептуальная идея**:
Внедрить ИИ (Large Language Models, такие как GPT-4/Claude/YandexGPT) для разбора сложных запросов и сопоставления внешних данных (Яндекс Карты / OSM).
Параллельно создать **Базу Знаний (Knowledge Base)** — локальное хранилище накопленного ИИ опыта. По мере работы система будет кешировать сложные логические выводы и гео-привязки, формируя «веса». При повторных или похожих запросах система будет обращаться к локальной Базе Знаний, минуя долгие и дорогие вызовы ИИ, тем самым система будет самосовершенствоваться.

---

## 2. Логическая архитектура

Пайплайн парсинга запроса изменится с прямолинейного на **гибридный**:

1. **Маршрутизатор запросов (Query Router)**:
   - Получает пользовательский текст.
   - Прогоняет через текущий быстрый regex-парсер (`app/parsing/parser.py`).
   - Если парсер вернул большое количество `warnings` (много нераспознанного текста) или найдены маркеры сложного контекста (например: "рядом с", "неподалеку", "школа", "парк", "центр"), запрос перенаправляется на **AI-ветку**. В противном случае отдается текущий быстрый ответ.

2. **Поиск по локальной Базе Знаний (Similarity Matcher)**:
   - Запрос преобразуется в векторное представление (Embeddings).
   - Происходит поиск по Базе Знаний (`app/knowledge_base/`). 
   - Если находится похожий ранее разобранный паттерн с **высоким весом**, применяются сохраненные правила, извлекая `Criteria` напрямую.

3. **AI Агент и Гео-Обогащение (при промахе в Базе Знаний)**:
   - ИИ анализирует намерение: извлекает "центр Москвы", "детский сад".
   - ИИ вызывает внешние инструменты (Tool Calling):
     - API Карт (поиск координат детских садов в центре Москвы).
     - Доступ к `complexes.json` (список ЖК ПИК с их координатами).
   - Скрипт пространственного поиска (Haversine distance) сопоставляет координаты найденных садов и ЖК ПИК, выбирая ЖК с минимальным расстоянием.
   - ИИ формирует итоговый `Criteria` (в котором поле `complexes` заполняется ID найденных подходящих ЖК).

4. **Обновление Базы Знаний и Промоушен (Feedback Loop & Promotion)**:
   - После успешного ответа пользователю, извлеченные факты записываются в БД `ai_structured_facts`.
   - При накоплении достаточной наблюдаемости (`observed_count >= 3`) и высокой уверенности (`confidence >= 0.8`), эти факты могут быть перенесены напрямую в детерминированные JSON-справочники (`app/reference/counties.json`, `districts.json`, `poi_cache.json`) с помощью скрипта промоушена: `python -m app.ai.promotion`.
   - Таким образом, вызовы к ИИ (и даже к локальной БД ИИ) будут сводиться к нулю для устойчивых запросов и фактов, и система будет работать чисто на детерминированных правилах. Отчет по доле вызовов ИИ можно будет собирать из логов.

## 3. Кодовая архитектура

Для сохранения инвариантов проекта (минимальная связность, отсутствие сети в рантайме где это возможно), внедрение ИИ должно происходить модульно.

**Структура папок:**
```text
app/
  knowledge_base/
    README.md
    embeddings.db         # Векторная база для хранения семантических связей (например SQLite + sqlite-vss, Chroma или FAISS)
    weights.json          # Хранение ассоциаций (слово/концепт -> набор параметров/ЖК) и их весов
  parsing/
    ai_parser.py          # Взаимодействие с LLM (LangChain/LangGraph)
    geo_matcher.py        # Утилиты для расчета дистанций (ЖК <-> Внешние объекты)
    router.py             # Точка ветвления: Regex vs AI
```

**Модель данных Базы Знаний (Пример):**
```json
{
  "patterns": [
    {
      "trigger_concept": "детский сад неподалеку",
      "geo_polygon": "center_moscow",
      "resolved_complexes": ["id_1", "id_5"],
      "weight": 0.85,
      "success_count": 12
    }
  ]
}
```

**Эндпоинты API:**
- Текущий `POST /build-url` остается работать как работал (на случай если нужна мгновенная реакция без ИИ).
- Можно добавить флаг `"use_ai": true` в тело `BuildUrlRequest` или создать эндпоинт `POST /build-url-smart`.

## 4. Критика, Идеи и Предложения

### Плюсы (Идеи и Предложения)
1. **Качество выдачи**: Пользователи смогут писать запросы как живому риелтору. "Хочу бегать по утрам в парке" -> ИИ переведет это в поиск ЖК около Мещерского леса или Сокольников.
2. **Накопительный эффект (Moat)**: База Знаний со временем становится уникальным конкурентным преимуществом. Никакая другая система не будет иметь такой же отточенной связи между естественным языком и объектами ПИК.
3. **Экономия бюджета**: Кэширование на основе семантической схожести и весов кардинально снизит расходы на токены API LLM (OpenAI/Anthropic).

### Минусы и Критика
1. **Проблема актуальности (Cache Invalidation)**:
   - Если ПИК строит новый ЖК "в центре рядом с садом", старые закешированные веса в Базе Знаний его не учтут, так как они ссылаются на старый массив `resolved_complexes`.
   - **Решение**: Вместо хардкода ID комплексов в весах, База Знаний должна хранить **"семантические правила"**, например: "детский сад неподалеку" = "geo_query: {type: kindergarten, max_distance: 500m}". А сам поиск пересечений с актуальным `complexes.json` должен происходить на лету при каждом запросе.
2. **Задержка (Latency)**:
   - Если текущий пайплайн отрабатывает за ~10-50 мс, то вызов LLM + API Карт займет от 2 до 5 секунд. Это критично для UX.
   - **Решение**: Асинхронный ответ или WebSocket / SSE (Server-Sent Events) для информирования пользователя о процессе ("Думаю...", "Ищу детские сады...").
3. **Галлюцинации ИИ**:
   - ИИ может "придумать" ЖК ПИК, которого не существует. 
   - **Решение**: Архитектурно запретить ИИ напрямую формировать URL. ИИ должен возвращать JSON со строгим контрактом `Criteria`, который затем валидируется нашим уже существующим валидатором (промпт 08).
4. **Сложность внедрения векторной БД**:
   - Поиск по Базе Знаний потребует эмбеддингов, что означает всё равно один сетевой вызов к легкой модели эмбеддингов, либо использование локальной модели (например, `all-MiniLM-L6-v2`), что утяжелит Docker-образ сервиса.

### Итог по внедрению
Внедрение ИИ необходимо начинать с создания **маршрутизатора (Router)**, который позволит плавно переводить сложные "warning"-запросы на AI-ветку. Базу Знаний стоит реализовывать на основе связки векторных эмбеддингов (для поиска похожих запросов) и графа знаний (для хранения ассоциаций между локациями и ЖК с их весами).

## 5. Детали гео-слоя (Milestone AI-1)

В рамках первого этапа подготовки к внедрению ИИ реализован гео-слой, фиксирующий источники данных для гео-привязок:

1. **Координаты ЖК**:
   - Извлекаются автоматически из ответа backend-API `api.pik.ru/v2/block` (поля `latitude`/`longitude`).
   - Сохраняются в локальный кэш `complexes.json` и доступны в памяти через `app.reference.loader.load_complexes()`.

2. **Источник POI (точек интереса)**:
   - В качестве источника POI (школы, детские сады, парки и др.) используется открытый **Overpass API** (OpenStreetMap).
   - Вызовы к Overpass API осуществляются асинхронно и локализуются в `app/geo/poi.py`.

3. **Эвристика «Центр Москвы»**:
   - Точка отсчёта: Координаты Кремля (`lat=55.7522200, lon=37.6155600`).
   - Радиус: 5000 метров (примерно покрывает ТТК/ЦАО по прямой).
   - Функция: Расчет расстояния по формуле гаверсинуса (Haversine). Это осознанное приближение для быстрого фильтра, в спорных ситуациях финальное слово останется за ИИ или Базой Знаний.

4. **Формат кэша**:
   - Поскольку планируется использование Postgres для Базы Знаний, структурированные факты и результаты поиска POI будут сохраняться в БД в таблицу `ai_structured_facts` (с указанием `source="geo"`), как предусмотрено в архитектуре `memory map` (промпт 17). До внедрения БД используется временное кэширование / прямые запросы при обновлении.

## 6. Карта памяти и хранилище (Milestone AI-2)

Реализовано хранилище для Базы Знаний на базе **PostgreSQL 15+ с расширением pgvector**.

1. **Схема таблиц (миграции лежат в `app/ai/migrations/01_memory_tables.sql`)**:
   - `ai_structured_facts` — хранит извлеченные факты (например, "is_center", "poi_school") для конкретных субъектов. Учитывает уверенность (confidence) и количество подтверждений (observed_count).
   - `ai_semantic_cache` — семантический кэш сложных запросов, использует векторное поле `embedding halfvec(384)` и индекс `HNSW` с `halfvec_cosine_ops` для поиска по косинусному расстоянию.

2. **Эмбеддинги**:
   - Выбрана локальная компактная модель: `all-MiniLM-L6-v2` (библиотека `sentence-transformers`).
   - Размерность векторов: 384 (синхронизировано с размерностью поля `halfvec(384)` в базе).
   - Инференс работает внутри процесса, без сетевых вызовов, что минимизирует задержку и стоимость.

3. **Запуск и настройка для разработки**:
   - Поднять локальную БД (через `docker-compose.yml`): `docker compose up -d postgres`
   - Накатить миграции вручную: `psql "$DATABASE_URL" -f app/ai/migrations/01_memory_tables.sql` (в тестовом окружении накатываются автоматически).

Слой доступа к памяти (`app/ai/memory.py`) использует `asyncpg` для эффективной асинхронной работы с PostgreSQL.

## 7. Клиент Claude и пайплайн обогащения (Milestone AI-3)

Реализовано ядро ИИ-слоя:
1. **Контракт ответа ИИ** (`app/ai/schema.py`):
   `AIEnrichmentAnswer` с:
   - `matched_complex_ids`: список ID подходящих ЖК.
   - `center_district_ids`: список ID округов в центре.
   - `poi_findings`: структура вида `{complex_id: {category: present}}`.
   - `explanation`: объяснение ответа.
   - `confidence`: уверенность ИИ (float).
   Строгая схема гарантирует надежный разбор и валидируется на уровне pydantic.
2. **Anthropic API (Messages)** (`app/ai/client.py`):
   Настроен клиент с вызовом `tool_choice`. Бюджет: 1 базовый вызов на запрос, 1 попытка retry в случае сетевого сбоя или таймаута, жесткий таймаут в 15 секунд.
3. **Оркестрация и Системный промпт** (`app/ai/enrichment.py`, `app/ai/prompts.py`):
   - **Системный промпт**: Сформулирован жестко ограничивающим («Реши, какие из НИХ подходят... Никогда не упоминай ЖК, которых нет в списке»). [app/ai/prompts.py](../app/ai/prompts.py).
   - ИИ вызывается только при наличии `poi_requirements` или `center_requested`.
   - **Политика санитайза**: Ответ ИИ обязательно очищается (sanitize) через шорт-лист кандидатов от гео-слоя. Любые ЖК или факты, выходящие за рамки шорт-листа, отбрасываются как галлюцинации.
   - Успешные результаты кэшируются (семантически) и записываются в базу знаний. Ошибки БД кэша (timeout/conn_error) игнорируются (best-effort).
