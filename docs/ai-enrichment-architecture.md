# Архитектурное предложение: Внедрение ИИ и Базы Знаний (Knowledge Base)

## 1. Цели и Концепция
Текущая реализация сервиса `picurl` опирается на детерминированные regex-правила и алгоритмы нечеткого поиска (RapidFuzz) по статичным справочникам. Это работает очень быстро и предсказуемо для типовых запросов. 
Однако, для обработки сложных контекстных и гео-пространственных запросов (например: _"Нужна классная квартира в центре с детским садом неподалёку"_) требуется понимание семантики и доступ к внешней информации.

**Концептуальная идея**:
Внедрить ИИ (Large Language Models, такие как GPT-4/Claude/YandexGPT) для разбора сложных запросов и сопоставления внешних данных (Яндекс Карты / OSM).
Параллельно создать **Базу Знаний (Knowledge Base)** — локальное хранилище накопленного ИИ опыта. По мере работы система будет кешировать сложные логические выводы и гео-привязки, формируя «веса». При повторных или похожих запросах система будет обращаться к локальной Базе Знаний, минуя долгие и дорогие вызовы ИИ, тем самым система будет самосовершенствоваться.

## 2. Логическая архитектура

Пайплайн парсинга запроса изменится с прямолинейного на **гибридный**:

1. **Маршрутизатор запросов (Query Router)**:
   - Получает пользовательский текст.
   - Прогоняет через текущий быстрый regex-парсер (`app/parsing/parser.py`).
   - Если парсер вернул большое количество `warnings` (много нераспознанного текста) или найдены маркеры сложного контекста (например: "рядом с", "неподалеку", "школа", "парк", "центр"), запрос перенаправляется на **AI-ветку**. В противном случае отдается текущий быстрый ответ.

2. **Поиск по локальной Базе Знаний (Similarity Matcher)**:
   - Запрос преобразуется в векторное представление (Embeddings).
   - Происходит поиск по Базе Знаний (`app/knowledge_base/`). 
   - Если находится похожий ранее разобранный паттерн с **высоким весом**, применяются сохраненные правила, извлекая `Criteria` напрямую.

3. **AI Агент и Гео-Обогащение (при промахе в Базе Знаний)**:
   - ИИ анализирует намерение: извлекает "центр Москвы", "детский сад".
   - ИИ вызывает внешние инструменты (Tool Calling):
     - API Карт (поиск координат детских садов в центре Москвы).
     - Доступ к `complexes.json` (список ЖК ПИК с их координатами).
   - Скрипт пространственного поиска (Haversine distance) сопоставляет координаты найденных садов и ЖК ПИК, выбирая ЖК с минимальным расстоянием.
   - ИИ формирует итоговый `Criteria` (в котором поле `complexes` заполняется ID найденных подходящих ЖК).

4. **Обновление Базы Знаний и Промоушен (Feedback Loop & Promotion)**:
   - После успешного ответа пользователю, извлеченные факты записываются в БД `ai_structured_facts`.
   - При накоплении достаточной наблюдаемости (`observed_count >= 3`) и высокой уверенности (`confidence >= 0.8`), эти факты могут быть перенесены напрямую в детерминированные JSON-справочники (`app/reference/counties.json`, `districts.json`, `poi_cache.json`) с помощью скрипта промоушена: `python -m app.ai.promotion`.
   - Таким образом, вызовы к ИИ (и даже к локальной БД ИИ) будут сводиться к нулю для устойчивых запросов и фактов, и система будет работать чисто на детерминированных правилах. Отчет по доле вызовов ИИ можно будет собирать из логов.

## 3. Кодовая архитектура

Для сохранения инвариантов проекта (минимальная связность, отсутствие сети в рантайме где это возможно), внедрение ИИ должно происходить модульно.

**Структура папок:**
```text
app/
  knowledge_base/
    README.md
    embeddings.db         # Векторная база для хранения семантических связей (например SQLite + sqlite-vss, Chroma или FAISS)
    weights.json          # Хранение ассоциаций (слово/концепт -> набор параметров/ЖК) и их весов
  parsing/
    ai_parser.py          # Взаимодействие с LLM (LangChain/LangGraph)
    geo_matcher.py        # Утилиты для расчета дистанций (ЖК <-> Внешние объекты)
    router.py             # Точка ветвления: Regex vs AI
```

**Модель данных Базы Знаний (Пример):**
```json
{
  "patterns": [
    {
      "trigger_concept": "детский сад неподалеку",
      "geo_polygon": "center_moscow",
      "resolved_complexes": ["id_1", "id_5"],
      "weight": 0.85,
      "success_count": 12
    }
  ]
}
```

**Эндпоинты API:**
- Текущий `POST /build-url` остается работать как работал (на случай если нужна мгновенная реакция без ИИ).
- Можно добавить флаг `"use_ai": true` в тело `BuildUrlRequest` или создать эндпоинт `POST /build-url-smart`.

## 4. Критика, Идеи и Предложения

### Плюсы (Идеи и Предложения)
1. **Качество выдачи**: Пользователи смогут писать запросы как живому риелтору. "Хочу бегать по утрам в парке" -> ИИ переведет это в поиск ЖК около Мещерского леса или Сокольников.
2. **Накопительный эффект (Moat)**: База Знаний со временем становится уникальным конкурентным преимуществом. Никакая другая система не будет иметь такой же отточенной связи между естественным языком и объектами ПИК.
3. **Экономия бюджета**: Кэширование на основе семантической схожести и весов кардинально снизит расходы на токены API LLM (OpenAI/Anthropic).

### Минусы и Критика
1. **Проблема актуальности (Cache Invalidation)**:
   - Если ПИК строит новый ЖК "в центре рядом с садом", старые закешированные веса в Базе Знаний его не учтут, так как они ссылаются на старый массив `resolved_complexes`.
   - **Решение**: Вместо хардкода ID комплексов в весах, База Знаний должна хранить **"семантические правила"**, например: "детский сад неподалеку" = "geo_query: {type: kindergarten, max_distance: 500m}". А сам поиск пересечений с актуальным `complexes.json` должен происходить на лету при каждом запросе.
2. **Задержка (Latency)**:
   - Если текущий пайплайн отрабатывает за ~10-50 мс, то вызов LLM + API Карт займет от 2 до 5 секунд. Это критично для UX.
   - **Решение**: Асинхронный ответ или WebSocket / SSE (Server-Sent Events) для информирования пользователя о процессе ("Думаю...", "Ищу детские сады...").
3. **Галлюцинации ИИ**:
   - ИИ может "придумать" ЖК ПИК, которого не существует. 
   - **Решение**: Архитектурно запретить ИИ напрямую формировать URL. ИИ должен возвращать JSON со строгим контрактом `Criteria`, который затем валидируется нашим уже существующим валидатором (промпт 08).
4. **Сложность внедрения векторной БД**:
   - Поиск по Базе Знаний потребует эмбеддингов, что означает всё равно один сетевой вызов к легкой модели эмбеддингов, либо использование локальной модели (например, `all-MiniLM-L6-v2`), что утяжелит Docker-образ сервиса.

### Итог по внедрению
Внедрение ИИ необходимо начинать с создания **маршрутизатора (Router)**, который позволит плавно переводить сложные "warning"-запросы на AI-ветку. Базу Знаний стоит реализовывать на основе связки векторных эмбеддингов (для поиска похожих запросов) и графа знаний (для хранения ассоциаций между локациями и ЖК с их весами).

## 5. Детали гео-слоя (Milestone AI-1)

В рамках первого этапа подготовки к внедрению ИИ реализован гео-слой, фиксирующий источники данных для гео-привязок:

1. **Координаты ЖК**:
   - Извлекаются автоматически из ответа backend-API `api.pik.ru/v2/block` (поля `latitude`/`longitude`).
   - Сохраняются в локальный кэш `complexes.json` и доступны в памяти через `app.reference.loader.load_complexes()`.

2. **Источник POI (точек интереса)**:
   - В качестве источника POI (школы, детские сады, парки и др.) используется открытый **Overpass API** (OpenStreetMap).
   - Вызовы к Overpass API осуществляются асинхронно и локализуются в `app/geo/poi.py`.

3. **Эвристика «Центр Москвы»**:
   - Точка отсчёта: Координаты Кремля (`lat=55.7522200, lon=37.6155600`).
   - Радиус: 5000 метров (примерно покрывает ТТК/ЦАО по прямой).
   - Функция: Расчет расстояния по формуле гаверсинуса (Haversine). Это осознанное приближение для быстрого фильтра, в спорных ситуациях финальное слово останется за ИИ или Базой Знаний.

4. **Формат кэша**:
   - Поскольку планируется использование Postgres для Базы Знаний, структурированные факты и результаты поиска POI будут сохраняться в БД в таблицу `ai_structured_facts` (с указанием `source="geo"`), как предусмотрено в архитектуре `memory map` (промпт 17). До внедрения БД используется временное кэширование / прямые запросы при обновлении.

## 6. Карта памяти и хранилище (Milestone AI-2)

Реализовано хранилище для Базы Знаний на базе **PostgreSQL 15+ с расширением pgvector**.

1. **Схема таблиц (миграции лежат в `app/ai/migrations/01_memory_tables.sql`)**:
   - `ai_structured_facts` — хранит извлеченные факты (например, "is_center", "poi_school") для конкретных субъектов. Учитывает уверенность (confidence) и количество подтверждений (observed_count).
   - `ai_semantic_cache` — семантический кэш сложных запросов, использует векторное поле `embedding halfvec(384)` и индекс `HNSW` с `halfvec_cosine_ops` для поиска по косинусному расстоянию.

2. **Эмбеддинги**:
   - Выбрана локальная компактная модель: `all-MiniLM-L6-v2` (библиотека `sentence-transformers`).
   - Размерность векторов: 384 (синхронизировано с размерностью поля `halfvec(384)` в базе).
   - Инференс работает внутри процесса, без сетевых вызовов, что минимизирует задержку и стоимость.

3. **Запуск и настройка для разработки**:
   - Поднять локальную БД (через `docker-compose.yml`): `docker compose up -d postgres`
   - Накатить миграции вручную: `psql "$DATABASE_URL" -f app/ai/migrations/01_memory_tables.sql` (в тестовом окружении накатываются автоматически).

Слой доступа к памяти (`app/ai/memory.py`) использует `asyncpg` для эффективной асинхронной работы с PostgreSQL.

## 7. Клиент Claude и пайплайн обогащения (Milestone AI-3)

Реализовано ядро ИИ-слоя:
1. **Контракт ответа ИИ** (`app/ai/schema.py`):
   `AIEnrichmentAnswer` с:
   - `matched_complex_ids`: список ID подходящих ЖК.
   - `center_district_ids`: список ID округов в центре.
   - `poi_findings`: структура вида `{complex_id: {category: present}}`.
   - `explanation`: объяснение ответа.
   - `confidence`: уверенность ИИ (float).
   Строгая схема гарантирует надежный разбор и валидируется на уровне pydantic.
2. **Anthropic API (Messages)** (`app/ai/client.py`):
   Настроен клиент с вызовом `tool_choice`. Бюджет: 1 базовый вызов на запрос, 1 попытка retry в случае сетевого сбоя или таймаута, жесткий таймаут в 15 секунд.
3. **Оркестрация и Системный промпт** (`app/ai/enrichment.py`, `app/ai/prompts.py`):
   - **Системный промпт**: Сформулирован жестко ограничивающим («Реши, какие из НИХ подходят... Никогда не упоминай ЖК, которых нет в списке»). [app/ai/prompts.py](../app/ai/prompts.py).
   - ИИ вызывается только при наличии `poi_requirements` или `center_requested`.
   - **Политика санитайза**: Ответ ИИ обязательно очищается (sanitize) через шорт-лист кандидатов от гео-слоя. Любые ЖК или факты, выходящие за рамки шорт-листа, отбрасываются как галлюцинации.
   - Успешные результаты кэшируются (семантически) и записываются в базу знаний. Ошибки БД кэша (timeout/conn_error) игнорируются (best-effort).

## 8. Наблюдаемость вызовов ИИ и возврат fallback-гейтов (Milestone AI-11)

### 8.1 Текущее состояние гейтов

Два `if`-блока в `app/ai/enrichment.py:enrich()`, которые должны ограничивать
вызов ИИ только реально нужными случаями, **сейчас закомментированы** (гейты
выключены — ИИ вызывается для любого запроса с непустым шорт-листом ЖК):

- **Гейт 1** — «нет `poi_requirements` и нет `center_requested` (и нет
  нераспознанных опционо-подобных фрагментов) → `noop()`». Проверку
  `option_candidates` добавляем при возврате обязательно, иначе резолвинг опций
  (промпт 25 — третий повод звать ИИ, не покрытый исходным гейтом 1) сломается.
- **Гейт 2** — «`fully_resolved(known, criteria, candidates)` → отвечаем
  детерминированно, без ИИ».

Гейты выключены осознанно: до закрытия пробелов промптов 22–25 их
преждевременное включение увело бы сложные запросы в `warnings` вместо
обработки. Возврат гейтов — **последний шаг серии 22–26**, выполняется только
когда численный критерий ниже подтверждён на реальных/тестовых данных.

### 8.2 Что измеряем — таблица `ai_call_log`

`app/ai/migrations/02_ai_call_log.sql` (+ `03_ai_call_failed.sql`). При **каждом**
вызове `enrich()` (не только при успехе) пишется строка (best-effort, `pool=None` —
пропуск):

| поле | смысл |
|---|---|
| `occurred_at` | момент вызова |
| `had_poi_or_center` | сработал бы старый гейт 1 |
| `fully_resolved_deterministically` | результат `fully_resolved()` — **вычисляется и логируется всегда**, даже пока гейт 2 выключен (это и есть измерение «что было бы, если включить гейт 2») |
| `cache_hit` | ответ взят из семантического кэша |
| `ai_called` | реально дёрнули LLM/`agy` |
| `criteria_changed_by_ai` | итоговый `criteria` после ИИ отличался от детерминированного слоя (реальная польза вызова, а не факт вызова) |
| `ai_failed` | попытка была и не удалась (колонка добавлена миграцией `03_ai_call_failed.sql`; строки, записанные до неё, читаются как `false` — тогда провал в лог не попадал вовсе) |

`ai_called` и `ai_failed` **независимы**: отказ по предохранителю (`CircuitOpenError`,
cooldown) пишется как `ai_called=false, ai_failed=true` — до провайдера не дошли, но
это отказ ИИ-слоя, а не гейт. Раньше такая строка была неотличима от «не звали».

### 8.3 Отчёт

```bash
python -m app.ai.usage_report            # за всё время
python -m app.ai.usage_report --days 30  # за период
```

Показывает: всего запросов → % `had_poi_or_center` → из них %
`fully_resolved_deterministically` (кандидаты на «гейт 2 спас бы вызов ИИ») → %
`cache_hit` → % `criteria_changed_by_ai` среди вызовов ИИ (реальная польза) → из
изменений — доля без POI/центра (метрика гейта 1). Аггрегация вынесена в чистую
`aggregate()` и покрыта тестами (`tests/ai/test_usage_report.py`).

Отдельная строка отчёта — «попытка провалилась (`ai_failed`)». Её знаменатель —
**попытки** (`ai_attempts` = `ai_called or ai_failed`), а не `ai_called`: у
breaker-отказа `ai_called=false`, и деление на `ai_called` занизило бы долю провалов
ровно на тех строках, ради которых показатель и заводился. `pct_ai_failed` считается
от `ai_attempts`; на данных до миграции 03 показатель тождественно нулевой — это
«не измеряли», а не «провалов не было».

### 8.4 Численный критерий возврата гейтов (зафиксирован)

Числа обсуждаемы, но это **числа, а не «когда почувствуем»**. Окно — не менее
`N = 500` вызовов `enrich()`, накопленных **после** закрытия промптов 22–25.

- **Гейт 2 включаем**, когда `fully_resolved_deterministically` держится
  **≥ 90%** среди запросов с `had_poi_or_center` над окном `N ≥ 500`. Смысл:
  детерминированный слой (после промптов 22–25) почти всегда закрывает запрос —
  значит гейт 2 отсекает вызов ИИ без потери качества.
- **Гейт 1 включаем** (с расширением проверкой `option_candidates`), когда доля
  `had_poi_or_center = false` среди строк с `criteria_changed_by_ai = true`
  **≤ 5%** над тем же окном. Смысл: ИИ почти никогда не меняет `criteria` для
  запросов без POI/центра — значит общий резолвинг опций (промпт 25) уже
  покрывает их, и гейт 1 (плюс ветка `option_candidates`) их не сломает. Если
  доля выше порога — сперва разобраться, какой класс запросов ИИ реально
  дорешивает, и покрыть его детерминированно, и лишь потом включать гейт 1.

**Статус на момент этого шага (Milestone AI-11): оба гейта ВЫКЛЮЧЕНЫ** —
ряд данных `ai_call_log` только начинает копиться, промпты 22–25 в процессе,
критерий не подтверждён. Таблица и отчёт подняты заранее, чтобы к моменту
решения были цифры.

### 8.5 Безопасность вызова `agy`

`agy` — агентный CLI, а в промпт попадает полный текст пользователя
(`user_query`) без санитизации — это поверхность prompt injection. Поэтому
`app/ai/client.py:call_antigravity` запускает CLI строго в неинтерактивном
режиме `--print` и **никогда** не передаёт `--dangerously-skip-permissions`
(или иные флаги, снимающие ограничения на действия агента).

### 8.6 Различитель состояний: не звали / выключен / без пользы / провал

Экстрактор свободного текста (`resolve_free_text_criteria`, ведро C) работает **до
гейта 1** и раньше глушил оба своих пути отказа: исключение вызова уходило в
`logger.error`, `CircuitOpenError` — в `logger.warning`, а у `FreeTextOutcome` не
было поля провала вовсе, поэтому отказ физически не мог доехать до
`EnrichmentResult.ai_failed`. Ответ API `ai_used=false, ai_failed=false` означал
одновременно «не звали», «позвали без пользы» и «позвали и упало» — нарушение
инварианта 1 на уровне телеметрии. `FreeTextOutcome` получил `failed` и
`failure_reason` (`"exception"` — вызов упал, `called=True`; `"breaker"` —
предохранитель в cooldown, `called=False`), и состояния разошлись:

| состояние | `ai_used` | `ai_failed` | `ai_called` | `criteria_changed_by_ai` |
|---|---|---|---|---|
| ИИ не звали (гейт сработал, нечего обогащать) | false | false | false | false |
| ИИ выключен (нет кредов / `AI_ENRICHMENT_ENABLED=false`) | false | false | false | false |
| позвали, вызов удался, пользы нет | false | false | true | false |
| вызов упал (`exception`) | false | true | true | false |
| предохранитель в cooldown (`breaker`) | false | true | false | false |

«Выключен» намеренно совпадает по флагам с «не звали»: отсутствие учётных данных и
снятый `AI_ENRICHMENT_ENABLED` — не ошибка (инвариант 9), провалом их считать нельзя.

**Границы провала узкие — «модель НЕ ответила».** «Ответила и ничего не заполнила» и
«значения отбиты `validate_assignment`/санитайзером» — это успешный вызов без пользы
(`failed=False`); иначе `ai_failed` начал бы срабатывать на исправном ИИ, ошибшемся
форматом, и флаг перестал бы означать отказ. Различает эти два случая лог, а не флаг:
после успешного вызова пишется `logger.info` с `changed`, числом фрагментов и
`answer.model_dump(exclude_defaults=True)` — без него «модель ничего не вернула» и
«вернула, но всё отбито валидацией» неразличимы (обе дают `changed=False,
failed=False`). Успешная ветка не логировала ничего вовсе, из-за чего диагностика
самого дефекта строилась на выводах **по отсутствию строк лога**.

**Слияние — в замыкании `_log()` внутри `enrich()`** (`if free_text.failed:
result.ai_failed = True`), и это единственная корректная точка: через `_log()`
проходят все return-пути `enrich()`, а `noop()`/`from_deterministic()` строятся с
`ai_failed=False`, то есть факт провала терялся бы ровно на гейте 1 — самом частом
пути free-text-запроса. Новых полей в `BuildUrlResponse` нет: провал доезжает до
ответа через существующее `ai_failed`, контракт API не менялся. В `ai_call_log`
значение колонки `ai_failed` берётся оттуда же (`log_ai_call(..., ai_failed=...)`).

Человеческая половина инварианта 1 — строка в `warnings`: «не удалось дообработать
оставшийся текст через ИИ — перечисленные выше фрагменты не учтены в ссылке». Сами
фрагменты и так оставались в `warnings`; новая строка объясняет, **почему** они там.
`ai_failed` читает машина, `warnings` — человек.

**Таблица выше описывала не все ветки ИИ, и это выяснилось позже** — см. §11:
`resolve_options` в разборе состояний отсутствовал вовсе, поэтому его вызовы не
попадали ни в одну строку таблицы.

### 8.7 Снятие warning'а — по факту применения, а не по заявке модели

`consumed_fragments` — это **заявка** модели о том, какие фрагменты она разобрала, а не
доказательство того, что значение доехало до `Criteria`. `_apply_free_text_answer`
снимал warning'и всех заявленных фрагментов под общим условием `if changed:`, где
`changed` означает «хоть одно поле применилось». Частичный ответ — два значения приняты,
третье отбито `validate_assignment` — уносил warning и по отбитому: значения нет,
предупреждения нет, фильтр исчезал бесследно. Нарушены сразу два инварианта: 3
(«выдуманное отбрасывается, фраза остаётся в `warnings`») и 1 («отбрасывается значение,
а не текст» — здесь отброшены оба).

**Точечно, по образцу `rejected_landmark_phrases`, починить нельзя.** У ориентиров связь
есть: `LandmarkMatch` несёт `phrase`, поэтому фразы отклонённых санитайзером ориентиров
исключаются из снятия поимённо. У скаляров и булевых такой связи в данных **нет вовсе** —
`FreeTextCriteriaAnswer` отдаёт голые значения (`floor_min: int | None`) и отдельный
плоский `consumed_fragments: list[str]`. Какой фрагмент породил отбитое поле, из ответа
невосстановимо.

**Решение — снимаем все или ничего:** любая отбивка валидацией отменяет снятие целиком
(`if changed and not rejected`). Цена известна и принята: в этом редком случае фрагмент,
чьё значение как раз доехало, сохранит warning «не удалось распознать». Лишний warning —
шум, снятый warning при непринятом значении — молчаливая потеря, и проект последовательно
выбирает первое. Валидные значения продолжают применяться: отменяется снятие warning'ов,
а не запись в `Criteria`.

Полное решение — провенанс на уровне поля (модель возвращает, из какого фрагмента взято
каждое значение) — меняет схему ответа и промпт, поэтому вынесено за границы правки.

Человеческая половина, как и в §8.6, — строка в `warnings`: «ИИ предложил значение, но
оно не прошло валидацию — перечисленные выше фрагменты оставлены как нераспознанные».
Без неё фрагмент говорит только «не удалось распознать», что здесь неправда: распознано
как раз было, отброшено значение. Строка добавляется при любой отбивке, в том числе
когда не применилось ничего. Категорию (`degraded` по
`docs/warnings-severity-proposal.md`) она получит вместе с Г6 — параллельный механизм
здесь не заводится, это обычная строка в `warnings`. На `ai_failed` правка не влияет:
отбивка валидацией остаётся успешным вызовом без пользы, граница §8.6 не сдвинута.

### 8.8 Два независимых способа не дозвониться до модели — и debug-флаги для каждого

При отладке правок промпта/кода легко перепутать причину, по которой конкретный запрос
не позвал ИИ. Их две, они не пересекаются и требуют разных обходов:

1. **Гейт 2** (`fully_resolved_deterministically`, §8.1/8.4) — все POI/центр-факты уже
   известны из детерминированного слоя, `enrich()` возвращает
   `EnrichmentResult.from_deterministic(known)` **до** вычисления сигнатуры и до
   обращения к кэшу вовсе. `AI_ENRICHMENT_FORCE=true` (`app/config.py`) пропускает
   именно эту проверку — запрос всё равно уходит в модель.
2. **Семантический кэш** (`ai_semantic_cache`, §6) — `lookup_semantic()` находит
   близкий по `embedding` прошлый ответ (порог `0.2`, cosine distance) и отдаёт его как
   есть: **без TTL и без версии по промпту/коду**. Правка `SYSTEM_PROMPT` не
   инвалидирует старые записи — тот же (или семантически близкий) текст запроса вернёт
   старый ответ, даже если промпт с тех пор изменился. `AI_ENRICHMENT_BYPASS_CACHE=true`
   пропускает только чтение (`lookup_semantic`); запись (`persist()` → `store_semantic`)
   продолжает идти как обычно — прод-кэш не теряется, флаг влияет лишь на текущий вызов.

Оба флага читаются из `get_settings()` внутри `enrich()`, дефолт `false` у обоих —
поведение прод-трафика не меняется. Если запрос гарантированно решается
детерминированно (гейт 2), одного `AI_ENRICHMENT_BYPASS_CACHE` для проверки живого
вызова недостаточно — нужен ещё `AI_ENRICHMENT_FORCE`, иначе до кэша дело не доходит
вообще.

## 9. Ведро C: отделка и POI в экстракторе свободного текста (2026-08-04)

### 9.1 Что было закрыто

Экстрактор свободного текста (`resolve_free_text_criteria`, ведро C; см. §8.6 про его
место до гейта 1) умел скаляры, булевы, `rooms` и ориентиры. Отделка и POI жили
**только** на детерминированных путях — regex-правила `rules/finish.py` и
`rules/poi.py`. Незнакомая формулировка регексом не бралась, дальше попадала в
`option_candidates` и уходила в `resolve_options()`, а тот сверяет ответ модели со
справочником **опций**, где отделки нет физически: она отдельный сегмент пути
`/finish` (`docs/pik-url-schema.md`). То есть модель фразу видела, но по построению не
могла ничего с ней сделать — резолвер бы отбросил любой её ответ как галлюцинацию.
Такой отказ не провал (§8.6: успешный вызов без пользы) и не молчаливая потеря (фраза
оставалась в `warnings`), но это оплаченный вызов ИИ с гарантированно нулевым
результатом.

Добавлено: `FinishMatch` (`phrase` + `finish: Finish | None`) и `POIMatch` (`phrase` +
`category: POICategory | None` + `max_distance_m` + `only_new`) в `app/ai/schema.py`,
поля `finish: list[FinishMatch]` и `poi: list[POIMatch]` в `FreeTextCriteriaAnswer`.
В `FREE_TEXT_SYSTEM_PROMPT` описаны новые поля (отделка — числа `0/1/2/3`, POI —
категории `school|kindergarten|shop|parking|park_forest|medical`), а строгое правило 1
переформулировано: «отделка» убрана из списка запрещённого, потому что теперь
разбирается здесь; «вид из окна» осталась запрещённой — это опция, её место в ведре
опций.

### 9.2 Третий рубеж: значение — из энума, фраза — из текста

Санитайзеры `sanitize_finish_resolution` и `sanitize_poi_resolution` построены по
образцу `sanitize_landmark_resolution` и держат **два** условия одновременно:

1. Принимается значение **энума** (`Finish`, `POICategory`), а не строка модели —
   инвариант 3 в его обычной форме: выдуманного фильтра не существует, потому что
   пространство значений закрыто.
2. Принимается, только если `phrase` **дословно** входит в переданные модели
   `fragments`.

Второе условие важнее, чем кажется, и без него схема была бы опасной именно потому,
что первое выполняется само собой. Значение энума всегда «валидно»: модель может
приписать `Finish.READY` произвольному шуму — приветствию, обрывку названия ЖК, —
и такой ответ прошёл бы любую проверку контракта. Результат — **лишний фильтр**, а не
потерянный, то есть ровно тот класс дефекта, который оба QA-корпуса не арбитрируют:
сводные метрики («фильтров на запрос», покрытие текста) от него только улучшаются.
Требование дословного вхождения фразы привязывает значение к куску пользовательского
текста и делает выдумку проверяемой.

### 9.3 Потолок дистанции `_AI_POI_MAX_DISTANCE_M`

Порог `max_distance_m` от модели вне диапазона `(0, 10_000]` гасится в `None`, **само
требование при этом сохраняется**.

Обоснование — в природе POI-требования: оно про пешую доступность. Дистанция в 300 км
— это не отсечка, а её отсутствие; записанная в фильтр, она даёт условие, которое
ничего не сужает, но в `criteria` и в объяснении выглядит применённым. Это тихая ложь
о том, что учтено, — та же болезнь, что у сфабрикованного фильтра, только с обратным
знаком.

Выбросить требование целиком тоже нельзя: сам факт «нужен детский сад рядом» из текста
никуда не делся, а его удаление было бы молчаливой потерей (инвариант 1). Поэтому
гасится **только число**: категория остаётся, дистанция уходит в дефолтный радиус
гео-слоя, который откалиброван и задокументирован (`docs/thresholds-rationale.md`).
Промпт с этой же стороны закрыт явным запретом вычислять: модель не пересчитывает
минуты ходьбы в метры и вообще ничего не считает — `max_distance_m` заполняется, только
если расстояние названо в тексте (инвариант 3: LLM не считает дистанции).

### 9.4 `rejected_landmark_phrases` → `rejected_phrases`

Механизм из §8.7 обобщён. Раньше поимённое исключение из снятия warning'ов было
привилегией ориентиров — единственного поля с провенансом (`LandmarkMatch.phrase`).
Теперь провенанс есть и у отделки, и у POI, поэтому все три складываются в общий
`rejected_phrases`: фраза, отбитая санитайзером, не исчезает молча даже тогда, когда
модель заодно угадала другое поле и общее `changed` истинно.

У скаляров провенанса по-прежнему нет, и там сохраняется прежнее all-or-nothing
(«снимаем все или ничего», §8.7). Обобщение — шаг к полному решению из §8.7, а не оно
само: провенанс появился у трёх полей из-за того, что их значения приходят
структурами, а не голыми скалярами.

Вливание в `Criteria` — только в **пустое** поле: детерминированный слой выигрывает у
модели всегда. Regex, взявший «черновая отделка», не переписывается ответом ИИ, даже
если тот уверен.

### 9.5 Следствие: POI от модели открывает гейт 1

Условие гейта 1 читает `criteria.poi_requirements` **после** вызова экстрактора
свободного текста (§8.6: ведро C работает до гейта). Значит POI, добавленный моделью,
гейт **открывает** и включает гео-сужение — построение шорт-листа плюс haversine по
координатам ЖК.

Это и есть смысл ветки: до правки такой запрос заканчивался ничем, теперь он доходит
до гео-слоя. Но цена запроса от этого растёт — один добавленный POI превращает дешёвый
путь в полный. Отсюда прямая связь с §9.2: рубеж проверки фразы стоит не только между
пользователем и лишним фильтром, но и между галлюцинацией модели и оплаченным
гео-проходом. Факт зафиксирован тестом `test_ai_added_poi_opens_gate_one`
(`build_candidate_shortlist` замокан, проверяется сам факт вызова) — чтобы будущая
перестановка гейтов и экстрактора не изменила эту зависимость незамеченной.

## 10. Что модель видит и что от неё принимается (2026-08-04)

Разбор дефекта «пустой `blocks=` у запроса про ВДНХ» целиком — в
`docs/geo-narrowing.md`; здесь только та его часть, которая про ИИ-слой, плюс два
уточнения санитайзеров POI.

### 10.1 Кандидаты без дистанции: вопрос, на который нельзя было ответить

`build_candidate_shortlist` при локации, не найденной по тегу, молча откатывался на
первые 50 ЖК из `complexes.json` в порядке файла. У `ComplexCandidate` при этом не было
**ни одного** поля с расстоянием, и причина отбора в контекст не передавалась. Модель
получала произвольный список без единого признака связи с названной станцией и отвечала
«подходящих нет» — корректно для такого входа.

Отсюда правило, которого раньше не было сформулировано: **инвариант 3 двусторонний.**
Раз дистанции считает не модель, значит посчитанное обязан приносить ей код. Добавлено
поле `ComplexCandidate.distance_to_location_m` (haversine, считается кодом; обратно от
модели не принимается — как и координаты, это факт «на просмотр»), а шорт-лист
ранжируется по нему.

В `SYSTEM_PROMPT` добавлен явный блок: отсутствие названия станции в поле `metro`
кандидата **не** основание его отклонять, и ответ «ни один не подходит» в такой ситуации
почти всегда неверен. Плюс второй пример (ВДНХ) — прежний единственный пример не
показывал случая, где отбор сделан кодом, а не совпадением строк.

Изменение промпта здесь — **вторично**. Первично то, что в контексте появились данные;
без них никакая формулировка не помогла бы.

### 10.2 `from_ai_unmatched`: «модель не подтвердила» ≠ «требование дало ноль»

`EnrichmentResult.from_ai` ставил `complexes_matched=True` безусловно. При пустом
`matched_complex_ids` это уводило `merge_enrichment` в `criteria.complexes=[]` +
`complexes_matched_empty=True`, а `combine_with_fallback` читал флаг как полноценное
требование с нулевым результатом и стирал посчитанные детерминированным слоем ЖК.

Новая фабрика `EnrichmentResult.from_ai_unmatched` отличается от `from_ai` ровно одним
полем — `complexes_matched=False`. Плюс `AI_NO_MATCH_WARNING`: «ИИ не подтвердил ни
одного ЖК из предложенных — гео-сужение оставлено детерминированному слою (ближайшие по
расстоянию)». Откат объявляется вслух — иначе пользователь не отличит его от «так и
посчитали».

**`ai_used` остаётся `True`, и это осознанно.** Первая версия правки выводила флаг из
фактического влияния на `criteria` — и сломала `test_ai_learning_loop` (сценарий 5:
галлюцинация, вычищенная `sanitize_against_shortlist`, даёт такой же пустой список,
но это другое состояние). Граница §8.6 не сдвигается попутно: различие «позвали без
пользы» / «реально повлиял» на уровне API не выражено вовсе, его различает лог. Менять
наблюдаемость заодно с гео-семантикой — подмена предмета правки, и цена такой подмены
измерена: падение теста, который проверяет совсем другой сценарий.

### 10.3 Потолок дистанции POI приравнен к радиусу кэша

§9.3 фиксировала `_AI_POI_MAX_DISTANCE_M = 10_000` как защиту от «300 км — это не
отсечка». Число было выбрано как разумный предел пешей доступности, но не сверено с тем,
что вообще лежит в кэше: POI собираются в радиусе **2000 м**. Диапазон 2–10 км —
зона-призрак: требование принимается, выглядит применённым, а подтвердиться физически не
может, потому что за радиусом сбора объектов в кэше нет ни одного.

Теперь `_AI_POI_MAX_DISTANCE_M = POI_CACHE_RADIUS_M`, а сама константа переехала в
`app/geo/poi.py` — единый источник правды для сборщика кэша и рантайма (подробнее —
`docs/poi-cache.md`). Механика §9.3 не изменилась: гасится **только число**, категория
и само требование остаются.

### 10.4 `POICategory.OTHER` и непроверяемая категория

Две дыры в санитайзере и в фильтрации, обе про одно: «валидный энум» ≠ «проверяемое
требование».

- `sanitize_poi_resolution` проверял только `category is not None`, а `OTHER` —
  полноценный член энума. Кэш под `OTHER` не собирается вовсе (`fetch_poi` возвращает
  пустой результат), поэтому требование не удовлетворил бы **ни один** ЖК. Это
  §9.2 в чистом виде: значение из энума проходит проверку контракта само собой, и
  ровно поэтому одного контракта мало. `OTHER` теперь отбрасывается.
- `resolve_known_facts` при непокрытой категории молча отсеивал всех кандидатов —
  снаружи это неотличимо от честного «подходящих ЖК нет». Прямая дыра в инварианте 1:
  причина исчезновения выдачи не называлась.

Починка: заведена `POI_CATEGORY_NOT_CACHED_WARNING`, `build_candidate_shortlist`
предупреждает по каждой запрошенной категории, которой нет в `known_poi` ни у одного
кандидата; `resolve_known_facts` перестал фильтровать по **непроверяемым** категориям.

**Источник правды о «собранных категориях» — файл кэша, а не текущие кандидаты.**
Первая версия считала их по `known_poi` шорт-листа и сломала
`tests/ai/test_enrichment.py::test_enrich_logs_ai_call_row`: такой критерий не различает
«категорию не собирали вовсе» и «у этих конкретных ЖК данных нет» — шорт-лист может
целиком состоять из ЖК без координат. Поэтому `_collected_poi_categories()` читает
`poi_cache.json`. Пробел у **отдельного** кандидата трактуется по-прежнему: близость
недоказуема → требование не пройдено.

Практический смысл механизма шире одного дефекта: восемь категорий POI, добавленных той
же правкой (`docs/poi-cache.md`), пока не имеют собранного кэша. Именно этот warning
делает их состояние «распознано, но выдачу не сужает» видимым, вместо того чтобы
показывать пустую выдачу без объяснения.

## 11. Третья ветка ИИ: `OptionsOutcome` и слепое пятно §8.6 (2026-08-04)

### 11.1 Почему дефект не был замечен раньше

§8.6 вводилась как «различитель состояний вызова ИИ» и выглядела исчерпывающей, но
разбирала **две ветки из трёх**: экстрактор свободного текста (ведро C) и основную
ветку обогащения. Резолвинг опций (`resolve_options`) в ней не упомянут ни разу — не
потому, что для него принято другое решение, а потому, что его при разборе не
рассмотрели. Пропуск был не в реализации, а в **инвентаре веток**, и заметить его по
самому тексту §8.6 было нечем: таблица состояний внутренне непротиворечива, если не
знать, что существует третий вызывающий.

Отсюда практическое правило: полнота такого различителя проверяется не чтением его
описания, а перечислением **всех** мест, откуда уходит вызов модели. Веток три, и
любая новая обязана появиться в §8.6 вместе с собой, а не «когда дойдут руки».

### 11.2 Что именно врало

`resolve_options` была объявлена `-> None`: она мутировала `criteria` и `warnings` по
ссылке и не сообщала вызывающему **ничего** — ни что модель звали, ни что её ответ был
применён. `enrich()` собирал флаги только из `FreeTextOutcome` и из основной ветки,
поэтому вызов, реально повлиявший на `Criteria`, для наблюдаемости не существовал: в
ответе API стоял `ai_used=false`, а в `ai_call_log` строки о вызове не было вовсе.

Дефект найден не тестом, а вопросом пользователя «почему не вызывался ИИ» на живом
прогоне, и ответ оказался обратным ожиданию: ИИ звался и повлиял, врал флаг.
Доказательство строилось **сравнением двух слоёв на одном тексте**: чистый `parse()`
давал `options=['vidNaPark']` и warning «город»: не удалось распознать, а ответ API —
`options=['vidNaPark','vidNaGorod']` и без этого warning'а. Детерминированный слой
`vidNaGorod` найти не мог по построению: во фразе «с видом на парк, город»
перечисление разрывает конструкцию, «парк» матчится, «город» остаётся огрызком. Второй
slug мог прийти только из `resolve_options`.

Приём общий и стоит запоминания: **дельта между `parse()` и ответом API — это ровно
вклад ИИ**, и она проверяема без единой строки телеметрии. Именно поэтому расхождение
с флагом доказуемо, а не предположительно.

### 11.3 `OptionsOutcome` — полный аналог `FreeTextOutcome`

Заведён класс `OptionsOutcome` (`called` / `changed` / `failed` / `failure_reason`) с
**теми же** узкими границами провала, что описаны в §8.6: `failed=True` только когда
модель не ответила — исключение вызова (`failure_reason="exception"`, `called=True`)
или cooldown предохранителя (`"breaker"`, `called=False`). «Ответила и ничего не
подобрала» и «slug отбит `sanitize_option_resolution`» — успешный вызов без пользы,
`failed=False`. Выключенный ИИ и отсутствие кредов дают пустой `OptionsOutcome` и
провалом не считаются (инвариант 9).

Одинаковость здесь важнее краткости: два разных определения провала в одном ответе API
означали бы, что `ai_failed` не имеет единого смысла и не читается машиной без знания,
какая ветка сработала.

**Мутация по ссылке сохранена.** `resolve_options` по-прежнему правит `criteria` и
`warnings` на месте, а `OptionsOutcome` возвращается **дополнительно** — на мутацию
опираются `build_url` и существующие тесты, и подмена её на возврат значения была бы
второй правкой, спрятанной внутри первой. Правка добавляет канал наблюдаемости, не
трогая канал данных.

### 11.4 Слияние — в `_log()`, и почему иначе нельзя

В `enrich()` результат кладётся в переменную `options`, поля лога собираются
объединением веток (`free_text.called or options.called`, и так же для `failed` и
`changed`), а в замыкании `_log()` добавлена ветка: `options.failed` выставляет
`result.ai_failed`, `options.changed` — `result.ai_used=True` и
`criteria_changed_by_ai=True`.

Точка слияния та же, что у ведра C в §8.6, и по той же причине: ниже по коду `enrich()`
может вернуть `noop()` или `from_deterministic()`, у которых `ai_used=False` **по
конструкции**. Ровно это и произошло в живом прогоне — после резолвинга опций сработал
гейт 2, вернулся путь без ИИ, и уже применённое влияние модели было затёрто флагами
конструктора. Через `_log()` проходят все return-пути, поэтому только там факт вызова
переживает выбор ветки.

Контракт API не менялся: и `ai_used`, и `ai_failed` уже существовали, у них лишь
появился третий источник. Строка в `ai_call_log` теперь пишется и для чисто
опционных вызовов — до правки такой вызов не оставлял следа ни в одном контуре
наблюдаемости, то есть не попадал и в статистику §8.4, на которой считается критерий
возврата гейтов.

Тесты — `tests/ai/test_option_resolution_observability.py` (6), включая
`test_enrich_reports_ai_used_when_only_options_branch_worked`: воспроизводит живой
случай — единственная сработавшая ветка опций плюс возврат через гейт 2.
