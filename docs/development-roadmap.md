# Пути развития picurl

Рабочий план на основе состояния репозитория и замеров, зафиксированных в июле–августе
2026 года. Цель — повысить достоверность ссылки и объяснений к ней, затем расширять
возможности поиска. Перед реализацией сетевых изменений замеры нужно повторить: данные
ПИК и поведение его эндпоинтов меняются.

## 1. Восстановить качество справочников локаций — первый приоритет

**Проблема.** Аудит нашёл 158 живых ID из 176 проверенных; все 10 ID округов в
`counties.json` не дали предложений на фактическом эндпоинте выдачи. При этом
нулевая выдача не доказывает невалидность ID: объект мог быть распродан. Для части
округов соответствие новому ID ещё требует ручной проверки.

**Что сделать.** Повторить `scripts/reference_audit.py`, затем сверить пары
«округ → ID» по названиям, географии ЖК и сужению реальной выдачи. Исправлять
только подтверждённые записи; спорные оставить с явным предупреждением. При
обновлении JSON сохранить кураторские алиасы и запрет слияния записей с
собственным `id` или `slug`. Добавить проверку регрессии на подтверждённые
округа и периодический отчёт об изменениях справочников.

**За счёт чего станет лучше.** Пользователь реже получит ссылку с пустой или
неверной выборкой по округу. Результат проверять на заранее записанных запросах:
доля подтверждённых ID, число неожиданных нулевых выдач и соответствие ЖК
запрошенному округу. Не подменять эти показатели простым наличием ID в фасете.

Источники: [аудит ID](measurements/2026-07-28-reference-audit.md),
[правила справочников](../CLAUDE.md).

## 2. Сделать проверку выдачи ближе к фактической ссылке

**Проблема.** Текущий валидатор обращается к `api.pik.ru/v2/filter`. Этот
эндпоинт не учитывает часть локационных фильтров, некоторые варианты отделки и
возвращает HTTP 500 для `rooms=3`. Поэтому `result_count` может вводить в
заблуждение, хотя сама ссылка построена верно. Эндпоинт, используемый сайтом,
применяет больше фильтров, но прежние замеры выявили ответы-заглушки с HTTP 200
и неверным счётчиком.

**Что сделать.** Сначала повторить сравнительный замер на наборе ссылок с
комнатностью, метро, округами и отделкой. Отдельно проверять маркер полноценного
ответа и контрольный запрос, который обязан сузить выдачу. Только после
стабильного результата рассматривать замену источника `result_count` или
проверку через карточки. При сомнительном ответе отдавать `result_count=None`
с диагностикой, а не точное на вид неверное число. Сохранить единый путь
гео-сужения для генератора URL и валидатора.

**За счёт чего станет лучше.** Число результатов будет соответствовать большему
числу фильтров ссылки, а сбой внешнего API станет видимым. Критерий готовности:
на контрольном наборе счётчик согласуется с карточками и ни одна намеренная
заглушка не принимается за достоверную выдачу.

Источники: [сравнение эндпоинтов](measurements/2026-07-28-five-params-real-endpoint.md),
[риск заглушки](measurements/2026-07-28-reference-audit.md),
[аудит карточек](outcome-audit.md).

## 3. Довести POI-поиск до обещанного покрытия

**Проблема.** Восемь новых категорий POI распознаются, но кэш под них на момент
документированного изменения не был собран. Такой запрос сохраняет критерий и
предупреждение, однако не сужает список ЖК. Кроме того, расстояние вычисляется
по прямой; перевод «минут пешком» в метры не равен времени маршрута.

**Что сделать.** Проверить доступность источников OSM и запустить
`uv run python -m app.geo.refresh_poi`; затем сверить покрытие каждой категории
по всем ЖК и дату обновления кэша. Ввести отчёт о пропусках и сроке давности
данных при обновлении, не превращая пустой кэш в «рядом ничего нет». Если
потребуется точное условие «пешком за N минут», оценить маршрутизацию отдельно
от текущего haversine: сравнить время, квоты, стоимость и полноту покрытия.

**За счёт чего станет лучше.** Уже распознанные запросы к стоматологии, спорту,
ТЦ и другим категориям начнут реально отбирать ЖК. Проверять долю ЖК с данными
по категории и соответствие нескольких вручную проверенных POI; для маршрутов —
ошибку оценки времени на контрольных парах точек.

Источник: [состояние POI-кэша](poi-cache.md).

## 4. Сделать потери и ограничения понятными пользователю

**Проблема.** `warnings_detailed` уже существует, но разметка категорий
выполнена лишь частично. Неразмеченные сообщения попадают в `unknown`: клиент
не всегда отличит неподдерживаемый фильтр от временной ошибки и справки.

**Что сделать.** Завершить оставшиеся шаги существующего плана: `capped`,
`degraded`, затем `info`. Проверить на запросах с неподдерживаемым условием,
недоступным ИИ и реальной потерей фильтра, что категории ведут к разным
действиям пользователя. Сохранить прежний `warnings: list[str]` и строковую
совместимость внутреннего канала; подробные предупреждения формировать до
создания Pydantic-ответа.

**За счёт чего станет лучше.** Можно явно показать, когда повторить запрос,
когда исправить формулировку и когда ссылка работает, но число результатов
неполно. Проверять точность разметки по размеченным примерам и отсутствие
изменений текста предупреждений на существующих корпусах.

Источник: [план категорий warnings](warnings-severity-proposal.md).

## 5. Проверять смысл результата, а не только количество фильтров

**Проблема.** Корпусные метрики ловят потерю фильтров, но могут улучшиться от
лишнего, выдуманного фильтра. Аудит карточек уже обнаруживал расхождения между
обещанием ссылки и фактической выдачей. Сетевой аудит по устройству не входит
в обычный `pytest`.

**Что сделать.** Пополнять корпус примерами с ожидаемыми критериями, URL,
предупреждениями и недопустимыми лишними фильтрами. Для небольшого набора
типовых запросов периодически выполнять `scripts/outcome_audit.py` и разбирать
значения из карточек вручную там, где автоматическая проверка односторонняя.
Сохранять результаты с датой и отделять изменения нашего кода от изменений
выдачи ПИК. Улучшать сами правила и данные; не ослаблять пороги QA ради роста
метрики.

**За счёт чего станет лучше.** Регрессии вроде ошибочного `timeOnFoot` будут
видны даже при формально «богатой» ссылке. Измерять отдельно долю верных
критериев, долю лишних фильтров и число расхождений с карточками.

Источник: [границы аудита выдачи](outcome-audit.md).

## 6. Улучшить сценарий использования после стабилизации точности

Сейчас основной интерфейс — Swagger UI; в репозитории есть вспомогательный
`app/templates/index.html` с Яндекс.Картами. После шагов выше можно оформить
простой пользовательский экран: поле запроса, ссылка на ПИК, применённые условия,
отдельно видимые потери и ограничения, карта и объяснение расстояний. Начать с
проверки текущего шаблона на нескольких реальных сценариях и дорабатывать его,
сохраняя API единым источником ответа.

Польза — человеку проще заметить неполную ссылку до перехода на сайт. Проверять
это задачами «ввести запрос → понять, какие условия учтены → открыть ссылку» и
долей пользователей, правильно распознавших предупреждение.

## Порядок работ

1. Сверить и исправить подтверждённые справочные ID; собрать POI-кэш и измерить
   полноту данных.
2. Повторить замеры бэкендов и прототипировать достоверный `result_count` с
   явной обработкой недостоверного ответа.
3. Завершить категории предупреждений и закрепить проверку смысла выдачи.
4. На стабильном API улучшить пользовательский экран; после этого оценивать
   расширение гео-поиска по реальным маршрутам и оптимизацию ИИ-вызовов.

Каждый этап должен оставлять работающим базовый детерминированный путь без ИИ
и не добавлять фильтры, которые нельзя подтвердить справочником или поведением
ПИК.
