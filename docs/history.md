## Описание проекта
**picurl** — микросервис для преобразования текстовых запросов на русском языке (например, «хочу двушку у метро до 15 млн») в готовые рабочие ссылки с примененными фильтрами на сайт недвижимости pik.ru. 
Сервис принимает свободный текст о желаемой квартире и возвращает рабочую ссылку на pik.ru с уже применёнными фильтрами и сортировкой — чтобы не тыкать вручную по чекбоксам на сайте.
Логика основана на детерминированном парсинге: используются регулярные выражения и нечеткий поиск по локальным JSON-справочникам. ИИ-обогащение работает как опциональный ограниченный fallback для сложных контекстных и пространственных запросов, при этом основной пайплайн полностью самодостаточен и не требует обращения к LLM в рантайме. Интерактивная работа осуществляется через Swagger UI (по умолчанию на `http://127.0.0.1:8000/docs`).

## Технологический стек
- **Язык**: Python 3.12+
- **Веб-фреймворк**: FastAPI, Uvicorn
- **Менеджер пакетов**: `uv`
- **Ключевые библиотеки**: `pydantic` v2, `rapidfuzz`, `httpx`
- **Тестирование**: `pytest`, `pytest-asyncio`
- **Линтер/Форматтер**: `ruff`
- **Стек ИИ-обогащения (v2)**: Anthropic SDK, Google Antigravity, PostgreSQL 15+ (с pgvector), `sentence-transformers`, `asyncpg`, `pydantic-settings`

## Конвенции кода
- Строгая типизация и валидация данных через Pydantic.
- Максимальная длина строки — 100 символов (настроено в Ruff).
- Включенные проверки Ruff: `E`, `W`, `F`, `I`, `UP`, `B`, `SIM`, `C4`, `RUF`.
- Проект намеренно использует русский текст в строках, докстрингах и комментариях, поэтому проверки амбигуити кириллицы отключены (`RUF001`, `RUF002`, `RUF003`).
- Асинхронные тесты выполняются через `pytest-asyncio` в режиме `auto`.

## Декомпозиция и промпты для сборки

В `prompts/` лежит готовая декомпозиция задачи — набор пронумерованных `.md`
промптов для пошаговой сборки сервиса (по одному на агента/шаг). Порядок и обзор —
в `prompts/README.md`; общие конвенции (стек, инварианты, структура) — в
`prompts/_conventions.md`; открытые вопросы — в `prompts/_open-questions.md`.

Порядок применения: 00 (каркас) → 01 (URL-схема pik.ru) → 02 (Criteria) →
03 (справочники) → 04 (regex-правила) → 05 (rapidfuzz-матчинг) → 06 (фасад parse)
→ 07 (url_builder) → 08 (валидатор) → 09 (POST /build-url) → 10 (интеграционные
тесты). Применять последовательно; после каждого шага гонять линт + тесты.

Ключевые инварианты (детали в `prompts/_conventions.md`): базовый пайплайн не использует LLM/внешние API в рантайме (ИИ-обогащение — опциональный слой); единственный обязательный сетевой вызов на запрос — валидация выдачи через backend API pik.ru; нераспознанное всегда уходит в `warnings`, ничего не отбрасывается молча; справочники — отдельный локальный JSON-слой, обновляемый скриптом.

## URL-схема pik.ru — источник правды

**`docs/pik-url-schema.md`** — единственный источник правды по схеме фильтров
`pik.ru/search` (промпт 01, выполнен). На него опираются справочники (03),
`url_builder` (07) и `validator` (08). Центральное правило схемы —
**single-путь / multi-query**: одно значение фильтра → слаг в пути URL,
два и больше → query-параметр с id/GUID через запятую.

Решённые открытые вопросы (из `prompts/_open-questions.md`):

- **№1 (дефолтная сортировка):** если пользователь не указал сортировку,
  `sortBy`/`orderBy` не добавляются вовсе — действует дефолтная выдача сайта
  («рекомендуемые»).
- **№2 (Одиночные optionGroups):** одиночные `optionGroups` всегда добавляются
  в query-параметры (как и `options`), а не в путь URL.

## Контракт Criteria и модели API (промпт 02 — выполнен)

- **`app/parsing/schema.py`** — внутренний контракт критериев: pydantic-модель
  `Criteria` (+ `Rooms`, `Sort`, `HousingType`, `MatchedEntity`). На неё
  опираются парсинг (промпты 04–06) и `url_builder` (07). «Пустой» `Criteria()`
  валиден: скаляры — `None`, списки — пустые. Ключевые решения — в докстринге
  модуля: `rooms` — всегда список (single vs multi решает url_builder по длине);
  `finish` — список `Finish` (`list[Finish]`); `sort` — строковый ключ
  `price_asc|price_desc|area_asc|area_desc` с properties `field`/`order`
  для `sortBy`/`orderBy`. Для подготовки к ИИ (промпт 16) добавлены поля
  `poi_requirements` (список POI, извлеченных из текста) и `center_requested` (булево).
- **Модели API** `BuildUrlRequest`/`BuildUrlResponse` живут в `app/main.py`
  (это контракт HTTP-слоя, не парсинга). Ответ: `{url, criteria, result_count,
  warnings}`; человекочитаемое представление критериев для поля `criteria` даёт
  `Criteria.to_public_dict()` (пример: `{"rooms": "2", "price_max": 15000000,
  "metro": ["Аэропорт Внуково"], "finish": "готовая", "sort": "price_asc"}`).
  Поле `text` запроса имеет `examples` — Swagger-форма открывается
  предзаполненной. Тесты контракта — `tests/parsing/test_schema.py`.

## Справочники (промпт 03 — выполнен)

Локальный JSON-слой для матчинга сущностей (метро/округа/районы/ЖК/программы/
опции). Лежат в `app/reference/*.json`: `metro.json`, `counties.json`,
`districts.json`, `complexes.json`, `benefits.json`, `option_groups.json`,
`options.json`.

- **Формат записи** (единый для всех файлов): `{"name": "...", "slug": "...",
  "id": "...", "aliases": [...]}` — pydantic-модель `RefEntry` в
  `app/reference/loader.py`. Из-за правила single-путь/multi-query на сущность
  нужны **обе URL-формы**: `slug` (одиночный выбор → путь) и `id`/GUID
  (multi-выбор → query). `slug`/`id` опциональны — недостающую форму
  `url_builder` обязан отправлять в `warnings`, а не отбрасывать молча.
  `id` хранится строкой (единый формат для GUID метро и числовых id).
- **Загрузка**: `app/reference/loader.py` — функции `load_metro()`,
  `load_counties()`, …, агрегат `load_all() -> ReferenceData` (точка входа для
  матчера, промпт 05). Кэш через `functools.cache`; сброс — `clear_cache()`.
  Точный поиск по имени/алиасу — `find_by_name()` (нормализация: casefold,
  ё→е, схлопывание пробелов — `normalize()`); fuzzy — задача промпта 05.
  **Рантайм читает справочники только с диска, в сеть за ними не ходит.**
- **Обновление**: `uv run python -m app.reference.refresh` — единственное
  (кроме валидатора) место с сетевым доступом; тянет открытый backend
  `api.pik.ru/v2/block` и перезаписывает `complexes/counties/metro/districts`.
  Мёрж не затирает ручную докурацию (кураторские `slug`/`id`/`aliases`
  сохраняются), сортировка стабильная — диффы читаемы. Эндпоинт `/internal/refresh-dicts`
  защищён секретным токеном через заголовок `X-Internal-Token`, который сверяется с
  переменной окружения `INTERNAL_REFRESH_TOKEN`.
- **Ограничение**: GUID-ы станций (`metroStations`) и числовые id округов
  (`districtCounties`) отдаёт только front-API `www.pik.ru` (закрыт бот-защитой
  Qrator) — эти поля докуриваются **вручную**; `benefits/option_groups/options`
  скрипт не трогает.
- Тесты: `tests/reference/test_loader.py`, `tests/reference/test_refresh.py`
  (сеть замокана через `httpx.MockTransport`).

### Гео-обогащение станций из OSM (`refresh_metro_geo`)

`uv run python -m app.reference.refresh_metro_geo` — **отдельная ручная
офлайн-команда** (в `REFRESHABLE` основного `refresh.py` намеренно не входит:
источник другой — OSM Overpass, а не api.pik.ru). Проставляет в `metro.json`
`lat`/`lon` и новое поле `RefEntry.line` (линия станции). Зачем: координаты
станции делают возможным детерминированное сужение ЖК по расстоянию до метро —
ровно тем же haversine-механизмом, что уже работает для ориентиров
(`landmarks.json` + `app/geo/candidates.py`); ИИ здесь не участвует.

- **Источник** — три маршрутные сети OSM (`type=route`): метро
  (`route=subway`, `network="Московский метрополитен"`), МЦК (`route=train`,
  `ref=14`, та же `network` — в OSM МЦК **не** `light_rail`, проверено на живых
  данных) и МЦД (`route=train`, `network="МЦД"`). Станция берётся из узлов-членов
  отношения, линия — из тегов самого отношения (`ref` `D2` → «МЦД-2», ветка
  `D4А` сводится к «МЦД-4»; у метро — имя маршрута до `:`/`(` без хвоста
  « линия»). Пересадочный узел законно принадлежит нескольким линиям, поэтому
  `line` — все они через `" / "` (ничего не теряем молча, инвариант 3).
- **Мёрж** — по образцу `refresh.merge_entries`: обновляются только
  `lat`/`lon`/`line`, кураторские `name`/`slug`/`id`/`aliases` не затираются,
  сортировка стабильная. Сопоставление: точное по имени → точное по алиасу →
  нечёткое (rapidfuzz `QRatio`, порог 93, имена короче 6 символов нечётко не
  сравниваются). Порог держим высоким намеренно: «Волоколамск» ≠
  «Волоколамская» (91.7 — ниже порога), лучше добавить новую запись, чем
  приписать координаты чужой станции. Если на одну запись претендуют несколько
  станций OSM, линии объединяются, а координаты берутся у совпадения с лучшим
  приоритетом (имя > алиас > fuzzy).
- **Новые станции** (в первую очередь МЦД, которых в справочнике почти не было)
  добавляются записями `name`+`aliases`(из `alt_name`/`short_name` OSM, не
  выдуманные)+`lat`/`lon`/`line` **без** `slug`/`id` — эти поля по-прежнему
  докуриваются вручную (то же известное ограничение, что и с GUID-ами).
- **Результат живого прогона** (2026-07-23): 379 записей, из них 350 с
  координатами и линией, 130 станций МЦД. Публичный Overpass регулярно отвечает
  429/504 под нагрузкой — это временный отказ, скрипт ретраит его
  (`RETRY_ATTEMPTS`/`RETRY_SLEEP_SECONDS`).
- Тесты: `tests/reference/test_refresh_metro_geo.py` (сеть замокана
  `httpx.MockTransport`: разбор ответа, вывод имени линии, ретрай, мёрж без
  потери кураторских полей, добавление новых станций, идемпотентность).

### Кураторская чистка дублей `metro.json` (после гео-обогащения)

По итогам прогона `refresh_metro_geo` из 379 записей 29 координат не получили —
разобраны вручную (проверка фактов через Wikipedia, не вслепую) скриптом
`scripts/cleanup_metro_duplicates.py` (разовый, идемпотентный: повторный запуск
на уже вычищенном файле падает с явной ошибкой «запись не найдена», а не молча
портит файл повторно). Итог: 379 → 357 записей, 350 с координатами. Формат
записи на диск переиспользует `refresh.write_entries`/`load_existing` — диффы
идентичны стилю `refresh.py`.

- **Станции других городов удалены** (СПб/Казань/Екатеринбург, ни у одной не
  было `slug`/`id`): Ботаническая (Екатеринбург), Девяткино, Ладожская,
  Обводный канал, Приморская, Проспект Ветеранов (все — Петербургский
  метрополитен), Суконная слобода (Казань).
- **Точные дубли-заглушки без своей ценности удалены** (без `slug`/`id`,
  содержимое уже покрыто полной записью): «Бутырская » (хвостовой пробел),
  «Красный строитель» (регистро-дубль «Красный Строитель»), «Новомосковская
  (Коммунарка)» (обе станции уже существуют отдельно с координатами).
- **Дубли БЕЗ `id`/`slug` слиты в основную запись как алиас** (имя дубля и его
  алиасы переносятся в `aliases` основной записи, сама запись убирается из
  списка): «Библиотека им.Ленина» → «Библиотека имени Ленина»; «Матвеевское» →
  «Матвеевская» (подтверждено Wikipedia: официальное название станции —
  «Матвеевская»); «Покровское-Стрешнево» (закрытая платформа) → «Стрешнево»;
  «Деловой центр (Выставочная)» → «Деловой центр» (алиас «Выставочная» — старое
  имя станции Филёвской линии, переименованной в 2023); «Тестовская» →
  «Москва-Сити» (переименована 31.03.2024, подтверждено).
- **Строящиеся станции с датой в названии оставлены**, а не удалены: «Липовая
  Роща 2027 год» → «Липовая Роща», «Новорижская 2027 год» → «Новорижская» (обе —
  реально строящиеся станции Рублёво-Архангельской линии БКЛ, есть `id`; дата
  вынесена в алиас).
- **Реальные, но пока не привязанные к OSM записи оставлены как есть** (не
  мусор, задокументированный пробел): «Ермакова Роща» (проектируемая станция
  МЦД-4), «Ж/д станция Мытищи» (есть `id` — правило 1 обязывает не удалять),
  «Лесная» (платформа Ярославского направления, Электросталь), «Малино»
  (временно закрытая платформа, Химкинский округ), «Серп и Молот» (платформа
  Горьковского направления).
- Тест инварианта — `tests/reference/test_metro_integrity.py`: ни одной записи
  без координат одновременно без `slug` и без `id` (кроме явного allowlist-а
  из пункта выше), нет дублей по нормализованному имени, нет повторяющихся id,
  регрессия на конкретно устранённые дубли.

#### Инцидент: потеря 7 GUID слиянием и его исправление

**Слияние записи с непустым `id`/`slug` в другую запись ЗАПРЕЩЕНО** — это
безвозвратно теряет её GUID/slug (в результирующей записи остаётся только id
основной записи, id дубля просто выбрасывается). Первая версия
`cleanup_metro_duplicates.py` нарушала это правило: она считала «запись с
`id`/`slug` никогда не удаляется — максимум сливается как алиас» достаточной
защитой, но слияние-как-алиас **тоже теряет id дубля**, если у основной записи
уже есть свой собственный `id`, — сохраняется только имя/алиасы, а не GUID.
Пострадали семь станций: «Крюково», «Кунцевская (БКЛ)», «Кунцевская
(Филёвская)», «МЦД-1 Кунцевская», «МЦК Бульвар Рокоссовского», «МЦК Шоссе
Энтузиастов», «Очаково I» — все были слиты в физически совпадающую станцию
(общие координаты), но GUID у каждой — **отдельное** значение фильтра
`metroStations` на pik.ru (разные платформы/линии одного узла), поэтому потеря
не косметика: выдача сужалась до одной платформы вместо всех.

Исправление:

- Все семь записей **восстановлены как самостоятельные записи** справочника
  (не алиасы) со своим оригинальным `id`; `lat`/`lon`/`line` проставлены по
  канонической станции, в которую их когда-то ошибочно слили (координаты
  физически совпадают — это одна и та же точка на карте, разные платформы).
- Имя каждой восстановленной записи убрано из `aliases` канонической записи
  (иначе один и тот же текст матчился бы на две записи и парсер выдавал бы
  «Неоднозначность»). Для пары «Кунцевская (БКЛ)»/«Кунцевская (Филёвская)»

## Справочник именованных ориентиров (промпт 23 — Milestone AI-8)

`app/reference/landmarks.json` — отдельный класс сущности: именованный ориентир
(вуз/крупный работодатель/достопримечательность), которого нет в URL-схеме
pik.ru. Запросы «рядом с МГУ», «у Кремля», «поближе к Сколково» сайт не может
выразить фильтром — их обслуживает **сужение списка ЖК (`complexes`) по
дистанции** через уже существующий multi-query механизм `blocks=id,id`.

- **Формат записи** — тот же `RefEntry` (`name`/`slug`/`aliases`) плюс
  обязательные `lat`/`lon` и поле `category` (`university | employer |
  landmark`, расширяемо). `slug` здесь — стабильный ключ ориентира, а не путь
  URL (у pik.ru нет пути «рядом с ориентиром»). Загрузка — `load_landmarks()`,
  входит в агрегат `load_all()` (поле `ReferenceData.landmarks`).
- **Откуда данные**: список **вручную курируемый** (35 самых частотных
  ориентиров Москвы), не скрейпинг. Это осознанно — полный OSM-дамп
  (`amenity=university`/`tourism=*`) добавил бы тысячи мелких точек и **снизил
  бы точность** нечёткого матчинга сильнее, чем отсутствие полноты. Полный
  источник (OSM Overpass) отмечен как возможное расширение в
  `prompts/_open-questions.md` (№12) — не реализован намеренно. Пополнение —
  правкой JSON вручную (аналогично докуривке GUID метро / id округов). Скрипт
  `refresh` этот файл **не трогает** (не в `REFRESHABLE`).
- **Извлечение**: `app/parsing/rules/landmark.py` (`extract_landmark_requirements`,
  включён в `apply_rules`). Переиспользует подход матчинга сущностей: маркер
  близости («рядом с», «у», «поближе к», «недалеко от», «ближе к», «около»,
  «возле» + имя) → скользящее окно из следующих 1–3 слов → нечёткое
  сопоставление (rapidfuzz `WRatio` + строгая перепроверка `QRatio`, порог 88)
  с именами/алиасами справочника. Результат — `Criteria.landmark_requirements:
  list[LandmarkRequirement]` (`app/parsing/schema.py`): имя + координаты
  ориентира + опциональный `max_distance_m` (по аналогии с `POIRequirement`).
  Маркеры-предлоги («у метро …») без совпавшего ориентира ложных требований не
  дают — порог держим высоким намеренно.
- **Превращение в сужение `complexes` без похода в ИИ**: как только ориентир
  распознан (детерминированно, rapidfuzz) и у него есть координаты, а у ЖК уже
  лежат `lat`/`lon` (промпт 16, `complexes_from_blocks`),
  `app/geo/candidates.build_candidate_shortlist` фильтрует/ранжирует кандидатов
  по расстоянию до ориентира через `app/geo/distance.haversine` — **чистая
  математика, ИИ здесь не участвует**. Ближайшие ЖК идут первыми; при заданном
  `max_distance_m` — жёсткая отсечка. Усечение до `SHORTLIST_LIMIT` (50)
  применяется **после** сортировки по дистанции, чтобы «первые N из справочника»
  не отсекли реально ближайшие ЖК. Координаты (`ComplexCandidate.lat/lon`)
  передаются модели лишь как объективный факт; расстояния LLM **не считает**
  (это невоспроизводимо и не проверяемо — см. инвариант 1 `_conventions.md`).
- Тесты: `tests/parsing/test_rules.py` (распознавание «рядом с МГУ», склонения,
  отсутствие ложных срабатываний), `tests/geo/test_candidates.py`
  (сортировка/отсечка шорт-листа по дистанции без ИИ).

## Regex-правила структурных фактов (промпт 04 — выполнен)

`app/parsing/rules.py` — извлечение структурных фактов из свободного текста
чистыми функциями (regex + словари синонимов, без сети/LLM/состояния). Каждая
`extract_*` возвращает `(значение, consumed_spans)` — список полуинтервалов
`(start, end)` «понятых» кусков исходного текста (для вычисления нераспознанного
в фасаде `parse`, промпт 06). Матчинг — по нормализованной копии текста
(lowercase + ё→е, длина сохраняется — индексы валидны для исходной строки);
regex скомпилированы один раз на уровне модуля.

Поддерживаемые фильтры:

- **комнатность** (`extract_rooms`) — «студия», «однушка/двушка/трёшка»,
  «2к», «2-комнатную», «2-х комнатная», перечисления («1-2 комнатные»,
  «1, 2 и 3 …»), чип «3+» (и «2+» → `[two, three_plus]`); ≥3 комнат → чип `3+`;
- **цена** (`extract_price`) — «до/от/за X», диапазоны «10-15 млн», «бюджет
  15м», слитные суффиксы «800к», единицы млн/тыс/руб; нормализация в рубли;
  голые числа ≥ 100 000 → рубли (порог отсекает этажи/метры);
- **площадь** (`extract_area`) — общая («от 70 м²», «70-100 метров»,
  «площадь от 40») и кухня («кухня от 8», «с кухней от 10 метров») — различаются
  ключевыми словами, кухня извлекается первой;
- **этаж** (`extract_floor`) — «с 5 по 20 этаж» → `floor_min/max`; «не первый»,
  «высокий этаж» → `not_first_floor`; «последний» → `last_floor`;
  «не последний» → `not_last_floor` (добавляет `notLastFloor=1`);
- **отделка** (`extract_finish`) — «с отделкой»/«чистовая»/«под ключ» → `True`;
  «без отделки»/«черновая» → `False`; при противоречии побеждает последнее
  упоминание;
- **заселение** (`extract_ready`) — «заселение сразу», «готовый дом», «сдан» →
  `ready=True`;
- **сортировка** (`extract_sort`) — «подешевле» → `price_asc`, «подороже» →
  `price_desc`, «площадь побольше/поменьше» → `area_desc`/`area_asc`;
- **прочее** — «только квартиры»/«без апартаментов» →
  `housing_type=flats_only` (`extract_housing_type`); «не бронь»/«только
  свободные»/«доступные» → `only_available` (`extract_only_available`);
- **неподдерживаемое** (`extract_unsupported`) — каталог заведомо
  неподдерживаемых pik.ru фильтров (`_UNSUPPORTED_CATALOG` в `rules/misc.py`):
  критерии не трогаются, фрагмент исходного текста возвращается маркером для
  warning **со своим человекочитаемым объяснением** (см. ниже).

Агрегат `apply_rules(text) -> RulesOutcome(criteria, consumed, unsupported)`
прогоняет все правила и собирает готовый `Criteria`. Тесты —
`tests/parsing/test_rules.py` (табличные, `pytest.mark.parametrize`).

### Каталог заведомо неподдерживаемых фильтров (Milestone AI-9, промпт 24)

`_UNSUPPORTED_CATALOG` в `app/parsing/rules/misc.py` (`extract_unsupported`) —
список `(паттерн, объяснение)` для пожеланий, которых **нет и не может быть**
в URL-схеме pik.ru (`docs/pik-url-schema.md`). Это **не баг парсера**, а потолок
возможностей самого сайта: строить по ним нечего ни детерминированному пайплайну,
ни ИИ — и ИИ **не должен** пытаться обойти это, придумав замену. Отличать от:
«бэк не осилил разбор» (промпт 22 — фильтр есть, но не распознан) и «нет
справочника сущностей» (промпт 23 — фильтр есть, но нет данных); здесь фильтра
нет в самой схеме.

Текст warning явно говорит «не поддерживается pik.ru — пропущен(о)» (в отличие
от generic «не удалось распознать, не попало в ссылку» для нераспознанного
мусора): клиенту это разное по смыслу — «сформулируй иначе» vs «pik.ru так не
умеет вообще». Записи (каждая сверена по факту со схемой):

- «вторичка / вторичный рынок / вторичное жильё» — pik.ru продаёт только
  новостройки;
- «сторона света» / вид «на светлую/солнечную/южную/северную… сторону» —
  фильтра по сторонам света в схеме нет (эталонный кейс милстоуна);
- «раздельный санузел» — в схеме есть только «Два и более санузла»
  (`manybathrooms`) и «Сквозной санузел» (`throughbathroom`);
- «кирпичный/монолитный/панельный/блочный дом» — фильтра по материалу стен нет.

**Важно:** прежде чем заносить кандидата, свериться со схемой, что фильтра
правда нет (а не просто отсутствует в справочнике). Так, «панорамные окна» и
«окна во двор» в каталог **не** попали — они поддерживаются под именами «Большие
окна» (`bigwindows`) и «Вид во двор» (`vidVoDvor`) в `option_groups.json` /
`options.json` и обслуживаются матчингом сущностей. Каждая запись каталога имеет
свой параметризованный тест на текст warning в `tests/parsing/test_rules.py`.

### Аудит тихих потерь в regex-правилах (Milestone AI-7, промпт 22)

Систематический проход по всем `extract_*` в `app/parsing/rules/*.py` на предмет
паттерна «regex матчит уточнение (span засчитан «понятым»), но содержимое
группы нигде не читается → факт теряется молча» (нарушение инварианта 3
`_conventions.md`). Находки и решения:

- **poi.py, префикс «нов-»** — `PREFIX` матчил «новые/новый» перед POI, но
  флаг «нужен новый» терялся. **Исправлено:** захват именованной группой `new`
  → новое поле `POIRequirement.only_new` (per-instance: «новые сады»
  `only_new=True`, а соседние «школы» — `False`). Прокинуто в шорт-лист/резолв
  фактов (`app/geo/candidates.build_query_signature` различает «сады» и «новые
  сады») и в промпт-контекст ИИ (через `Criteria.to_public_dict`, как
  структурный факт, а не текст).
- **poi.py, дистанция POI** (закрытие `AUDIT_REPORT.md` 2.11) — поле
  `POIRequirement.max_distance_m` было объявлено, но парсинг не написан
  (`# TODO`). **Исправлено:** разбор «школа в 300 метрах», «садик не дальше
  500 м» (группа `dist`) заполняет `max_distance_m`; поле больше не «висит».
- **poi.py, предлог «с/со» и хвост «поблизости/рядом/близко»** — матчатся и
  входят в span, но фильтрующего смысла не несут (грамматическая связка /
  «близость» — это и есть суть POI-требования). **Осознанно отброшено**,
  причина задокументирована в docstring `extract_poi_requirements` и в
  комментариях у `PREFIX`/`SUFFIX` (поле не заводится — «не плодить поля ради
  полноты»).
- **Остальные `extract_*`** (area/price/floor/rooms/misc/time) — необязательные
  части там либо декоративные связки вокруг уже разбираемого значения
  (`_AREA_FILLER` «была/чтоб/большая», `_OPT_RUB`, «год» в сроке заселения,
  дата-хвост у `requiredTags`), либо служат только для консюминга span'а
  (`_ROOMS_NEGATION` «кроме студии» — исключающего фильтра комнат на pik.ru
  нет). Новые поля не заводились; значимых структурных потерь не найдено.

Тесты аудита: `test_poi_only_new_flag`, `test_poi_only_new_is_per_instance`,
`test_poi_max_distance_parsed` в `tests/parsing/test_rules.py`.

## API

**Интерфейс пользователя — это Swagger-форма на `/docs`** (своего фронтенда нет). 
Пользовательский сценарий:
1. Запустить сервис (`uv run fastapi dev`).
2. Открыть в браузере `http://127.0.0.1:8000/docs`.
3. Раскрыть `POST /build-url`, нажать **Try it out**.
4. Вписать желание в поле `text` (например: `"хочу двушку у метро, до 15 млн, с отделкой"`).
5. Нажать **Execute**.
6. В ответ приходит JSON-документ:
   ```json
   {
     "url": "https://www.pik.ru/search/...",
     "criteria": { "rooms": "2", "price_max": 15000000, "complexes": ["Какой-то ЖК"] },
     "result_count": 47,
     "warnings": [],
     "ai_used": true,
     "ai_failed": false,
     "ai_cache_hit": false,
     "ai_explanation": "ЖК 'Какой-то ЖК' имеет школу поблизости."
   }
   ```

**Поток обработки:**
1. Принимается запрос `BuildUrlRequest` со строкой `text`.
2. `parse(text)` извлекает `Criteria` и список предупреждений `warnings`.
2.5. **ИИ-обогащение (опционально)**: если в `criteria` есть `poi_requirements` или `center_requested`, вызывается ИИ для сужения `complexes`. Обратная совместимость сохранена — при выключенном ИИ или ошибке процесс продолжается с исходными `criteria`.
3. `build_url(criteria)` строит ссылку `url` на основе собранных критериев.
4. `validate(criteria)` делает проверочный HTTP-запрос к API pik.ru. Если результатов 0, в `warnings` добавляется: `"под критерии ничего не найдено"`.

## Стресс-тестирование парсера (`stress_test_queries.md`)

`stress_test_queries.md` — 10 объёмных запутанных запросов (противоречия,
сленг, опечатки, «вода») для ручной проверки устойчивости парсера. По итогам
прогона все 10 пунктов через `POST /build-url` найден и исправлен ряд багов:

- **Матчер сущностей** (`app/parsing/entity_match.py`) ложно матчил короткие/
  служебные слова на случайные сущности справочника («мы» → район «Мытищи»,
  «молодая» → метро «Молодежная», обрывок «Этаж … Ищем» → опция «Два и более
  санузла»), потому что заглавная буква (первое слово предложения — не
  признак имени собственного) или триггер-слово полностью отключали защитную
  проверку `QRatio`. Убрана привилегия по заглавной букве; «синтетические»
  окна эвристики союзов («и»/«или», склеивающие слова из разных мест текста)
  теперь всегда проверяются строго — это же убрало и ложную сущность/
  предупреждение об неоднозначности («Бульвар МЦК» → «Бульвар Адмирала
  Ушакова», «метро Строгино Мякинино» → мнимая неоднозначность с Мякинино).
- **regex-правила** (`app/parsing/rules.py`): «высокий этаж»/«площадь общая»
  распознавались только в одном порядке слов (не в обратном — «этаж
  высокий»/«площадь общая»); ключевые слова «кухня»/«площадь» не допускали
  связку перед числом («кухня была от 12», «кухня чтоб большая от 12») — из-за
  этого площадь кухни могла попасть в общую площадь или потеряться целиком.
  Добавлена поддержка обратного порядка и типовых связок.

- **Справочник округов** (`app/reference/counties.json`): в «Новомосковский
  АО» добавлен алиас «ТиНАО» — без него округ не распознавался вовсе.
- **warnings-шум**: список стоп-слов в `app/parsing/parser.py` расширен

## Архитектура ИИ и Базы Знаний (Предложение и v2)

Сформировано архитектурное решение по внедрению ИИ для разбора сложных контекстных и пространственных запросов ("квартира с детским садом неподалеку").
ИИ-обогащение работает как ограниченный fallback: оно вызывается только когда после детерминированного парсинга остаётся нераспознанный семантический остаток запроса.
Каждый ответ ИИ сохраняется в карту памяти. Основной пайплайн полностью самодостаточен.
Подробное описание архитектуры, потока запроса и интеграции с текущим кодом находится в `docs/ai-enrichment-architecture.md`.

Создана директория `app/knowledge_base/` для будущего локального векторного хранилища и кэшированных весов.
Также созданы директории `app/ai/` и `app/geo/` для работы ИИ-агента и гео-слоя.

### Аудит и починка слоя данных ИИ (гео-контекст кандидатов)

По итогам аудита ИИ-обогащения устранены три дефекта, из-за которых модель
работала «вслепую» (кандидаты уходили в LLM с пустыми полями):

- **Связь ЖК→локация больше не теряется** (`app/reference/refresh.py`).
  `api.pik.ru/v2/block` отдаёт `block.district` / `block.metro` /
  `locations.child` (округ), но `complexes_from_blocks` раньше сохранял только
  name/slug/id/lat/lon. Теперь привязка ЖК к району/метро/округу пишется прямо
  на записи ЖК: в `RefEntry` добавлены поля `district`/`county`/`metro`
  (заполняются только для `complexes.json`, у прочих справочников — `None`),
  `merge_entries` их сохраняет при мёрже. **Чтобы данные попали в JSON, нужен
  ручной прогон `python -m app.reference.refresh`** (сеть) — текущий
  `complexes.json` их ещё не содержит.
- **Шорт-лист кандидатов сужается по запросу** (`app/geo/candidates.py`).
  `build_candidate_shortlist` теперь заполняет `ComplexCandidate` реальными
  district/county/metro и вычисляет `is_center` по району (маппинг из
  `districts.json`). Лимит вынесен в `SHORTLIST_LIMIT`. Если пользователь назвал
  ЖК — берутся только они; если сузил запрос районом/округом/метро — в шорт-лист
  попадают только совпадающие ЖК, а не произвольные «первые N».
- **Центр разрешается детерминированно** (`app/geo/candidates.py`).
  Центральность района — статический флаг `is_center` в справочнике, LLM для неё
  не нужен. `resolve_known_facts` больше не обнуляет POI-матчинг при
  `center_requested` (совпадением по центру считается ЖК с `is_center=True`), а
  `fully_resolved(known, criteria, candidates)` разрешает центр из справочника,
  когда `is_center` известен у всех кандидатов; хоть один неизвестный (`None`) —
  уходим в ИИ, а не додумываем молча. Наполнение `is_center`/`id` районов —
  вопрос ручной докуривки/промоушена (`districts.json` их пока не содержит).

Заполнение `candidate.district` реальными данными автоматически чинит и
`sanitize_against_shortlist` (фильтр центральных районов по кандидатам), который
раньше вырезал всё из-за пустого `district`. Тесты: `tests/geo/test_candidates.py`,
`tests/reference/test_refresh.py::TestExtractors::test_complexes_carry_location_binding`.

### Аудит ИИ-слоя, часть 2 (надёжность обучения, кэш, клиент)

- **Промоушен-пороги вынесены в конфиг и ужесточены** (`app/config.py`,
  `app/ai/promotion.py`). `AI_PROMOTION_MIN_OBSERVATIONS` (дефолт 5, был хардкод 3)

- **Многоязычные эмбеддинги** (`app/ai/embeddings.py`):

  почти нулевой hit-rate кэша. Размерность 384 сохранена (схема БД `halfvec(384)`
  не меняется). Порог кэша `lookup_semantic` поднят 0.15 → 0.2 (0.15 отсекал
  перефразировки; значение требует калибровки на реальных данных).
- **Сигнатура кэша учитывает criteria** (`app/geo/candidates.py`):
  `build_query_signature` добавляет POI-категории и флаг центра к тексту, чтобы
  кэш различал запросы, совпадающие по словам, но требующие разного обогащения.
- **Клиент Claude** (`app/ai/client.py`): `AsyncAnthropic` переиспользуется
  (кэш по ключу, не новый httpx-пул на запрос); импорт `google.antigravity`

- **Дефолтная модель** — `gemini-3.5-flash` (была `claude-haiku-4-5` и
  `claude-3-haiku-20240307`): дешёвая и быстрая для семантического отбора по

### ИИ-резолвинг фраз под опции + самообучение алиасов (Milestone AI-10, промпт 25)

**Новая способность ИИ (не доработка существующего пути):** фразы-синонимы
фильтров, которые rapidfuzz не матчит по строковому сходству («квартира с
отдельным санузлом» ≈ «Два и более санузла», slug `manybathrooms`), раньше молча
уходили в `warnings` — общего fallback «на весь необъяснённый остаток» в коде не
было (был только для POI-категорий и флага центра). Теперь такие фрагменты
добивает ИИ.

- **Сбор фрагментов-кандидатов** (`app/parsing/parser.py`): фасад `parse` кроме
  `warnings` возвращает `ParseResult.option_candidates` — короткие нераспознанные
  фрагменты, похожие на опцию/группу опций. Эвристика `_looks_like_option`:
  значимых (не стоп-слов) лексем не больше `MAX_OPTION_CANDIDATE_WORDS` (4), есть
  хотя бы одна буквенная (даты/голые числа отсекаются). Заведомо
  неподдерживаемые pik.ru фразы (каталог 24) сюда не попадают — их спаны уже
  «понятые». Обратная совместимость: `criteria, warnings = parse(text)` работает
  (итерация `ParseResult` даёт ровно два элемента).
- **Резолвинг через ИИ** (`app/ai/enrichment.py`, `resolve_options`): если
  фрагменты есть, в контекст модели (`app/ai/prompts.py`, `build_option_context`
  + `OPTION_SYSTEM_PROMPT`) уходит **полный** список `options`/`option_groups`
  (name+slug, без усечения шорт-листом — тут кандидаты не ЖК, а сами фильтры) и
  сами фрагменты. Модель (`call_option_resolver`, схема `OptionResolutionAnswer`)
  на каждый фрагмент отвечает slug совпавшего фильтра или `null`. Ответ
  **обязательно** валидируется против реального списка slug'ов справочника
  (`sanitize_option_resolution` — аналог `sanitize_against_shortlist`):
  выдуманные slug и `null` отбрасываются, фраза остаётся в `warnings`. Ветка
  независима от шорт-листа ЖК (мутирует `criteria.options`/`option_groups` и
  `warnings` на месте), вызывается из `enrich(..., option_candidates=...)`, а тот
  — из `POST /build-url` (`app/api/endpoints.py`) с
  `parse_result.option_candidates`. При выключенном ИИ фрагменты остаются в
  `warnings`, модель не дёргается.
- **Логирование сопоставлений** (`app/ai/enrichment.py`): каждое «нормализованная
  фраза → slug» пишется в `ai_structured_facts` через `store_structured_fact`
  (карта памяти промпта 17, логика конфликтов переиспользуется) с
  `fact_type="option_alias"` (`OPTION_ALIAS_FACT_TYPE`),
  subject_type/subject_id = тип и slug фильтра, `fact_value={"phrase": ...}`.
- **Промоушен алиасов с защитой от неоднозначности** (`app/ai/promotion.py`,
  `analyze_option_aliases`/`promote_aliases`): **до** обычного порога
  наблюдений/уверенности (промпт 20) проверяется согласованность фразы по **всем**
  наблюдениям (не по конкретному `subject_id`). Если доля наблюдений,
  указывающих на доминирующий slug, ниже `AI_ALIAS_PROMOTION_MIN_CONSISTENCY`
  (дефолт 1.0 = единогласие) — фраза расходится между slug, это конфликт по
  промпту 17: **не промоутится никогда** независимо от числа наблюдений, уходит в
  отчёт «неоднозначные». Согласованная фраза дополнительно проходит обычный
  вентиль; не набравшая порога тихо остаётся на ИИ. При успехе — запись в
  `aliases` `options.json`/`option_groups.json` тем же безопасным мёрж-паттерном,
  что и промпт 20 (кураторские алиасы не затираются). Отчёт «неоднозначные»
  выводится в stdout (`python -m app.ai.promotion --report` — только отчёт,
  ничего не промоутит).
- Тесты: `tests/ai/test_enrichment.py` (фрагмент → контекст модели → slug в
  `criteria`, логирование, отбрасывание галлюцинаций), `tests/ai/test_promotion.py`
  (согласованные наблюдения → alias; расходящиеся → «неоднозначные», не
  промоутятся ни при каком числе наблюдений).

### Наблюдаемость вызовов ИИ и возврат fallback-гейтов (Milestone AI-11, промпт 26)

Полное описание — `docs/ai-enrichment-architecture.md`, раздел 8. Кратко:

- **Таблица `ai_call_log`** (`app/ai/migrations/02_ai_call_log.sql`): при каждом
  вызове `enrich()` (не только при успехе) пишется строка
  (`app.ai.memory.log_ai_call`, best-effort — при `pool=None` пропуск). Поля:
  `occurred_at`, `had_poi_or_center`, `fully_resolved_deterministically`
  (вычисляется и логируется **всегда**, даже пока гейт 2 выключен — это
  измерение «что было бы, если включить»), `cache_hit`, `ai_called`,
  `criteria_changed_by_ai` (итог ИИ отличался от детерминированного слоя).
- **Отчёт**: `python -m app.ai.usage_report` (или `--days N`) — всего запросов →
  % `had_poi_or_center` → из них % `fully_resolved_deterministically` (кандидаты
  на «гейт 2 спас бы вызов») → % `cache_hit` → % `criteria_changed_by_ai` среди
  вызовов ИИ (реальная польза). Аггрегация — чистая `aggregate()`, тесты в
  `tests/ai/test_usage_report.py`. (Отдельная команда, не путать с
  `python -m app.ai.promotion --report` — та про неоднозначные алиасы.)
- **Гейты в `enrich()` были ВЫКЛЮЧЕНЫ** (закомментированы) — возврат
  планировался последним шагом серии 22–26, только когда численный критерий
  подтверждён на данных: гейт 2 при `fully_resolved_deterministically ≥ 90%`
  среди `had_poi_or_center` над окном `N ≥ 500`; гейт 1 (с обязательным
  расширением проверкой `option_candidates` под промпт 25) — при доле
  `had_poi_or_center=false` среди `criteria_changed_by_ai` ≤ 5%. Детали и
  обоснование — раздел 8.4 архитектурного документа. **Статус после Milestone
  AI-14 — см. раздел ниже: гейт 1 включён, гейт 2 остаётся выключенным.**
- **Безопасность `agy`**: `call_antigravity` запускает CLI строго `--print`
  (неинтерактивно) и **никогда** не передаёт `--dangerously-skip-permissions` —
  в промпт попадает сырой `user_query`, это поверхность prompt injection.
- **Модель ИИ — одно поле** `AI_MODEL_NAME` (дефолт `gemini-3.5-flash`),
  используется обоими провайдерами (в `agy --model` и в Anthropic API). Отдельное
  `ANTIGRAVITY_MODEL` убрано (AUDIT_REPORT 1.4). Дефолтный провайдер —
  `AI_PROVIDER=antigravity`.

- **Зависимость `google-antigravity`** оставлена в `pyproject.toml`: Python-кода
  она не импортируется (`grep -rn "import.*antigravity" app/` пусто),

## OAuth-сессия Claude Code вместо API-ключа (Milestone AI-13)

При `AI_PROVIDER=claude` API-ключ больше **не обязателен**. Достаточно быть
залогиненным в Claude Code на этой машине (`claude` → `/login`) — сервис сам
возьмёт OAuth-токен активной сессии. Подход перенесён из соседнего проекта
`workflow-ai`, где он уже отработан. Полное руководство — `ENABLE_ANTIGRAVITY.md`,
шаблон конфигурации — `.env.example`.

- **Резолвинг учётных данных** (`app/ai/client.py`): `resolve_claude_credentials()`
  возвращает `ClaudeCredentials(kind, secret)`, где `kind` — `api_key` либо
  `oauth`. Приоритет: `ANTHROPIC_API_KEY` → `CLAUDE_OAUTH_TOKEN` →
  keychain macOS (`_read_keychain_token()` читает запись
  `Claude Code-credentials` → `claudeAiOauth.accessToken`). Отсутствие всех трёх
  — **не ошибка**, а сигнал выключить ИИ-слой: базовый пайплайн самодостаточен.
- **Заголовки — строго XOR.** Для `api_key` клиент создаётся с `api_key=`
  (заголовок `x-api-key`), для `oauth` — с `auth_token=` (`Authorization:
  Bearer`) плюс `default_headers={"anthropic-beta": "oauth-2025-04-20"}`; без
  этого бета-заголовка API токен сессии не примет. Отправлять оба заголовка
  сразу нельзя — API отвергает такой запрос, поэтому это именно выбор одного.
- **TTL токена — 60 секунд** (`_TOKEN_TTL_SECONDS`). Токен в keychain обновляет
  сам CLI, поэтому он перечитывается, а не кэшируется на весь процесс: refresh
  подхватывается без перезапуска сервиса. Кэш нужен, чтобы не дёргать
  блокирующий `security` на каждый HTTP-запрос.
- **`CLAUDE_OAUTH_TOKEN`** (`app/config.py`) — для сред, где keychain недоступен
  (Linux, CI, docker): туда кладётся токен от `claude setup-token`
  (префикс `sk-ant-oat01-`). На macOS заполнять не нужно.
- **Гейт в `enrich()`/`resolve_options()`** (`app/ai/enrichment.py`) теперь
  считает валидными учётными данными и OAuth-сессию, а провайдера сравнивает
  через `.lower()` — раньше `AI_PROVIDER=Claude` проскакивал гейт и падал уже
  внутри клиента.
- **Проверено живым прогоном:** аутентификация по OAuth работает — API принимает
  токен сессии, запрос доходит до модели. Подтверждение от обратного: в логе нет
  ни одного `401`/`authentication_error`, а приходит `429 rate_limit_error`
  (неверный токен дал бы 401, а не 429).
- **ВАЖНО, лимиты общие.** Токен сессии Claude Code делит квоту с самим Claude
  Code: пока в терминале идёт активная работа, picurl конкурирует с ней за один
  и тот же лимит и получает `429`. Для фонового/продакшн-использования это
  означает, что OAuth-режим — режим для локальной разработки, а под нагрузку
  нужен отдельный `ANTHROPIC_API_KEY` со своей квотой. `429` штатно
  ретраится один раз (`_is_transient`), при повторной неудаче ИИ-слой
  деградирует с warning'ом, базовый пайплайн не страдает.

## Починка по итогам прогона 15 запросов (Milestone AI-13)

Живой прогон 15 разнородных запросов через `POST /build-url` вскрыл пять
дефектов. Все закрыты по TDD, полный `uv run pytest` зелёный.

- **Ориентир не сужал выдачу и молчал** (`app/geo/candidates.py`,
  `app/ai/enrichment.py`). `landmark_requirements` использовались только для
  *ранжирования* шорт-листа: `resolve_known_facts()`/`fully_resolved()`
  проверяли лишь `poi_requirements`/`center_requested`. Запрос «однушка рядом с
  МГУ» отдавал URL без `blocks=` и с пустыми `warnings` — единственное место,
  где нарушался инвариант «ничего не отбрасывается молча». Теперь
  `resolve_known_facts()` считает haversine до ориентира, а в `enrich()` есть
  **всегда включённая ветка без ИИ** для чистого landmark-случая: сужение
  работает независимо от наличия учётных данных Claude. Гейты 1 и 2 остались
  выключенными (Milestone AI-11) — ветка от них независима. Если сузить нельзя
  (ни у одного кандидата нет координат) либо в радиусе пусто — выдаётся явный
  warning. Радиус по умолчанию `LANDMARK_DEFAULT_RADIUS_M` = `CENTER_RADIUS_M`
  (5 км) — **эвристика, требует калибровки** на реальных данных, как и порог
  семантического кэша. Проверка гипотезы: в `complexes.json` координаты есть у
  69 из 72 ЖК, так что сужение физически возможно уже сейчас.
- **Ложный `manybathrooms`** (`app/parsing/entity_match.py`). «Отдельный
  санузел» матчился на «Два и более санузла» — почти противоположность.
  Подстрочный триггер `сануз` из `kw_partial` делал окно «триггернутым», порог
  падал до 75, а строгая перепроверка `QRatio` для таких окон **пропускалась**:
  алиас «несколько санузлов» давал `WRatio=78.75` за счёт `partial_ratio` при
  честном `QRatio=53.85`. Добавлено условие `single_token_option_window`:
  строгая проверка форсируется для односимвольных окон **только** при
  `etype in ("options", "option_groups")`. Шире распространять нельзя —
  проверено: общая версия ломала `ЖК Волжский парк`, где окно «Волжский»
  законно матчится через `partial_ratio`, а за ним обнаруживался ложный район
  «Всеволожский». Триггеры локаций (`жк `, `метро `, `район `) — явные якоря,
  в отличие от подстрочного `kw_partial`, поэтому класс риска у них разный.
- **Противоречие по отделке** (`app/parsing/rules/finish.py`). Код расходился с
  этим файлом: докстринг обещал «сохраняются все уникальные варианты», CLAUDE.md
  — «побеждает последнее упоминание». «С отделкой… без отделки» давало
  `hasFinish=1,0` (оба взаимоисключающих значения). Теперь `Finish.NONE`
  взаимоисключающ с положительными (`READY`/`WHITE_BOX`/`FURNISHED`), при
  конфликте побеждает последнее по позиции; несколько *разных положительных*
  значений конфликтом не считаются и сохраняются (законный мультивыбор). Спаны
  по-прежнему покрывают и проигравший фрагмент — отбрасывается значение, а не
  текст. Два теста с именами `..._last_mention_wins` закрепляли в ассертах ровно
  обратное — приведены в соответствие с именами и с этим файлом.
- **Голое «сады»** (`app/parsing/rules/poi.py`). Паттерн детсада требовал
  «садик/детский сад/детсад», из-за чего «новые сады в 300 метрах» теряло и
  категорию, и `only_new`, и `max_distance_m`. Множественные формы
  («сады/садов/садами») матчатся свободно; голое единственное «сад» — только с
  обязательным префиксом «нов-». Обоснование: станции метро «Ботанический сад» и
  «Александровский сад» существуют только в единственном числе, поэтому
  множественное число безопасно само по себе. На оба топонима есть негативные
  тесты.
- **Цена «лямов за 15»** (`app/parsing/rules/price.py`). Все паттерны требовали
  порядок «число → единица»; добавлен `_PRICE_ZA_UNIT_FIRST` для обратного
  порядка «единица → за N» → `price_max` (поля `price_exact` в `Criteria` нет, а
  «за N» — потолок бюджета; та же трактовка, что у существующего `_PRICE_ZA`).

**Известное и не исправленное:** заглушки в `metro.json` («Аэропорт», «Динамо» —
только `name`, без `slug`/`id`) при точном совпадении имени перебивают полные
записи, и локационный фильтр исчезает из URL (с корректными warnings, не молча).
Это задокументированное ограничение ручной докурировки GUID, а не ошибка кода —
чинится наполнением справочника официальными данными.

## Возврат гейта 1, честный `ai_used` (Milestone AI-14)

Живой прогон показал живой инцидент: на запрос, который ИИ ничем не мог
обогатить (нет `poi_requirements`/`center_requested`/фраз-кандидатов на опции),
`enrich()` всё равно делал **два** обращения к модели (`resolve_options` +
основной вызов) — оба упали в `429` (общая квота OAuth-сессии, см. раздел про
OAuth выше). Это и есть тот самый сценарий, под который проектировался гейт 1
(Milestone AI-11), просто раньше не было живого доказательства необходимости.

- **Гейт 1 ВКЛЮЧЁН.** Итоговое условие в `enrich()` (`app/ai/enrichment.py`):
  не идти в ИИ-путь (шорт-лист/семантический кэш/`call_model`), если у запроса
  нет ни `poi_requirements`, ни `center_requested`, ни непустых
  `option_candidates`, **ни** `landmark_requirements`. Первые три — буквально
  условие из промпта 26/раздела 8.4 (`option_candidates` обязателен в условии —
  иначе резолвинг фраз-синонимов опций, промпт 25, ломался бы, если бы гейт стоял
  раньше вызова `resolve_options()`; на практике `resolve_options()` и так
  вызывается безусловно до гейта, поэтому сам резолвинг опций от гейта не
  зависит — но условие оставлено явным для читаемости и на случай будущего
  рефакторинга порядка вызовов). **`landmark_requirements` — добавленное по
  факту падения тестов исключение**, не входившее в буквальную формулировку
  промпта 26: сужение по ориентиру («рядом с МГУ», Milestone AI-13) — отдельная
  всегда включённая детерминированная ветка ниже гейта, которая сама не зовёт
  ИИ. Без этого исключения гейт схлопывал landmark-only запросы в `noop()` до
  этой ветки — регрессия ровно того бага AI-12, который чинили отдельно
  (проверено падением `test_enrich_resolves_landmark_*`/`test_enrich_landmark_*`
  при попытке обойтись без исключения).
- **Формальный численный критерий активации гейта 1** (доля
  `had_poi_or_center=false` среди `criteria_changed_by_ai` ≤ 5%, раздел 8.4) **на
  момент включения ещё не был подтверждён накопленной статистикой** —
  `ai_call_log` пока не набрал показательного окна наблюдений. Гейт включён по
  прямому эксплуатационному сигналу (живой `429`-инцидент, задокументированный
  выше), а не по достижении порога на данных. Это осознанное отступление от
  плана раздела 8.4, а не молчаливая подмена критерия: как только окно
  наблюдений наберётся, стоит свериться с отчётом `usage_report`, что решение
  задним числом подтверждается.
- **Гейт 2 остаётся ВЫКЛЮЧЕННЫМ** — его численный критерий
  (`fully_resolved_deterministically ≥ 90%` над `N ≥ 500`) тем более не
  проверялся; включать его отдельно от гейта 1, по тем же основаниям раздела
  8.4 (риск додумывать факты как «полностью решённые детерминированно» без
  достаточной статистики).
- **Честный `ai_used`.** `EnrichmentResult.failed()` раньше выставлял
  `ai_used=True` при провале вызова (сеть/валидация/провайдер упал) — ответ API
  читался как «ИИ поучаствовал» вместе с пустым `ai_explanation` и warning об
  ошибке. Теперь `ai_used` означает буквально «ИИ реально повлиял на результат»:
  `failed()` даёт `ai_used=False`. Факт неудачной попытки не теряется — заведено
  отдельное поле `ai_failed` (`EnrichmentResult`/`AIMeta`/`BuildUrlResponse.ai_failed`
  в `app/api/schemas.py`). `ai_used=False, ai_failed=False` теперь означает «ИИ
  не звали вовсе» (гейт сработал/выключен/нечего обогащать) — раньше это было
  неотличимо от «звали и упало».
- Тесты: `tests/ai/test_enrichment.py` (блок «Гейт 1 (Milestone AI-14)» —
  блокировка при пустых критериях, пропуск при poi/center/option_candidates/
  landmark, сохранность warnings, честные `ai_used`/`ai_failed` при ошибке
  провайдера). `tests/integration/test_ai_learning_loop.py`, сценарий 6
  («v1 Regression») скорректирован: чисто структурный запрос («двушка у метро
  Внуково, до 15 млн, с отделкой») теперь не вызывает ИИ вовсе
  (`ai_used=False`, число вызовов модели не растёт) — это и есть цель гейта 1,
  а не регрессия; счётчик вызовов модели в тесте раньше рос на каждый запрос
  просто потому, что гейт был выключен.

## Класс станций «любая станция линии» (Milestone AI-15)

Обобщение именованных ориентиров (промпт 23) на КЛАСС точек. Регрессия бага:
запрос «Нужна двушка рядом с МЦД не важно какой станции и округа, до 15 млн»
терял фрагмент «рядом с МЦД не важно какой станции» в `warnings` целиком — хотя
это не ограничение схемы pik.ru (как «сторона света», промпт 24), а обычная
задача сужения `complexes` по дистанции: пользователю подходит **любая**
станция указанной линии/класса, а не одна конкретная точка, как у ориентира.

- **Контракт** (`app/parsing/schema.py`): `StationClassRequirement` (`line_prefix`
  — `"МЦД"`/`"МЦК"` (любая линия класса), конкретная линия («МЦД-2») или
  `"метро"` — «любая станция метро вообще»; `raw` — исходный фрагмент;
  `max_distance_m` — верхняя граница расстояния, «у МЦД в 500 метрах»; парсинг
  реализован позже, см. ниже раздел «Дистанция для класса станций»,
  Milestone AI-19). Поле `Criteria.station_class_requirements`
  отражено в `to_public_dict()`.
- **Извлечение** (`app/parsing/rules/station_class.py`,
  `extract_station_class_requirements`, включено в `apply_rules`): маркер
  близости (тот же список форм, что у `landmark.py`, — «рядом с», «у», «около»,
  «недалеко от» и т.д.) + либо явное имя линии («МЦД», «МЦК», «МЦД-2»), либо
  явное указание «не важно» («любая станция метро», «метро не важно каким/какой
  станции», «у любого метро»). Хвост-уточнение «не важно какой станции» сразу
  после явной линии засчитывается «понятым» вместе с линией — это и было
  причиной исходного бага. **Негативный случай**: «у метро Аэропорт» (названа
  конкретная станция) этим правилом не перехватывается — при отсутствии и
  явного класса, и маркера «не важно»/«любой» правило не матчит вообще, и
  фраза остаётся на матчинге сущностей (`app.parsing.entity_match`), как и
  раньше.
- **Сужение `complexes` без похода в ИИ** (`app/geo/candidates.py`): станции
  берутся из `metro.json` — у `RefEntry` появилось поле `line` (напр. «МЦД-2»,
  «МЦК», «Сокольническая»; у пересадочных станций — несколько линий через
  « / », матчится по любой из них). `station_class_points(criteria)` —
  публичная функция, собирающая координаты всех станций, подходящих хотя бы
  под одно из требований (`"МЦД"` матчит по префиксу и «МЦД-1», и «МЦД-2» и
  т.д.; `"метро"` — вообще все станции с координатами, включая МЦД/МЦК, они
  физически часть карты метро). `build_candidate_shortlist` ранжирует
  кандидатов по расстоянию до БЛИЖАЙШЕЙ подходящей станции (haversine, чистая
  математика — как и для ориентиров); усечение до `SHORTLIST_LIMIT` идёт
  **после** сортировки. `resolve_known_facts`/`fully_resolved` считают ЖК
  совпадением, если он в радиусе хотя бы от одной станции класса; при
  одновременном landmark- и station-class-запросе приоритет — за ориентиром
  (более точная точка).
- **Радиус по умолчанию** — новая константа `STATION_CLASS_DEFAULT_RADIUS_M =
  1500` (метры). Сознательно меньше `LANDMARK_DEFAULT_RADIUS_M` (5 км,
  «районный» масштаб «рядом с ориентиром/центром»): здесь это пешая доступность
  до станции (~15–20 минут шагом), а не «где-то в том же районе». Как и другие
  калибруемые пороги проекта (семантический кэш, confidence промоушена) — это
  эвристика, требующая калибровки на реальных данных, а не точная величина.
- **Работает без ИИ и без учётных данных Claude.** По аналогии с
  landmark-веткой (Milestone AI-13, регрессия AI-12) в `enrich()`
  (`app/ai/enrichment.py`) заведена отдельная, всегда включённая ветка именно
  для `station_class_requirements` (не гейт 1/2 — та же чистая математика, что
  и у ориентиров) и добавлено обязательное исключение из условия гейта 1
  (Milestone AI-14): без него станция-класс-запросы схлопывались бы в `noop()`
  до этой ветки, регрессия того же паттерна, что и в баге AI-12. Если у станций
  подходящего класса вовсе нет координат (`metro.json` ещё не обогащён
  `lat`/`lon`/`line`) либо в радиусе не нашлось ни одного ЖК — выдаётся явный
  `warning`, а не тишина (инвариант «ничего не отбрасывается молча»).
- Тесты: `tests/parsing/test_rules.py` (распознавание класса линии/«любой
  станции», хвост «не важно какой» засчитан понятым, негативный тест «у метро
  Аэропорт», регрессия исходного бага на уровне `parse()`),
  `tests/geo/test_candidates.py` (матчинг по префиксу линии/пересадочным
  станциям, сортировка и жёсткая отсечка шорт-листа по дистанции, `warning`-
  прекурсоры через `fully_resolved`/`resolve_known_facts` при отсутствии
  координат), `tests/ai/test_enrichment.py` (гейт 1 пропускает
  station-class-only запрос, детерминированное сужение при выключенном ИИ,
  явные warning'и при отсутствии координат станций/ЖК/пустом радиусе).

## Номер линии не утекает в числовые правила (Milestone AI-16)

Побочный дефект, вскрытый живым прогоном сразу после AI-15: с появлением в
тексте токенов вида «МЦД-3» цифра линии стала попадать в числовые regex-правила
как самостоятельное значение. `«однушка у МЦД-3 до 12 млн»` давало
`price_min=3 000 000` — фильтр, которого пользователь не просил, и он молча
уезжал в URL (`priceFrom=3000000`). Причина — граница `\b` сразу после дефиса в
паттернах голого диапазона (`(NUM) sep (NUM) unit`): она срабатывает и когда
дефис приклеен к предыдущей букве (`д` + `-` + `3`).

- **Решение** — общий негативный lookbehind `_NOT_LINE_NUMBER = r"(?<![^\W\d_]-)"`
  в `app/parsing/rules/core.py`: число не матчится, если ему непосредственно
  предшествуют «буква + дефис» без пробела. Приём намеренно **общий, а не список
  «МЦД|МЦК»** — завтра появится МЦД-5 или другая линия, перечисление устареет.
  Применён точечно в позициях, где дефект воспроизводится, а не вшит в общий
  фрагмент `_NUM` (иначе задел бы законные случаи вроде «бюджет—15 млн»).
- **Тот же класс бага найден аудитом ещё в двух правилах** (искать надо было не
  только там, где заметили): `_AREA_RANGE` в `rules/area.py` («у МЦД-3 до 60
  метров») и `_ROOMS_NUM`/`_ROOMS_PLUS` в `rules/rooms.py` («у МЦД-2 комнатная
  квартира» ложно давало `Rooms.TWO`). Починены тем же приёмом.
- **`extract_floor` утечки не имеет** — проверено явно: паттерны этажа требуют
  ключевого слова вплотную к цифре («с/от/до/не выше»), голый `мцд-N` их
  структурно не удовлетворяет. Записано как результат проверки, а не пропуск.
- Регрессии закреплены тестами: «10-15 млн», «от 10 до 15 млн», «70-100 метров»,
  «кухня 8-12», «1-2 комнатные», «2-х комнатная», «2+»/«3+» продолжают
  разбираться как раньше; «мцд-3 трешка» по-прежнему даёт `THREE_PLUS`
  (словоформа, к цифре линии отношения не имеет). Тесты —
  `tests/parsing/test_rules.py`, включая end-to-end через `parse()`.

## Разговорные названия линий метро: цвета/номера/прозвища (Milestone AI-17)

Живой баг: «Нужна двушка в районе коричневой ветки» терял локационную часть
целиком в `warnings` и вдобавок зря уходил в ИИ (падал на 429), хотя механизм
класса станций (промпт/Milestone AI-15) уже полностью готов и у каждой станции
в `metro.json` проставлено поле `line` — не хватало только словаря разговорных
названий линий («коричневая» → «Кольцевая» и т.п.).

- **Где живёт словарь**: прямо в `app/parsing/rules/station_class.py` (не
  отдельный JSON и не отдельный модуль), по образцу `_UNSUPPORTED_CATALOG` в
  `rules/misc.py` — статическая лингвистическая конфигурация, тесно связанная
  с конкретной regex-логикой этого файла (приоритеты матчинга, границы слов,
  разрешение неоднозначностей), а не сущность со `slug`/`id`/`aliases`
  (`RefEntry`), которую обновляет `refresh`/`refresh_metro_geo`.
- **Извлечение — БЕЗ обязательного маркера близости** (в отличие от
  `_EXPLICIT_LINE_PATTERN`, где «рядом с»/«у» обязательны): защиту от ложных
  срабатываний («зелёный двор», «коричневый дом», «жёлтые окна», «квартира в
  зелёном районе») даёт обязательное слово-носитель «ветка»/«линия» рядом с
  цветом/номером (поддержаны оба порядка слов). Это же снимает исходный баг
  без необходимости заводить маркер «в районе» в общий список — «в районе
  коричневой ветки» матчится по слову-носителю «ветки», а не по марке
  близости. Прозвища кольца («кольцо»/«кольцевая»/«БКЛ»/«центральное кольцо»/
  «диаметры») сами по себе служат словом-носителем, доп. маркер не нужен
  («на кольце»).
- **Одно прозвище → несколько линий**: «жёлтая»/«восьмая» разговорно
  покрывают всю бывшую Калининско-Солнцевскую, которая в `metro.json`
  разложена на «Калининская» и «Солнцевская» (см. раздел «Гео-обогащение
  станций из OSM» выше). Решение — на один распознанный фрагмент добавляется
  по одному `StationClassRequirement` на каждую линию (семантика «ИЛИ» между
  несколькими требованиями уже реализована в `app.geo.candidates`, новых полей
  не потребовалось).
- **«Зелёная» vs «тёмно-зелёная»** (Замоскворецкая vs Троицкая) — реальный
  риск спутать, подстрока «зелёная» есть в обеих фразах. Решено порядком
  матчинга: составные цвета («тёмно-зелёная», «светло-зелёная» — синоним
  салатовой, Люблинско-Дмитровская) проверяются ПЕРВЫМИ, их спан регистрируется,
  и обычная «зелёная» пропускает любой пересекающийся фрагмент (`_overlaps`).
  Итог — точное сопоставление в обе стороны, а не додумывание; отдельный
  warning не понадобился, ambiguity снята самим порядком проверки.
- **«Голубая» vs «синяя»** (Филёвская vs Арбатско-Покровская) — разные стемы
  («голуб»/«син»), подстрочных пересечений нет, путаницы не возникает.
- **«Кольцо»/«кольцевая» vs МКАД/ЦКАД** — во избежание ложного матча на
  «кольцевая дорога»/«кольцевая автодорога» (частые синонимы МКАД/ЦКАД)
  добавлено исключение «не считать, если сразу после идёт (авто)дорога» —
  применено единообразно и к специфичным прозвищам Большой кольцевой/МЦК
  («большая кольцевая автодорога» тоже не матчится), и к общему паттерну.
  Остаточный риск (редкие бытовые упоминания колец-украшений) осознанно
  принят — в объявлениях о недвижимости такие фразы практически не
  встречаются, а более узкое сужение (обязательный маркер «на»/«по») вырезало
  бы законные «рядом с кольцом», «у кольца».
- **Бутовская и МЦК** намеренно не получили цветовых прозвищ — в разговорной
  речи цветом почти не называются, выдумывать не стали.
- **Числовые формы линий («2-я ветка») не реализованы** — только словесные
  порядковые числительные («вторая», «пятая» и т.д.), как и было запрошено;
  задокументировано как известное ограничение в docstring модуля.
- Тесты: `tests/parsing/test_rules.py` (табличные тесты на цвета/номера/
  прозвища со склонениями, «жёлтая»/«восьмая» → обе линии, негативные тесты
  на слово без носителя и на МКАД/ЦКАД, e2e-регрессия исходного бага через
  `parse()`), `tests/geo/test_candidates.py` (несколько
  `station_class_requirements` трактуются как ИЛИ на уровне
  `station_class_points`).
- **Живой прогон** (2026-07-23) подтвердил конец-в-конец `parse` → `enrich`
  (`pool=None`) → `build_url` без обращения к ИИ (`ai_used=False`,
  `ai_failed=False`) для всех трёх контрольных запросов. «Однушка у жёлтой
  ветки» дал `blocks=1108,378,1580` (3 ЖК, warnings пустые) — механизм
  сужения работает end-to-end. «В районе коричневой ветки» и «на кольце»
  корректно распознали `line_prefix="Кольцевая"`, но выдали честный warning
  «подходящих ЖК не найдено» вместо `blocks=` — это не баг кода, а факт
  данных: ближайший ЖК в `complexes.json` (набор новостроек ПИК, в основном
  на периферии) находится в 2.5 км от ближайшей станции Кольцевой линии,
  что превышает `STATION_CLASS_DEFAULT_RADIUS_M` (1500 м). Инвариант «ничего
  не отбрасывается молча» соблюдён — выдаётся явный warning, а не тишина.
  Продолжение этой находки — следующий раздел (Milestone AI-18).

## Фолбэк на ближайшие ЖК для класса станций (Milestone AI-18)

Продолжение находки предыдущего раздела: пустая выдача для «в районе
коричневой ветки»/«на кольце» формально верна (инвариант «ничего не теряется
молча» соблюдён — есть warning), но бесполезна пользователю, который просил
«в районе» — сайт вполне может показать ближайшие варианты. Осмысленная
деградация вместо пустого результата, **без вранья о фактическом расстоянии**.

- **`app/geo/candidates.station_class_nearest_fallback`** — если в радиусе
  по умолчанию (`STATION_CLASS_DEFAULT_RADIUS_M`) не нашлось ни одного ЖК,
  возвращает `STATION_CLASS_FALLBACK_LIMIT` (8) ближайших ЖК вместо пустого
  списка. N=8 — компромисс: достаточно, чтобы пользователь мог дальше сам
  отфильтровать по цене/комнатности, но не настолько много, чтобы под видом
  «ближайших» подсунуть половину каталога ПИК без всякой связи с запрошенной
  линией. Как и другие калибруемые пороги проекта — эвристика, не точная
  величина. Усечение до лимита — **после** сортировки по дистанции (как и
  весь остальной ранжирующий код модуля), реальное расстояние до ближайшего
  берётся из фактического `haversine`-расчёта, а не шаблонного текста.
- **Жёсткая граница: фолбэк только при ДЕФОЛТНОМ радиусе.** Если пользователь
  указал дистанцию явно (`StationClassRequirement.max_distance_m` задан хотя
  бы у одного требования — «у МЦД в 500 метрах») — это жёсткая отсечка
  пользователя, а не «примерно рядом»: `station_class_nearest_fallback`
  возвращает `([], None)`, пустой результат с прежним warning остаётся
  правильным ответом. Та же функция возвращает `([], None)`, если у станций
  подходящего класса вовсе нет координат — эта ситуация обслуживается более
  ранней (уже существующей) веткой `enrich()` и не маскируется фолбэком.
- **Ориентиры (`landmark_requirements`) фолбэк НЕ получили** — сознательно:
  там своя семантика (единственная точка, не класс) и свой радиус
  (`LANDMARK_DEFAULT_RADIUS_M`, 5 км — «районный» масштаб, в разы больше
  `STATION_CLASS_DEFAULT_RADIUS_M`), пустая выдача там менее вероятна и не
  наблюдалась живым прогоном. Открытый вопрос на будущее, не реализовано.
- **Формат warning** (пример реального прогона): `"в радиусе 1.5 км от
  станций класса «Кольцевая» ЖК нет; показаны ближайшие — от 2.51 км"` —
  число километров берётся из фактического расчёта расстояния до ближайшего
  кандидата, не из шаблона.
- **Живой прогон** (2026-07-23) подтвердил исправление: «двушка в районе
  коричневой ветки» и «квартира на кольце до 20 млн» теперь отдают `blocks=`
  с 8 ближайшими ЖК (Первый Дубровский и др., ~2.51 км от Кольцевой линии) и
  явным warning о деградации, без обращения к ИИ (`ai_used=False`). «Однушка
  рядом с МЦД» (запрос, где радиус и так находил ЖК) не изменилась — 15 ЖК в
  `blocks=`, warnings пустые, как и до этой правки.
- Тесты: `tests/geo/test_candidates.py` (фолбэк отдаёт N ближайших
  отсортированными с warning о фактическом расстоянии; усечение до лимита
  после сортировки на >N кандидатах; фолбэк не запускается, когда в радиусе
  уже есть матч; жёсткая отсечка явной дистанции отключает фолбэк; отсутствие
  координат станций фолбэк не маскирует), `tests/ai/test_enrichment.py`
  (`enrich()` вызывает фолбэк только когда `matched_complex_ids` пуст и
  использует его исход для `matched_complex_ids`/warning).

## Дистанция для класса станций — «предохранитель без провода» (Milestone AI-19)

Живой баг: «квартира у МЦД в 500 метрах» терял «в 500 метрах» в `warnings` как
нераспознанный текст и сужал выдачу по дефолтному радиусу 1500 м (все 15 ЖК)
вместо заданных пользователем 500. Причина — `StationClassRequirement.
max_distance_m` было объявлено в `schema.py` и УЖЕ корректно учитывалось в
`app/geo/candidates.py` (жёсткая отсечка, отключение фолбэка AI-18), но
`app/parsing/rules/station_class.py` никогда его не заполнял — тот же класс
дефекта, что уже разбирался у `POIRequirement.max_distance_m` (см. выше,
«Аудит тихих потерь в regex-правилах»): предохранитель подключён к проводу,
который никуда не идёт.

- **Общий фрагмент дистанции вынесен в `app/parsing/rules/core.py`**
  (`_DIST_MARKER`, `_DIST_UNIT`, `_DIST_NUM`, `_parse_distance_meters`) —
  переиспользован и в `poi.py` (группа `dist`/`dist_unit` в `_DISTANCE`, ранее
  собственный локальный regex только на целые метры), и в `station_class.py`.
  Один диалект вместо двух: числовая часть + единица (метры/километры,
  дробные километры — «1.5 км», «1,5 км») и перевод в метры общие; расстановка
  маркера близости и его позиция относительно текста-носителя (POI-категория
  vs линия/класс станций) — забота конкретного модуля, там разный контекст.
  Побочный эффект рефакторинга: POI теперь тоже понимает километры («школа в
  1.5 км»), раньше поддерживались только метры — расширение возможностей, не
  регрессия (старые формулировки продолжают работать один в один).
- **Два порядка слов** в `station_class.py`: «после» — маркер + линия +
  дистанция («у МЦД в 500 метрах», «рядом с МЦД не дальше 800 м», «у
  коричневой ветки в 1 км») — общий суффикс `_DISTANCE_AFTER`, приклеенный
  РОВНО один раз к каждому уже существующему паттерну линии (явная линия,
  «любая станция», цвета/номера/прозвища) — вне альтернации порядка слов
  внутри паттерна, иначе именованные группы `dist`/`dist_unit` задвоились бы
  в одном regex (Python re такое запрещает); «до» — дистанция + предлог «от» +
  линия («в пределах 700 метров от МЦД-3») — отдельный паттерн
  `_DISTANCE_BEFORE_EXPLICIT_LINE_PATTERN`, структура принципиально другая
  (нет маркера близости `_MARKER` перед числом, объект вводится предлогом
  «от», а не «у»/«рядом с»).
- **«В пешей доступности» (без числа) — сознательно НЕ константа.** Фраза
  консьюмится (не остаётся в `warnings`), но `max_distance_m` не заполняется:
  это МЯГКОЕ пожелание, а не жёсткая пользовательская отсечка, и уже
  покрывается дефолтным поведением (`STATION_CLASS_DEFAULT_RADIUS_M` — тот же
  порядок величины, «пешая доступность до станции»). Если бы фраза заполняла
  `max_distance_m`, это сломало бы фолбэк на ближайшие ЖК (Milestone AI-18):
  фолбэк отключается только при явной дистанции, а «в пешей доступности» —
  это и есть случай, для которого фолбэк придуман.
- **Разведение «метров площади» и «метров радиуса»** (самый опасный случай
  ложных срабатываний — обе величины меряются в метрах): синтаксис отличается.
  Радиус требует маркер вплотную к линии («в 500 метрах», «не дальше 500 м»,
  «в пределах 700 метров от ...») — маркер `_DIST_MARKER` НЕ включает «от» как
  триггер после линии, поэтому «у МЦД от 60 метров» (площадь, `area.py._AREA_
  MIN`, ключевое слово «от» само по себе) распознаванием дистанции не
  перехватывается: марker-группа в `_DISTANCE_AFTER` пытается сопоставить
  «от», не находит его среди своих альтернатив, а без маркера следующий
  символ должен быть сразу цифрой — «от» цифрой не является, весь необязательный
  суффикс матчится пустым фрагментом. Симметрично цена («до 15 млн») не
  распознаётся дистанцией — единица «млн» не входит в `_DIST_UNIT`
  (метры/километры). Проверено обоими направлениями и живым прогоном.
- **Этаж не задет**: `_DISTANCE_AFTER` не матчит «на 5 этаже» (маркер «на» не
  входит в альтернативы `_DIST_MARKER`, следующий символ не цифра) — линия
  «съедает» только «у МЦД-3», хвост остаётся для `floor.py` (у которого
  отдельное, не связанное с этой правкой, известное ограничение — голое «на N
  этаже» без ключевого слова диапазона/границы вообще не разбирается; не
  чинилось, вне рамок этой задачи).
- **Живой прогон** (2026-07-23) `parse` → `enrich(pool=None)` → `build_url`,
  провода `merge_enrichment`: «квартира у МЦД в 500 метрах» → жёсткая отсечка,
  `blocks=1692` (1 ЖК вместо 15 дефолтных), `warnings=[]`, `ai_used=False`;
  «однушка у МЦД от 60 метров» → `areaFrom=60.0`, дистанция НЕ распознана
  (`max_distance_m=None`), станция класса сузила по дефолтному радиусу до тех
  же 15 ЖК, что и без дистанции; «двушка у МЦД до 15 млн» → `priceFrom=0&
  priceTo=15000000`, дистанция снова не распознана, те же 15 ЖК; «однушка
  рядом с МЦД» (регрессия) — без изменений, 15 ЖК, `warnings=[]`. Ни один из
  четырёх запросов не вызвал ИИ.
- Тесты: `tests/parsing/test_rules.py` (табличный тест на все формулировки из
  докстринга выше, «в пешей доступности» консьюмится без `max_distance_m`,
  e2e-регрессия исходного бага через `parse()`, три негативных теста —

## Системная починка вместо симптомов (Milestone AI-20)

Поводом стал живой запрос «Нужна двушка c новым детсадом недалеко от метро
Коммунарка»: мусорные warnings («c», «недалеко от метро»), лишний район
«Коммунарка» в criteria, двойное падение ИИ в 429 и — главное — ссылка с
фильтром по станции, которой **нет в фильтрах pik.ru**. Вместо точечных фиксов
проведена диагностика четырьмя параллельными аудитами; найдены и закрыты
ЧЕТЫРЕ корневые причины, каждая порождала целый класс «новых» багов.

### 1. Замкнутый контур проверки (его не существовало)

- `tests/corpus/queries.txt` — 197 разнородных запросов (все виды фильтров,
  сленг, опечатки, гомоглифы, противоречия, «вода»); `scripts/parse_audit.py` —
  офлайн-харнесс: `parse` → `build_url` без сети/ИИ, группирует дефекты в
  классы с частотами, пишет `graphify-out/parse_audit.json` (флаги `--limit`,
  `--only-warnings`, `--json-out`, `--quiet`; падение parse — класс `CRASH`,
  прогон не рушит).
- `tests/test_parse_audit_regression.py` — корпус гоняется В КАЖДОМ `pytest` с
  порогами «не хуже» (crashes=0, empty≤35, no-filter-URL≤66, coverage≥0.86).
  Ухудшение целостности разбора теперь роняет тесты раньше, чем его найдёт
  живой пользователь. Пороги ужесточать по мере улучшений; ослаблять — только
  с обоснованием. Замер до/после AI-20: пустые criteria 37→32, URL без

  законные кейсы: station-class/landmark сужение делает `enrich()`, которого
  офлайн-аудит намеренно не зовёт; болтовня; неподдерживаемые фильтры).

### 2. Слой парсинга: классы, не экземпляры

- **Гомоглифы латиница→кириллица** (`LATIN_TO_CYRILLIC_CONFUSABLES` в
  `app/reference/loader.py`): «квaртира с oтделкой» с подменёнными буквами
  раньше давала ПУСТЫЕ criteria и голый URL (5 из 6 стресс-запросов класса
  проваливались целиком). Таблица применяется в обоих местах нормализации —
  `loader.normalize` (сущности) и `rules/core._normalize` (правила; инвариант
  «длина строки не меняется» сохранён, гомоглифы 1:1).
- **Единый маркер близости** `_PROXIMITY_MARKER` (`rules/core.py`): раньше ТРИ
  независимых неполных списка одной семантики (TRIGGERS в `entity_match`, где
  не было «недалеко от»; `_MARKER` в `landmark.py`; SUFFIX в `poi.py`, где не
  было «недалеко»). Теперь один источник; TRIGGERS собраны из него, добавлен
  голый триггер «метро » (симметрично «район »/«жк »), `get_trigger_type`
  нормализует вход (гомоглиф «мeтро» не ломает триггер, индексы валидны).
  POI-SUFFIX получил негативные lookahead-ы: «детсадом недалеко от метро X» не
  ворует «недалеко» у следующей конструкции (иначе маркер метро разрывался).
- **Одноимённые сущности разных типов** («Коммунарка» = метро И район):
  раньше обе добавлялись молча (ambiguity-warning был завязан на разные
  `entry.name`). Теперь типоспецифичный триггер контекста («у метро …»,
  «в районе …» или единственное слово-носитель в окне) однозначно выбирает
  тип; без триггера — лучший по score тип + явный warning о неоднозначности.
- **Геохвосты не идут в ИИ**: `_looks_like_option` отбрасывает фрагменты
  целиком из маркеров близости/слов-носителей («недалеко от метро») — раньше
  КАЖДЫЙ такой хвост порождал паразитный вызов `resolve_options` (и 429).
  Однобуквенные огрызки-гомоглифы («c») больше не «значимы» в warnings.
- **Warning «не имеет id, в ссылку не попадет» подавляется** для сущностей,
  которые берёт на себя geo-фолбэк (см. ниже): текст стал бы враньём, исход
  фолбэка сообщает своя заметка через validator
  (`location_fallback.handled_by_fallback`).

### 3. Честность локационных фильтров (аудит validate, живые замеры curl)

- **Факт: `api.pik.ru/v2/filter` ИГНОРИРУЕТ `metroStations`/
  `districtLocations`/`districtCounties`** — baseline, реальный GUID и
  `deadbeef` дают побайтово одинаковый count. Реально проверяется только
  `blocks` (`blocks=999999` → 0). Значит result_count при локационном фильтре
  отражал только комнатность/цену и выдавался за полноценную проверку.
  `validate()` теперь честен: warning «result_count не учитывает фильтр по
  метро/округу/району…» + структурное поле
  `ValidationResult.location_filters_not_verified`.
- **5 доказанно фейковых GUID вычищены из `metro.json`** (записи сохранены —
  имя/алиасы/координаты нужны гео-механике): «Коммунарка»
  `c1d2e3f4-…` (hex-лесенка), «Одинцово» `a1b2c3d4-…`, «Баковка» `b1c2d3e4-…`
  (одна серия), «Варшавская» `guid-varshavskaya`, «Сокол» `guid-sokol`.
  Реестр — `app/pik/id_trust.py` (`REMOVED_SYNTHETIC_METRO_IDS`); подозрительная
  пара Митино/Мякинино (различаются последним символом, формат выпадает из
  общего UUIDv6-семейства) в JSON оставлена, но в URL как штатный
  `metroStations` не подставляется (`is_verified_metro_id`). Снимок
  `KNOWN_METRO_GUIDS` в `test_metro_integrity.py` сохранён как документ эпохи,
  но ассерты исключают вычищенный реестр (раньше тест ЗАЩИЩАЛ фейки) + новый
  тест «фейки не вернулись».
- **Geo-фолбэк на `blocks`** (`app/pik/location_fallback.py`) — сущности без
  достоверного id не выпадают молча и не тащат фейк: (1) точный тег-матч по
  привязке ЖК (`block_ids_by_tag`), (2) для метро с координатами — сужение по
  расстоянию (`nearby_block_ids`, радиус `STATION_CLASS_DEFAULT_RADIUS_M`,
  фолбэк на N ближайших как в AI-18), (3) иначе — явный warning «фильтр
  пропущен». Встроен И в `build_url`, И в `validate` — result_count проверяет
  ровно то сужение, что получит пользователь. Живой прогон: «двушка недалеко
  от метро Коммунарка» → `blocks=` 8 ближайших ЖК + честный count 628 (вместо
  прежних 2634 «всех двушек») + warning «id не подтверждён, в радиусе 1.5 км
  ЖК нет — показаны 8 ближайших, от 3.06 км».
- Из 183 локационных id живыми данными подтверждаются только 72 (все — ЖК);
  111 id метро/районов/округов не подтверждаемы, пока front-API закрыт Qrator
  (наши id округов расходятся со ВСЕМИ живыми `locations.child.id`). Это

### 4. ИИ-слой: устойчивость и данные вместо надежды

- **Ретраи с экспоненциальным backoff** (`app/ai/client.py`,
  `_execute_with_retry`): `AI_RETRY_MAX_ATTEMPTS`=3, base 0.5s × 2^n + джиттер,

## Имена линий метро + регрессия гейта 2 (Milestone AI-21)

Живой баг: «Нужна двушка в районе Троицкой ветки» давал округ «Троицкий АО»

## Транспорт Claude — Claude Agent SDK поверх локального CLI (Milestone AI-22)

Провайдер `claude` (`app/ai/client.py`) переведён с прямого HTTP к Anthropic
Messages API (класс `AsyncAnthropic` + сырой OAuth-токен в заголовках) на
**Claude Agent SDK** (`claude-agent-sdk`, `query()` + `ClaudeAgentOptions`) —
по образцу соседнего проекта `workflow-ai`
(`backend/app/orchestrator/claude_agents.py`). Мотив пользователя: там ему
нравится, как организовано локальное подключение Claude. Перенесён **только
механизм подключения**; канбан/dev→QA-петля/cost-трекинг/usage-probe из
workflow-ai сознательно НЕ переносились.

- **Как теперь вызывается** (`call_claude`): SDK сам запускает установленный
  Claude Code CLI (`claude`, проверено на v2.1.218) и берёт авторизацию из
  логина Claude Code — ручной OAuth-заголовок (`anthropic-beta:
  oauth-2025-04-20`) и самописное чтение keychain для передачи токена больше
  не нужны. Один ход, без тул-лупа (`tools=[]`, `allowed_tools=[]`),
  `setting_sources=[]` (CLAUDE.md/настройки хоста не подгружаются). Структурный
  ответ — нативно: `output_format={"type":"json_schema","schema":
  answer_model.model_json_schema()}` → `ResultMessage.structured_output`, с
  текстовым фолбэком из `ResultMessage.result` (на случай CLI без поддержки
  `output_format`). Чтение стрима обёрнуто в `contextlib.aclosing` —
  обязательно: выходим по первому `ResultMessage` через `return`, и без явного
  закрытия недоеденный async-генератор SDK добивается GC на живом event loop
  (`RuntimeError: aclose(): asynchronous generator is already running` + риск
  утечки дочернего процесса CLI). Проверено живым прогоном: до фикса ошибка
  была, после — чисто.
- **Авторизация и квота — источник кредов из `_claude_sdk_env(settings)`:**
  `ANTHROPIC_API_KEY` (своя квота, единственный вариант гарантированно без 429
  под нагрузкой) → иначе `CLAUDE_OAUTH_TOKEN` (токен `claude setup-token`)
  прокидывается в env CLI как `CLAUDE_CODE_OAUTH_TOKEN` → иначе (пусто) на
  macOS SDK/CLI берёт keychain-логин сам. Разбор находки (форк-агент по
  workflow-ai): там 429 не выскакивает, потому что ходят **не** живым
  keychain-токеном сессии, а отдельным `setup-token`
  (`CLAUDE_SANDBOX_OAUTH_TOKEN`) — эту же логику воспроизводит наш приоритет
  `CLAUDE_OAUTH_TOKEN`→`CLAUDE_CODE_OAUTH_TOKEN`. **Важно:** это снижает
  конкуренцию за квоту, но `setup-token` привязан к той же подписке — «сделать
  как в workflow-ai» **не** равно «фикс 429». Гарантированно без 429 под
  нагрузкой — только `ANTHROPIC_API_KEY`.
- **Гейт «настроен ли ИИ»** (`app/ai/enrichment.py`): `resolve_claude_credentials`
  заменён на лёгкий `claude_credentials_available(settings) -> bool` (API-ключ
  задан ИЛИ читается OAuth-логин). Смысл прежний: провайдер `claude` без
  логина/ключа → ИИ тихо выключается, детерминированный пайплайн работает.
  Keychain-probe оставлен ТОЛЬКО как дешёвый признак «залогинен», не для
  передачи токена (её делает CLI).
- **Ретраи/circuit breaker сохранены** без изменений (`_execute_with_retry`).
  Новый предикат транзиентности `_is_transient_claude_sdk`: инфраструктурные
  сбои CLI (`CLIConnectionError`/`ProcessError`/`CLIJSONDecodeError` и оборванный
  стрим `ClaudeStreamError`) и ошибочный результат с HTTP-кодом 429/5xx
  (`ResultMessage.api_error_status`) либо текст-маркером → транзиент;
  `CLINotFoundError` (нет CLI) и брак валидации ответа → фатал, не ретраим.
  Ошибочный результат поднимается как `ClaudeSDKCallError(detail, status)`.
- **Конфиг** (`app/config.py`): добавлены `CLAUDE_CLI_PATH` (пусто =
  авто-дискавери SDK) и `CLAUDE_MAX_TURNS` (=4, cost-guard). `AI_MODEL_NAME`
  теперь для claude уходит в `ClaudeAgentOptions.model`. `ANTHROPIC_API_KEY`/
  `CLAUDE_OAUTH_TOKEN` сохранены.
- **Зависимости** (`pyproject.toml`): `anthropic` удалён (после перехода не
  импортируется), добавлен `claude-agent-sdk>=0.2.100` (живьём встал 0.2.126).
- **Тесты** (`tests/ai/test_client.py`): переписаны под SDK — вместо патча
  `_get_claude_client`/anthropic-ошибок патчится `app.ai.client.query`

## Ослабление гейтов: детерминированные добивки + экстрактор свободного текста

Контекст: 429 на общей OAuth-квоте решён отдельным ключом — **главная причина
жёсткости гейта 1 отпала**. QA (`parse_audit`) показал 32 пустых критерия / 64 URL
без фильтров / покрытие 88.6%: всё, что regex не поймал, молча уходило в warnings,
структурных сигналов нет → гейт 1 = `noop()`, Claude запрос не видел. Нераспознанное
разложили на три ведра (A — опечатки/синонимы, чинятся детерминированно; B — не
поддерживается pik.ru, в ИИ слать нельзя; C — сложный контекст, тут открыть гейт).
Решение пользователя: оба ведра фазами, механизм — ослабить гейт и дать судить Claude.

- **Фаза 1 (ведро A, без ИИ).** Мелкие низкорисковые правки правил парсера с анти-
  регрессиями: `падешевле/падороже`→sort (опечатка о→а, `misc.py`); `трёха/трёху`→
  three_plus (`rooms.py`, `\bтрех[ауи]\b` — защита от числительного «трёх» и
  «трёхкомнатн»); альтернация `1 либо 2` (`rooms.py`); `с отделкай`→finish
  (`finish.py`, `с отделк\w+`); `кухня ат N`→kitchen (`area.py`, опечатка ат→от,
  скоуп только кухня); позитивный `первый этаж`→floor=1 + постфиксное `первый этаж
  не предлагать`→not_first (`floor.py`, защита `первый взнос`); алиас `своя ванная`
  (`option_groups.json`). Итог: **32→28 / 64→60 / 0.886→0.906**; пороги регрессии
  ужесточены (empty≤31, no-filter≤63, coverage≥0.89). Тесты —
  `tests/parsing/test_rules_typo_tolerance.py`.

- **Фаза 2 (ведро C, ослабление гейтов).** Новая способность — `resolve_free_text_
  criteria` (`enrichment.py`): отдельная ветка ДО гейта 1, по шаблону
  `resolve_options`. Восстанавливает реальный остаток из warning'ов «не удалось
  распознать» (`_residual_fragments`; ведро B с текстом «не поддерживается pik.ru» в
  остаток НЕ попадает — вызов не жжётся), шлёт текст+фрагменты в модель
  (`FREE_TEXT_SYSTEM_PROMPT` → `FreeTextCriteriaAnswer` через
  `call_free_text_extractor`). Модель заполняет **только пустые СКАЛЯРНЫЕ** поля
  Criteria (rooms/price/area/floor+флаги/sort/housing_type/ready/settlement_year/
  only_available); метро/районы/ЖК/опции не трогает. Инварианты: детерминированное
  выигрывает (пишем лишь `None`-поля); невалидное отбрасывает `validate_assignment`;
  `ai_used`/`criteria_changed_by_ai` честно True даже при `noop()`/`from_deterministic`
  ниже. `ai_call_log` переиспользует `ai_called`/`criteria_changed_by_ai` (без миграции
  БД). Тесты — `tests/ai/test_free_text_enrichment.py`. Полный прогон: **648 зелёных,
  ruff чист.** Живой E2E (Swagger `POST /build-url`) — за пользователем.

- **Осознанные компромиссы:** (1) шум/приветствия («привет, помогите») попадают в
  экстрактор и жгут пустой вызов — принято по выбору «пусть судит Claude», модель
  возвращает пусто, вреда нет; (2) POI/center-гейты и guard vacuous-truth (AI-21)
  оставлены жёсткими — ослабление гейта 1 идёт ТОЛЬКО через новую ветку, чтобы не
  вернуть слив полкаталога в `blocks`.

## Системная устойчивость парсера (6 классов ошибок из живого запроса)

Один живой запрос («большая квартира… до 18 минут школы и сады… метро в доступности
15 минут… раздельные санузлы… внутри МКАД кольца») вскрыл 6 разных классов проблем.
Чинили не под запрос, а по классам — общими механизмами.

- **A. Ложные срабатывания дорог vs метро-кольцо.** `station_class._NOT_ROAD_TAIL` —
  lookahead только ВПЕРЁД на «дорога» после «кольцо»; «МКАД кольца» проскакивало (дорога
  ПЕРЕД словом, «МКАД» не в списке). Добавлен `_is_road_context` — блок-лист дорог
  (МКАД/ЦКАД/ТТК/садов/бульварн/транспортн/шоссе/трасс/автодорог) по ОБЕ стороны матча.
- **B. Время до метро.** `timeOnFoot` — реальный URL-фильтр, но идиома «(в пешей/шаговой)
  доступности N минут» не покрывалась (жёсткий лимит на один предлог между «метро» и
  числом). Добавлены `_ACCESS`-паттерны в `rules/time.py`.
- **C. Дистанция в минутах.** `_DIST_UNIT` (`core.py`) знал только метры/км. Добавлена
  единица «минут» с переводом `WALK_METERS_PER_MINUTE`≈80 (общая для poi/landmark/
  station-class) + маркер «до». Для POI — `_LEADING_DISTANCE`: дистанция ДО категорий
  («до 18 минут … школы и сады») применяется ко всем POI без своей суффиксной дистанции;
  сегменты с «метро/станц» пропускаются (это время до метро, а не дистанция). POI-
  дистанция — гео-сужение шорт-листа, не URL-фильтр.
- **D. Раздельные санузлы.** Семантически раздельный (планировка одного санузла) ≠
  manybathrooms (количество). Каталог `_UNSUPPORTED_CATALOG` сужен до ЕД. ч.; разговорное
  МН. ч. «раздельные санузлы» → alias `manybathrooms` в `option_groups.json` (продуктовое
  решение пользователя: мн. ч. = «их несколько»). Ед. ч. остаётся честным warning.
- **E. «Внутри/за МКАД».** У pik.ru фильтра границы МКАД НЕТ → гео-сужение по `blocks`.
  Новое: `Criteria.within_mkad`, правило `extract_within_mkad`, `app/geo/mkad.py`
  (`point_in_mkad`, ray-casting над `mkad_ring.json`), `complexes_in_mkad` в `candidates`,
  врезка в `resolve_fallback_block_ids` (пересечение с др. локациями = AND). Полигон —
  документированное **приближение** (эллипс по bbox кольца): Overpass в среде разработки
  был недоступен (400/406/таймауты), точный контур пересобирается `refresh_mkad.py`, когда
  доступно full-planet зеркало. Заметки честно помечают «приближение».
- **F. ИИ-страховка.** `time_on_foot/time_on_transport` добавлены в поля
  `FreeTextCriteriaAnswer`/`_FREE_TEXT_SCALAR_FIELDS`: пропущенную детерминикой идиому
  подхватит ИИ (детерминированное по-прежнему выигрывает).
- **⑥ (заметка).** pik API 500 на `rooms=3` — best-effort валидатор, поймано. Проверка
  сериализации `three_plus` (не теряет ли комнаты 4+) — отдельная задача.

Полный прогон: **679 тестов зелёные, ruff чист.** Репро исходного запроса офлайн:
`time_on_foot=15`, `option_groups=[manybathrooms]`, `within_mkad=True` (без ложной
Кольцевой), POI-дистанция 1440 м у школ/садов, `blocks`-сужение по МКАД. Живой E2E —
за пользователем (плюс регенерация точного полигона МКАД при доступном Overpass).

## Milestone AI-22 — ориентиры в ИИ-экстракторе и суперлатив «самая ближайшая»

**Повод — живой прогон:** `хочу двушку самую ближайшую к Политеху, с раздельными
санузлами` → URL `search/two-room?optionGroups=manybathrooms`, warning «самую ближайшую
к Политеху: не удалось распознать», `ai_used=false`, `ai_failed=false`.

**Разбор (важно, потому что гипотеза «ИИ не позвали» была неверна).** ИИ вызывался, и
даже дважды: остаток в warning'ах был, `resolve_free_text_criteria` прошла свой вход,
провайдер `claude` с `CLAUDE_OAUTH_TOKEN` был доступен. Модель не сделала ничего по двум
причинам сразу: (1) `FREE_TEXT_SYSTEM_PROMPT` прямым текстом запрещал извлекать «названия
ориентиров», а `_apply_free_text_answer` умел писать только скаляры; (2) в
`landmarks.json` не было «Политеха» вообще. Гейты 1/2 при этом ни при чём — они до
ветки не доходили. Вывод, зафиксированный в CLAUDE.md: вопрос был не «когда зовём ИИ», а
«что ему разрешено» и «что есть в справочнике». Идея «перепроверять ИИ каждый запрос»
отклонена: ничего бы не починила, а инвариант «детерминированное всегда выигрывает»
сломала бы (модель начала бы переписывать корректно разобранное).

**Сделано:**
- **A. Справочник.** Запись `mospolytech` («Московский политех», aliases `политех`,
  `мосполитех`, …). Координаты — OSM way 1218498180 (`addr:street=Большая Семёновская
  улица`, `housenumber=38`), зеркало `maps.mail.ru`, как в `refresh_metro_geo`. Ловушка:
  у отношения вуза (`relation 2018405`) центроид `55.7802, 37.6628` — кампусы разбросаны,
  и центр указывает в район Садовой-Спасской, то есть не туда.
- **B. Ориентиры в экстракторе (ведро C).** `LandmarkMatch` + поле `landmarks` в
  `FreeTextCriteriaAnswer`; каталог `name`/`slug` уходит модели в `build_free_text_context`
  (ровно как каталог опций); `sanitize_landmark_resolution` валидирует slug против
  `landmarks.json` и **сам подставляет координаты** — у модели их не просят и не
  принимают (инвариант «LLM не считает дистанции»). Пишем только в пустой
  `landmark_requirements`.
- **C. Суперлатив.** Оказалось, регекс уже ловил «самую ближайшую к X» (маркер
  `ближайш\w+\s+к`, зелёный тест с 2024-х пор) — не хватало другого: факт суперлатива
  никуда не сохранялся, и запрос деградировал до обычного «рядом» (радиус 5 км).
  Добавлены `LandmarkRequirement.nearest_only`, `landmark_nearest_ids` и
  `LANDMARK_NEAREST_LIMIT=3`; радиус для суперлатива не применяется вовсе, явная
  `max_distance_m` остаётся жёсткой отсечкой. `_SUPERLATIVE_PREFIX` втягивает «самую» в
  consumed-span (иначе слово оседало ложным warning'ом) и ловит «ближе всего к», где
  маркером работает голое «к». Окончания перечислены явно: открытый стем `сам\w+` цеплял
  бы «самолёта у аэропорта».

- **D. Фолбэк «рядом с X» при пустом радиусе.** Отдельный от суперлатива случай:
  пользователь просил именно «рядом», радиус применён и дал пусто. Раньше ветка отвечала
  тишиной с warning'ом «не найдено» — формально верно, бесполезно на практике; у станций
  класса это же лечилось фолбэком ещё в AI-18. Добавлен `landmark_nearest_fallback` +
  `LANDMARK_FALLBACK_LIMIT=8`, общий с суперлативом хелпер `_landmark_distances`. Явная
  `max_distance_m` фолбэк выключает — жёсткая отсечка сильнее эвристики (симметрия с
  инвариантом 16). Тест `test_enrich_landmark_warns_when_nothing_nearby` переименован в
  `test_enrich_landmark_falls_back_to_nearest` и переписан под новое поведение; на старый
  контракт (пусто + «не найдено») заведён отдельный тест с явной дистанцией.

- **E. Правки по код-ревью диффа.** Ревью субагентом нашло 7 дефектов, все закрыты
  тестами:
  1. Warning отбитого санитайзером ориентира снимался, если модель заодно угадала любое
     другое поле (`changed=True` снимал ВСЕ `consumed_fragments`) — фраза «рядом с
     Атлантидой» исчезала молча. Теперь фразы отклонённых ориентиров исключены из снятия.
  2. `sanitize_landmark_resolution` не проверял `phrase` против переданных фрагментов:
     реальный slug на произвольной фразе проходил насквозь и на любом шуме в остатке
     сузил бы выдачу по случайному ориентиру. Проверка добавлена; мёртвое поле
     `LandmarkMatch.confidence` убрано.
  3. ИИ-путь всегда ставил `nearest_only=False` — суперлатив терялся ровно там, где
     детерминика промахнулась (склонения ниже `SCORE_THRESHOLD`: «бауманке» → QRatio
     87.5). Добавлен `has_superlative_cue(text)` с guard'ом на «в ближайшее время».
  4. `max_distance_m` у ориентира не заполнялся НИГДЕ — «предохранитель без провода»
     (тот же класс, что AI-19 у станций): guard в фолбэке был недостижим, а «рядом с МГУ
     не дальше 1 км» возвращало ЖК на 4.4 км. Добавлен `_DISTANCE_SUFFIX` с суженным
     маркером (без «до» и без бесмаркерной формы — иначе «площадью до 45 метров» уводило
     бы площадь в дистанцию).
  5. «рядом с политехом» (творительный падеж) не матчилось: QRatio 87.5 против порога 88.
     Закрыто алиасами, не понижением порога — в этом проекте склонения лечатся лексикой.
  6. `any(nearest_only)` распространял суперлатив на ВСЕ ориентиры: «рядом с МГУ и
     ближайшую к Политеху» отбрасывал радиус МГУ целиком, а warning врал про «ближайшие к
     обоим». Теперь суперлатив применяется только когда суперлативны ВСЕ, иначе —
     радиусная семантика + honest warning.
  7. Суперлативный warning не называл дистанцию (нарушение инварианта 14 на фоне
     соседнего фолбэка, который её называет). Добавлен `landmark_nearest` → `(ids,
     nearest_m)`.
  Плюс два дефекта, найденных при e2e-проверке самих исправлений: ориентир в комбинации
  с POI/центром терял требование совсем молча (landmark-ветка закрыта условием
  `not poi_requirements`) — добавлен явный warning; и пустой из-за жёсткой отсечки
  шорт-лист возвращал `ai_failed=True` с невнятным «Список кандидатов пуст», хотя ИИ не
  звали вовсе — теперь `noop()` и warning с именем ориентира и дистанцией.

**Проверено:** 738 тестов зелёные, ruff чист. Исходный запрос офлайн:
`blocks=481,1580,1460` (Амурский парк / Плеханова 11 / Лосиноостровский парк),
`landmark=Московский политех, nearest_only=True`, warnings пустые кроме честного
«у pik.ru такого фильтра нет — показаны 3 ближайших ЖК». Ирония в том, что после (A)
запрос закрывается **детерминированно, без ИИ вообще** (`ai_used=false` — теперь по
правильной причине). ИИ-ветка (B) проверена живым вызовом отдельно: «однушка в двух шагах
от Бауманки» (маркер `в двух шагах от` детерминике неизвестен) → модель вернула slug
`bauman`, координаты подставил справочник, warning снят. Запрос добавлен в корпус:
198 запросов, coverage 0.9138 → 0.9142, empty/no-filter без изменений.

## Milestone AI-23 — второй корпус (30 сложных запросов) и семь дефектов, которые он вскрыл

**Повод.** Живой запрос пользователя: «хочу трёшка ближайшая к Политеху, с раздельными
санузлами, с кухней от 15 квадратов, этажностью от 7 этажа, заселение с 2026 года по 2029
год, готовая отделка, рядом должны быть детские сады, чтобы до этих детских садов было идти
до 15-20 минут». Ответ выглядел правильным: `blocks=481,1580,1460` — Амурский парк, Плеханова
11, Лосиноостровский парк, у всех троих сады действительно есть (36/32/30 записей в
`poi_cache.json`, ближайшие 623/710/97 м — то есть в 15-20 минут пешком укладываются с
запасом). Проверка данных подтвердила: сады не выдуманы, ответ по факту верен.

**Но верен по случайности.** Две ошибки взаимно погасились.

1. `nearest_only=True` парсер выставил, а прочитать его было НЕКОМУ: вся суперлативная ветка
   в `enrich()` закрыта условием `not criteria.poi_requirements`. Сады в запросе есть →
   ветка пропущена → «ближайшая к Политеху» молча стала «в радиусе 5 км от Политеха».
2. «до 15-20 минут» не распозналось (`_DIST_NUM` не знал вилок), поэтому дистанция до садов
   не применилась вовсе.

Обе трактовки на Политехе дают одни и те же 3 ЖК — но это 1 случай из 5 на 50 ориентиров.
Замер по всем ориентирам с координатами: **суперлатив и радиус совпадают у 5 из 50**; у
МГИМО, МФТИ и Храма Христа Спасителя радиусная трактовка даёт **0 ЖК** там, где суперлатив
даёт 3. То есть на любом другом ориентире пользователь получил бы пустоту.

**Вывод про инструмент, а не про баг.** Существующий `parse_audit` этого класса дефектов не
видит в принципе: он меряет ПАРСЕР (доля покрытия текста, классы warning'ов) на коротких
запросах и намеренно не зовёт `enrich()`. Всё, что происходит на гео-сужении — где живёт
`blocks=` и где фильтр может быть распознан и не доехать до ссылки, — оставалось вне
контура. Поэтому заведён **второй корпус**: `tests/corpus/complex_queries.txt` (30 длинных
многофильтровых запросов уровня живого), `scripts/complex_audit.py` (полный путь
`parse → enrich` при выключенном ИИ `→ build_url`, валидатор не зовётся — он единственный
сетевой шаг), `tests/test_complex_queries_regression.py`. Формат вывода — **«запрос →
ссылка → критерии → ЖК с дистанциями → warnings»**: сводные метрики не показывают, доехали
ли фильтры до URL, а эта пара показывает.

Харнесс окупился на первом же прогоне — из семи починенных дефектов **три** он нашёл сам,
и они не имели отношения к исходному запросу.

**Что починено.**

- **Суперлатив при POI** (`app/ai/enrichment.py`). Ветка комбинации пересчитывает
  `matched_complex_ids` через `landmark_nearest` по кандидатам, прошедшим ОСТАЛЬНЫЕ
  требования (`resolve_known_facts` с пустым `landmark_requirements`). Ключевой инвариант:
  суперлатив заменяет **радиус**, а не весь фильтр — POI остаётся обязательным. Общие
  хелперы `_all_superlative`/`_apply_superlative`/`_warn_mixed_superlative`, чтобы текст
  warning'а и правило «суперлативны ВСЕ ориентиры» не двоились между двумя ветками.
- **Вилка дистанции** (`rules/core._DIST_NUM`). Верхняя граница; разделитель только
  дефис/тире — словесное «от X до Y» отдано площади и цене. Общий фрагмент, поэтому чинит
  сразу poi/landmark/station_class.
- **Вилка ЛЕТ** (`rules/misc._SETTLEMENT_YEAR_RANGE`) — найдено харнессом. Было ХУЖЕ, чем
  потеря: «сдача в 2026-2027 годах» давала `from=to=2026`, то есть URL-фильтр, ПРОТИВОРЕЧАЩИЙ
  запросу — он отсекал ровно те годы, которые просили. Плюс форма «с 2026 ГОДА по 2029 год»
  (слово между годом и предлогом) теряла верхнюю границу.
- **Хвостовая дистанция через разрыв** (`rules/poi._TRAILING_DISTANCE`). Устранена асимметрия
  с `_LEADING_DISTANCE`. Два предохранителя: зазор без цифр и знаков препинания (чтобы
  дотянуться до «до 45 метров» в «площадью от 35 до 45», зазору пришлось бы проглотить «35»)
  и обязательный маркер дистанции. Привязка — к конкретному POI, чей спан предшествует.
- **Дедуп POI** (`rules/poi._dedupe`). Ключ `(категория, only_new)`, дистанции по минимуму.
- **Молчаливый откат шорт-листа** (`geo/candidates.build_candidate_shortlist`) — известный
  дефект, описанный в CLAUDE.md с AI-22. Теперь параметр `warnings` и явное предупреждение.
- **«В центре»** (`enrich`). Замер: `is_center=None` у всех 51 района, а среди округов ЖК
  ЦАО отсутствует полностью; из районов ЦАО в справочнике только Таганский, и ЖК в нём нет.
  Значит заполнять `is_center` бессмысленно — «в центре» вернёт пусто в любом случае, это
  потолок портфеля застройщика (тот же класс факта, что «внутри Садового у ПИК новостроек
  нет» из AI-18). Лечится warning'ом, а не данными.
- **Разговорный суперлатив и падежные алиасы** — найдено харнессом. «Максимально близко к»,
  «как можно ближе к» добавлены в `_SUPERLATIVE_PREFIX`/`_SUPERLATIVE_CUE`. Склонения
  ориентиров закрыты алиасами, а не понижением порога: QRatio «бауманки»→«бауманка» 87.5,
  «патриарших прудов»→«патриаршие пруды» 84.8, «киевскому вокзалу»→«киевский вокзал» 81.2 —
  все ниже 88, а порог 81 впустил бы ложные срабатывания.

- **Гео-фолбэк стирал сужение по ориентиру** (`pik/url_builder.py`) — найдено последним, при
  проверке самого отчёта. `build_url` объединял `resolve_fallback_block_ids` с уже выбранными
  `criteria.complexes` через OR, хотя оба списка сужают одну ось («какие ЖК»). Итог:
  «двушку внутри МКАД около Патриарших прудов» = 8 ЖК от ориентира ∪ 27 внутри МКАД =
  **все 27**, ориентир исчезал молча. Замер подтвердил точное равенство множеств. Теперь
  AND; пустое пересечение не расширяется (это и был баг), а оставляет более специфичный
  список плюс warning. Эффект: №27 27 → 8, №9 44 → 3, №5 27 → 1.

**Результат.** Тесты 738 → 791 passed, 0 failed. Метрики парсер-аудита не сдвинулись
(0 crash / 27 empty / 60 no-filter / 91.4% — правки ничего не сломали). Сложный корпус:
запросов без гео-сужения 15 → **9**, покрытие текста 86.1% → **89.9%**, фильтров на запрос
8.53 → **8.87**. Живой запрос пользователя сохранил `blocks=481,1580,1460` (закреплено
точечным тестом) и дополнительно получил `settlementYearTo=2029`, `max_distance_m=1600` у
садов, схлопнутый дубль POI и честный warning про суперлатив. Антипример — «максимально
близко к МФТИ + сады» — был пуст, стал `blocks=1129,1555,7`.

## Г2: «до метро БЫЛО идти» и почему джокер сюда нельзя (Milestone AI-27)

**Дефект.** `_T_FOOT_MODE` допускал между «метро» и глаголом движения ровно один токен из
закрытого списка `_PREP`. Слова «было» там нет: «до метро идти не более 16 минут» → 16,
«до метро было идти 16 минут» → `None`. Терялся `timeOnFoot` — реальный URL-фильтр.

**Вопрос дизайна: свести ли слот к ограниченному джокеру по образцу
`poi._LEADING_DISTANCE`?** Ответ — **нельзя**, и это подтверждено замером, а не вкусом.
Полный разбор — `docs/parsing-rationale.md`, коротко три причины:

1. **Контрпример, выведенный из корпуса.** В `complex_queries.txt` есть строка «однушку у
   метро Аэропорт, до детского сада идти не более 10 минут». Её естественное сокращение —
   «однушку у метро до садика идти не более 10 минут» — на джокере `{0,15}` (та же длина,
   что в `poi.py`) даёт **выдуманный `timeOnFoot=10`**. Сама корпусная строка уцелела
   случайно: её спасают запятая после «Аэропорт» и длина зазора 27 символов — оба факта
   свойство формулировки, а не предохранитель.
2. **Guard `_is_poi_time_context` не спасает, и не по недосмотру.** Он смотрит контекст
   ВОКРУГ спана (`norm[start-70:start]` и `norm[end:end+70]`), намеренно исключая сам матч.
   Джокер затягивает POI-подсказку («садика», «школы», «магазина») ВНУТРЬ спана — guard её
   не видит. Замер: на всех четырёх контрпримерах `guard = False`, то есть «это не POI,
   пропускай». Чем шире джокер, тем слепее guard; подключение `_T_FOOT_MODE` к
   `metro_free_form` сделало бы хуже — появился бы уверенный неверный вердикт.
3. **Асимметрия последствий с `poi.py`.** Там отказ джокера теряет фильтр → фраза уходит в
   `warnings` (инвариант 1), это видно. Здесь отказ **фабрикует** `timeOnFoot`, вред уже
   измерен проектом: ЖК «Волжский парк» (id 411) при `timeOnFoot=12` вместо реального 15
   отдаёт 0 однушек против 31 без фильтра. И оба корпуса такой дефект не ловят
   принципиально — «фильтров на запрос» от лишнего фильтра только РАСТЁТ.

**Что сделано вместо джокера.** Отдельная константа `_FILLER`
(`было|нужно|надо|желательно|хотелось бы`) и слот `(?:(?:_PREP|_FILLER)\s+){0,2}` только в
`_T_FOOT_MODE`/`_T_FOOT_MODE_INV`. Дописывать те же слова в общий `_PREP`, как звучала
исходная формулировка задачи, **нельзя** — замер: `_PREP` живёт в 11 паттернах, и в
`_T_FOOT_2` (якоря-глагола нет, `_MINUTES` необязательно) это немедленно крадёт чужие
числа — «метро нужно 15 млн» → `timeOnFoot=15`, «метро желательно 40 метров площадь» →
`timeOnFoot=40`. Цена и площадь превращались бы в тот самый выдуманный фильтр. В новом
слоте такого нет: он зажат перед ОБЯЗАТЕЛЬНЫМ словом способа передвижения, которое и
служит семантическим якорем. `{0,2}` — ровно под «надо было идти».

Это по-прежнему игра в крота (следующее незнакомое служебное слово снова потеряет фильтр),
но крот здесь предпочтительнее джокера: промах закрытого списка **теряет** фильтр (видно в
`warnings` и в покрытии), промах джокера **выдумывает** его (не видно нигде).

**Результат.** `uv run pytest`: 975 passed, 1 skipped, 0 failed; ruff чист. Парсер-аудит не
сдвинулся (0 crash / 27 empty / 60 no-filter / 91.4%). Сложный корпус — эффект правки
изолирован от эффекта новой строки: на одном и том же корпусе из 34 запросов **без** правки
94.1% / 9.03, **с** правкой **94.9% / 9.06** (+0.8 п.п. покрытия; +0.03 фильтра = ровно один
восстановленный `timeOnFoot`). Запросов без гео-сужения 8 — не изменилось.

**Находка на пороге.** Первая версия новой корпусной строки («трёшку в Отрадном…»)
сужалась районом, а не `blocks=`, и уронила `MAX_WITHOUT_BLOCKS` (9 > 8). Порог не
ослаблялся: слабой оказалась строка корпуса, а не планка — корпус существует ровно для
проверки гео-сужения. Ориентир заменён на МИФИ (4 ЖК, покрытие 1.0, `timeOnFoot=16` в
ссылке). Отдельно зафиксировано: у `MAX_WITHOUT_BLOCKS` сейчас **нулевой запас** — его
израсходовал AI-26, и следующий запрос без гео-якоря снова упрётся в планку.

## Г5: невидимый провал free-text-ветки ИИ (Milestone AI-28)

Правка от 2026-07-28. Разбор состояний и таблица-различитель —
`docs/ai-enrichment-architecture.md`, раздел 8.6.

**Дефект.** `resolve_free_text_criteria` (экстрактор свободного текста, ведро C, работает
ДО гейта 1) глушила оба пути отказа: исключение вызова уходило в `logger.error(exc_info=
True)` и возвращало `FreeTextOutcome(called=True)` без признака отказа; `CircuitOpenError`
(cooldown предохранителя) — в `logger.warning` и `FreeTextOutcome(called=False)`, то есть
неотличимо от «модель не звали». Поля провала у `FreeTextOutcome` не было вовсе, поэтому
отказ физически не мог доехать до `EnrichmentResult.ai_failed`. Следствие: ответ API с
`ai_used=false, ai_failed=false` означал одновременно три разных состояния — «не звали»,
«позвали, и он ничего не поменял», «позвали, и упало». Это нарушение инварианта 1 на
уровне телеметрии: фрагменты оставались в `warnings`, но причина их появления пропадала.

**Почему не ловилось.** Успешная ветка экстрактора не логировала вообще ничего, поэтому
диагностику пришлось строить на выводах ПО ОТСУТСТВИЮ строк лога — это и был главный
симптом, а не побочная деталь. Оба QA-корпуса такой дефект не видят принципиально: они
гоняются при `AI_ENRICHMENT_ENABLED=False`, где free-text-ветка возвращает «выключен».

**Что сделано.**
- `FreeTextOutcome` получил `failed: bool` и `failure_reason: str | None` со значениями
  `"exception"` (вызов упал, `called=True`) и `"breaker"` (предохранитель в cooldown,
  `called=False` — до провайдера не дошли, но это отказ ИИ-слоя, а не гейт).
- **Границы провала намеренно узкие — «модель НЕ ответила».** «Ответила и ничего не
  заполнила» и «значения отбиты `validate_assignment`/санитайзером» — успешный вызов без
  пользы (`failed=False`), иначе `ai_failed` срабатывал бы на исправном ИИ, ошибшемся
  форматом. Отсутствие кредов и снятый `AI_ENRICHMENT_ENABLED` — «выключен», НЕ провал
  (инвариант 9).
- Провал доезжает до ответа через **существующее** поле `ai_failed`; новых полей в
  `BuildUrlResponse` нет, контракт API не сломан. Слияние — в замыкании `_log()` внутри
  `enrich()` (`if free_text.failed: result.ai_failed = True`), и это единственная
  корректная точка: через `_log()` проходят все return-пути `enrich()`, а
  `noop()`/`from_deterministic()` строятся с `ai_failed=False` — без этой строки факт
  провала терялся бы ровно на гейте 1, самом частом пути free-text-запроса.
- Инвариант 1 на уровне текста: при провале в `warnings` добавляется строка «не удалось
  дообработать оставшийся текст через ИИ — перечисленные выше фрагменты не учтены в
  ссылке». Фрагменты и так там были — новая строка объясняет, ПОЧЕМУ. `ai_failed` читает
  машина, `warnings` — человек.
- Наблюдаемость успешного пути: после удачного вызова пишется `logger.info` с `changed`,
  числом фрагментов и `answer.model_dump(exclude_defaults=True)`. Без него «модель ничего
  не вернула» и «вернула, но всё отбито валидацией» неразличимы (обе дают
  `changed=False, failed=False`).
- `ai_call_log`: миграция `app/ai/migrations/03_ai_call_failed.sql` (`ADD COLUMN IF NOT
  EXISTS ai_failed BOOLEAN NOT NULL DEFAULT false`), у `log_ai_call` — kwarg
  `ai_failed: bool = False`, который `enrich()` заполняет из `free_text.failed`. Строка на
  каждый `enrich()` писалась и раньше — не хватало именно признака провала: breaker-путь
  писал `ai_called=false`, и отказ сливался с «не звали».
- `app/ai/usage_report.py`: `CallLogRow.ai_failed` (дефолт `False` — строки до миграции 03
  провалов не различали), агрегаты `ai_failed` и `ai_attempts`, свойство `pct_ai_failed`,
  строка отчёта «попытка провалилась (ai_failed)». Знаменатель доли — **попытки**
  (`ai_called or ai_failed`), а не `ai_called`: breaker даёт `ai_called=false` при
  `ai_failed=true`.

**Побочная находка.** Существовавший тест `test_enrich_gate1_preserves_existing_warnings`
(`tests/ai/test_enrichment.py`) не мокал экстрактор и уходил в РЕАЛЬНЫЙ вызов провайдера с
фиктивным ключом — зелёным его держал ровно чинимый дефект: провал не оставлял следов, и
тест не отличал «гейт сработал» от «сходили в сеть и упали». Экстрактор в нём замокан
пустым ответом; теперь тест проверяет гейт, а не сеть.

**Результат.** Новый файл `tests/ai/test_free_text_failure_visibility.py` — 12 тестов
(уровень `FreeTextOutcome`; границы «что провалом не является»; уровень
`enrich()`/`ai_call_log`; критерий готовности через реальный `POST /build-url` с
искусственно уроненным вызовом), плюс два теста в `tests/ai/test_usage_report.py`.
`uv run pytest` — 989 passed, 1 skipped; `ruff check` и `ruff format --check` чисты.
**Пороги обоих QA-корпусов не ослаблялись и не двигались** — правка их не касается:
корпуса идут при `AI_ENRICHMENT_ENABLED=False`, где новая строка warning не добавляется.

## Г1: sentinel «любое метро» съедал уточнение линии (Milestone AI-29)

Живой запрос «рядом с любым метро коричневой ветки, рядом детский сад не дальше
10 минут пешком» возвращал 31 ЖК со всей Москвы и пустой `warnings` (кроме строки
про садик). Дефект составной — ломались три слоя сразу:

1. парсер отдавал ДВА `StationClassRequirement` (sentinel `метро` + `Кольцевая`);
2. `station_class_points` трактует список как OR, sentinel разворачивается во все
   357 станций справочника с координатами — union «357 ∪ 12» = 357, вклад линии
   нулевой;
3. вся станционная диагностика жила в ветке `enrich`, требующей одновременного
   отсутствия POI, центра и ориентира, — её выключал детский сад в том же запросе.

При этом честный фильтр по Кольцевой даёт `blocks=0`: ближайший ЖК 2.51 км при
радиусе 1500 м. Запрос невыполним, и правильный ответ — деградация с объяснением.

**Три принятых решения** (разбор — `docs/geo-narrowing.md`, прецедент по парсеру —
`docs/parsing-rationale.md`):

- **Слияние — в парсере**, но правилом гео-слоя («специфичное побеждает
  универсальное», а не «смежные спаны клаузы»). В гео-слое лечилась бы выдача, но
  `to_public_dict()` продолжал бы показывать два требования. Область слияния
  ограничена примыканием спанов: «любое метро ИЛИ Кольцевая» и «любое метро, но
  лучше Кольцевая» не сливаются — там молчание спрятало бы сужение запроса.
  Схлопывание молчаливое: спан sentinel'а остаётся съеденным, отобрано значение,
  а не текст.
- **Разгейчено дублированием ветки**, как уже сделано для ориентиров:
  комбинированная ветка мутирует `known["matched_complex_ids"]` и проваливается

## Отбитое валидацией значение уносило warning своего фрагмента (Milestone AI-30)

Дефект найден при проектировании Г6, живым запросом не ловился. `_apply_free_text_answer`
снимал warning'и всех фрагментов из `consumed_fragments` под общим условием `if changed:`

нет, фильтр исчезал бесследно. Инвариант 3 требует обратного — «выдуманное
отбрасывается, фраза остаётся в `warnings`»; отбитый скаляр это тот же случай, правило
просто не применялось последовательно.

**Чем случай отличается от `rejected_landmark_phrases`** (прецедент выше по файлу). У
ориентиров фраза привязана к значению — `LandmarkMatch.phrase`, — поэтому отклонённые

нереализуемо — это и определило форму правки.

**Принятые решения** (разбор — `docs/ai-enrichment-architecture.md`, раздел 8.7):

- **Снимаем все или ничего.** Любая отбивка отменяет снятие целиком. Цена принята:
  фрагмент, чьё значение доехало, в этом редком случае сохранит лишний warning. Лишний

- **Добавлена строка `_FREE_TEXT_REJECTED_WARNING`** — по образцу
  `_FREE_TEXT_FAILED_WARNING` из AI-28: фрагменты и так остаются, но сами по себе говорят

  получит вместе с Г6; параллельный механизм не заводился.
- **Провенанс на уровне поля не делался.** Связь «поле → фрагмент» потребовала бы менять
  схему ответа и промпт — за границами точечной правки.
- **`ai_failed` не трогался.** Отбивка валидацией остаётся успешным вызовом без пользы
  (граница из AI-28), новый тест это фиксирует.

**Замер.** Метрики обоих корпусов не изменились и измениться не могли: корпуса гоняются

## Один элемент warnings — один факт (2026-07-28)

Подготовка к Г6. Четвёртый элемент `warnings` живого запроса
(`docs/measurements/step-a-baseline.md`) нёс три несвязанных факта сразу:
несостоявшуюся проверку выдачи, справку о вечно непроверяемых параметрах и
заметку о гео-сужении по полигону МКАД. Причина — `compose_warning` в
`validator.py` склеивал всё через `"; "`, а `endpoints.py` клал результат в
ответ **одним** элементом. Под моделью категорий из
`docs/warnings-severity-proposal.md` такому элементу пришлось бы быть
одновременно `unverified`, `capped` и `info`: разметить неделимое невозможно,
поэтому форма правится до разметки, а не вместе с ней.

`ValidationResult.warning: str | None` стал `warnings: list[str]`, склейка
исчезла, `endpoints.py` делает `extend`. Разбирать готовую строку обратно по
разделителю было бы неверно: локационный литерал успешной ветки сам содержит
`"; "` внутри — список собирается у источника, а внутренний разделитель из
литерала убран, чтобы ложной границы не осталось.

**Чей это был факт.** Заметка про МКАД к валидатору отношения не имеет — её
порождает `resolve_fallback_block_ids` (`location_fallback.py`), и приехала она
сюда не правкой Г6: `fallback.notes` уходили в `success_warning` и раньше, Г6
лишь распространила их на ветку отказа. Теперь их публикует `build_url` —
безусловно, вне ветки `if fallback.block_ids`, иначе терялось бы объяснение
«ни одного ЖК нужной стороны». Валидатор ту же логику по-прежнему прогоняет
(иначе `result_count` проверял бы не то сужение), но приёмник предупреждений
получает `None`. Побочно снят дубль: предупреждение о непересечении гео-условий
уходило в ответ **дважды** — отдельным элементом из `build_url` и внутри
склейки из `validate`; склейка это маскировала, после разделения дубль стал бы
виден. Следствие формы: заметки фолбэка теперь стоят в списке выше
валидаторских фактов — `build_url` отрабатывает раньше `validate`.

**Перевёрнутый акцент.** Текст отказа перечислял отделку и год — то, что не
подтверждается НИКОГДА, даже при успешном ответе, — и молчал про `blocks`,
единственный фильтр, который бэкенд по нашим замерам реально проверяет. При
отказе теряется ровно одна настоящая проверка, и названа теперь именно она;
справка о вечно непроверяемых параметрах осталась отдельным элементом и больше
не пересказывает сам факт несостоявшейся проверки.

**Риск, снятый до правки.** `warnings` — не выходной буфер, а несущий канал:
`enrichment.py` удаляет элементы по точному равенству строк, `_residual_fragments`
разбирает их `startswith`/`endswith`, `parse_audit.py` матчит фразу регексом.
Ни одного из трёх правка не задевает. Удаление и разбор работают только с
элементами вида `«…»: не удалось распознать, не попало в ссылку` (их порождает
`parser.py`), а составной элемент валидатора попадает в список на
`endpoints.py` **после** `enrich()` — на момент работы `resolve_options` и
`_apply_free_text_answer` его там физически нет. Оба аудита `validate()` не
вызывают вовсе, а пороговая метрика покрытия считается от содержимого
(`"\n".join(warnings)` + регекс по фразе) и к числу элементов инвариантна.
Правка стала бы опасной, только если бы меняла текст элементов
`parser.py` — она их не трогает.

**Замер.** Живой запрос из `docs/measurements/step-a-baseline.md`: было 4
элемента (четвёртый — тройной), стало 6, каждый — один факт, ничего не
потеряно. Корпуса без изменений, **пороги не ослаблялись**: короткий — crashes 0,

## Проверка семантики `floorFrom`/`floorTo` — тревога не подтвердилась (2026-07-28)

**Повод.** Сообщение от пользователя: ссылка с `floorFrom=7`, открытая на pik.ru, якобы
показывает РОВНО седьмой этаж, а не «седьмой и выше». Если бы это было так, все ссылки
проекта с «этаж от N» были бы правдоподобными и неверными — а `docs/pik-url-schema.md`
объявлен единственным источником правды, значит правка была бы документа, не только кода.
Область сознательно ограничена этажом: `settlementYearTo=2029` одиночной границей работает
правильно (проверено на живом сайте), то есть речь не о системном поведении одиночных
границ.

**Что сделано.** Замер до правки — сначала бэкенд, потом фронт. Полный протокол вынесен в
новый каталог `docs/measurements/` (файл `2026-07-28-floor-from-to.md`); здесь — только
выводы.

- **Бэкенд `api.pik.ru/v2/filter` опроверг гипотезу ещё до захода на сайт.** Полигон ЖК 477
  (этажность 2…21), `rooms=1`, baseline 55. `floorFrom=7` → **33**, а `floorFrom=7&floorTo=7`
  → **2**. Будь `floorFrom=7` точным значением, числа совпали бы. Тождества:
  `floorFrom=7` = `floorFrom=7&floorTo=50` (33 = 33), `floorTo=12` = `floorFrom=1&floorTo=12`
  (34 = 34), `floorFrom=1&floorTo=50` = baseline (55 = 55). Контроль `floorFrom=99` → 0.
  Зеркальной болезни у `_FLOOR_MAX` нет.
- **Фронт подтвердил бэкенд живыми карточками.** `curl` до `www.pik.ru` не достаёт (Qrator,
  **HTTP 401**) — замер сделан реальным браузером. При `floorFrom=7` в выдаче физически
  присутствуют этажи **7, 10, 11, 13, 16, 20, 21**; при `floorTo=12` — **2, 4, 5, 6, 7, 9,
  10, 11**; при `floorFrom=7&floorTo=12` — **7, 9, 10, 11, 12**. Счётчики сайта (33 и 2)
  совпали с бэкендом.
- **Эталон UI совпал с нашим генератором побайтово.** Фильтр «Этаж» на сайте — пара полей;
  при вводе только нижнего значения правое поле остаётся ПУСТЫМ, и применение даёт
  `https://www.pik.ru/search/one-room?blocks=477&floorFrom=7`. picurl для «однокомнатную
  квартиру в Руставели 14 от 7 этажа» выдаёт ровно эту строку. Следовательно дополнять
  одиночную нижнюю границу верхней (максимальной этажностью, константой — чем угодно) не
  просто не нужно, а **вредно**: это развело бы нас с эталоном.

**Источник ложной тревоги — подпись чипа в UI pik.ru.** «Применённые фильтры» показывают
«**7 этаж**» и для `floorFrom=7` (33 квартиры, этажи 7…21), и для `floorFrom=7&floorTo=7`
(2 квартиры, только этаж 7) — две принципиально разные ссылки подписаны одинаково. Две
разные границы дают «7 этаж - 12 этаж», но одиночная читается как точное значение.
Повлиять на это мы не можем; прочитать применённый фильтр надёжно можно только по паре
полей в панели «Фильтр» или по подписям «Этаж N из M» на карточках.

**Изменения.** Кода — нет, и это осознанный итог, а не недоделка: `rules/floor.py`,
`Criteria.to_query_dict()` и `url_builder` были верны. `docs/pik-url-schema.md` — строка
таблицы уточнена и добавлен раздел «Этаж: семантика границ» с замером, тождествами и
подразделом «Чем это НЕ является» (про чип), чтобы следующий человек с тем же наблюдением
не начинал расследование заново. Добавлены два теста
(`tests/pik/test_url_builder.py`): одиночный `floor_min` не должен приводить к появлению
`floorTo`, одиночный `floor_max` — к появлению `floorFrom`. Они закрепляют **состав
параметров**, а не семантику выдачи, и защищают ровно от «улучшения» по мотивам этой
тревоги.

**Урок (третий случай подряд класса «фильтр доехал, но означает не то»).** Ни один
автоматический контур проекта такое поймать не мог и не может. Оба корпуса сравнивают
запрос со ссылкой и никогда — ссылку с выдачей pik.ru; `validate()` берёт `result_count` с
того же бэкенда, что и генерирует ссылку, поэтому согласованность параметра с самим собой
он подтвердит при любой трактовке. Здесь к этому добавился новый подкласс: сигнал о
дефекте пришёл из **UI-подписи**, а не из данных, — то есть ложным было само наблюдение, и
единственный способ это установить — измерить. Минимум, который сделал бы класс видимым,
сформулирован и НЕ реализован: контур, который для нескольких эталонных критериев
вытаскивает из выдачи pik.ru фактические значения отфильтрованного поля (этаж, год, цену)
и проверяет, что все они попадают в запрошенный интервал, — то есть сверяет ссылку не с
`count`, а с содержимым карточек.

## Г6, порция 1: категории warnings — каркас и различитель остатка (2026-07-28)

**Повод.** Живой инцидент: `«Привет»: не удалось распознать` и `«этаж от 7»: не удалось
распознать` в плоском `list[str]` неотличимы. Первое — корректно отброшенный шум, второе —
потерянный фильтр; ссылка во втором случае неполная, но выглядит рабочей. Дизайн задачи
целиком — `docs/warnings-severity-proposal.md`; внедряется **порциями**, здесь закрыты
шаги 1-2 из пяти.

**Форма — «дополнить, не ломать».** Ключевой факт, определивший выбор: `warnings` — не
выходной буфер, а **внутренний канал данных**. Один мутируемый список передаётся по
ссылке; `enrichment` удаляет из него элементы **по точному равенству строк**,
`_residual_fragments` разбирает строки регексом и возвращает фрагменты в ИИ, а
`scripts/parse_audit.py` матчит суффикс «не удалось распознать, не попало в ссылку» — и на
этом регексе держатся пороги QA. Любая форма, ломающая строковое равенство или подстроку,
ломает не отображение, а поведение: устаревшие warning'и перестанут сниматься, и тест на
это может не упасть.

Поэтому носитель категории — **подкласс `str`** (`app/warnings.py`, `TaggedWarning`):
несёт атрибут `category`, но для `==`, `in`, `list.remove()`, регекса, `deepcopy`,
`json.dumps` и pydantic остаётся обычной строкой. `WarningCategory` — семь значений
(`lost`/`unknown`/`noise`/`capped`/`unverified`/`degraded`/`info`), граница между ними
проведена там, где у пользователя **разное действие**. `severity` — производная от
категории, не независимое поле.

- **Что выяснилось только на реализации:** pydantic v2 **коэрсит подкласс `str` к обычному
  `str`** (проверено на 2.13.4) — внутрь `BuildUrlResponse` категория не доезжает в
  принципе. Поэтому `warnings_detailed` собирается в `endpoints.py` **до** конструирования
  модели, а плоский `warnings` выводится из него — источник правды один, каналы не
  разъезжаются. Закреплено тестом.
- **Что проверено сверх предложения:** оба аудит-скрипта гоняют warnings через `asdict()`
  (= `copy.deepcopy` каждого элемента) и `json.dumps`. `deepcopy` подкласса категорию
  сохраняет, `json.dumps` пишет обычную строку — скрипты не правились.

**Различитель остатка (`parser._classify_residual`)** — единственное место всей разметки,
где нужна новая логика: остальные ~61 точка определяется местом вызова, а здесь парсер
физически не знает ответа (видит остаток спанов, а не намерение). Правило намеренно
**асимметрично**: `lost` требует предметного признака (слово-параметр либо число с
единицей — проверяется только соседняя справа лексема и слипшаяся форма «45м»/«15млн»),
`noise` требует, чтобы **каждое** слово было приветствием/вежливостью или стоп-словом, всё
прочее остаётся `unknown`. Причина: `unknown` и `lost` дают одинаковый severity (`error`),
спутать их дёшево, а `noise` на реальной потере **гасит сигнал** и хуже сегодняшнего
плоского списка. Приветствия заведены отдельным списком `_GREETING_WORDS`, а не
дополнением `STOP_WORDS`: тот переиспользуется матчером сущностей, и всё попавшее туда
перестаёт открывать окно топонима — это изменило бы поведение парсинга, то есть ровно то,
чего порция обязана не делать.

**Совместимость — измеренная, не заявленная.** 1009 тестов зелёные; **ни один
существующий ассерт, ни один аудит-скрипт, ни один порог QA не правился** (единственный
диff в `tests/` — новый файл `tests/test_warning_categories.py`). Плоский `warnings` на
обоих корпусах (229 запросов, 69 строк) сверен с прогоном на чистом `HEAD` и совпал
**побайтово**. Метрики не сдвинулись: `parse_audit` — 0 crash / 27 пустых / 91.4%
покрытия; `complex_audit` — 0 crash / 93.6% / 8.97 фильтров на запрос (те же числа до и
после).

**Что порция дала сразу.** На исходном инциденте: `«Привет»` → `noise`/`info`,
`«этаж от 7»` → `lost`/`error`. На двух корпусах остаток разложился как **23 `lost` /
2 `noise` / 26 `unknown`** плюс 18 неразмеченных точек (каталог «не поддерживается
pik.ru», неоднозначности), честно отдаваемых как `unknown` — это шаги 3-5. И сразу же
ведро `lost` показало **три реальные потери поддерживаемого фильтра**, до сих пор
лежавшие в одном списке с «либо» и «что посоветуете»: «окна во двор» (опция `vidVoDvor` в
справочнике **есть**, алиасы только «вид во двор»/«с видом во двор»), «санузлов несколько»
(инверсия мн. ч., обязана уходить в `manybathrooms`), «отделка готовая» (инверсия, правило
требует прямой порядок). **Ни одна не чинилась** — порция 1 не имеет права менять
поведение парсинга; они записаны заявками в §5 предложения.

**Чего разметка НЕ делает — и не может по определению.** Категорию можно навесить только
на warning, который существует; две молчаливые потери, найденные на дизайн-этапе
(`enrichment` снимает warning для фрагмента, чьи значения отбиты валидацией; `validator`
теряет собранный `success_warning` в аварийных ветках), остаются открытыми и требуют
отдельных правок. Что разметка даёт — **возможность их находить**: непустеющее ведро
`unknown` и доля `lost` на корпус превращают молчаливую потерю в наблюдаемую метрику,
которой раньше не было вовсе.

## graphify

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
