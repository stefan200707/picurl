# Спецификация URL-схемы pik.ru/search

Единый источник правды по схеме фильтров каталога `https://www.pik.ru/search`.
Схема восстановлена **вживую**: кликами по фильтрам на сайте с фиксацией
адресной строки. Официальной документации у сайта нет.

На этот документ опираются:

- промпт 03 — справочники (метро/округа/районы/ЖК);
- промпт 07 — `app/pik/url_builder.py` (Criteria → URL);
- промпт 08 — `app/pik/validator.py` (проверочный запрос к backend-API).

Статусы полей: **✅ подтверждено** — проверено живыми кликами;
**❔ предположение** — выведено из общей закономерности, вживую не проверено.

---

## Ключевая закономерность: single-путь / multi-query

Подтверждена на трёх независимых фильтрах (комнатность, округ, метро): ✅

- **Единственное** выбранное значение фильтра → уходит в **путь** URL
  человекочитаемым слагом.
- **Два и больше** значений → сегмент пути пропадает, вместо него появляется
  **query-параметр** со списком «сырых» id/GUID через запятую.

Это правило — центральное для `url_builder`: при построении URL каждый
«локационный» фильтр сначала проверяется на количество значений, и только
потом решается, куда он попадёт — в путь или в query.

```
1 значение:   https://www.pik.ru/search/two-room
2+ значения:  https://www.pik.ru/search?rooms=1,2
```

---

## Сегменты пути

Порядок сегментов: `/search/{комнатность}/{отделка-или-заселение}/{локация}`.
Каждый сегмент опционален; при пропуске сегмента остальные «сдвигаются влево»
(пустых слотов в пути не бывает).

| Фильтр | Значения | Пример | Статус |
|--------|----------|--------|--------|
| Комнатность | `studio`, `one-room`, `two-room`, `three-room` (чип «3+» на сайте → `three-room`) | `/search/two-room` | ✅ |
| Отделка «Готовая» | `finish` | `/search/two-room/finish` | ✅ |
| «Заселение сразу» | `ready` | `/search/two-room/ready` | ✅ |
| Округ (Москва) | код округа, напр. `zao` | `/search/three-room/zao` | ✅ |
| Метро | `m-<слаг-станции>` | `/search/two-room/m-aeroport-vnukovo` | ✅ |
| ЖК | слаг ЖК, **перед** комнатностью (переход со страницы ЖК) | `/search/{жк-слаг}/two-room` | ✅ |

Примечания:

- Слот «локация» занимает **один** из вариантов: округ *или* метро
  (одновременно два локационных сегмента в пути не встречались). ❔
- «Отделка» и «Заселение сразу» делят один слот пути; их совместное
  использование вживую не проверялось. ❔

## Single (путь) vs Multi (query) по фильтрам

| Фильтр | Single (путь) | Multi (query) | Статус |
|--------|---------------|---------------|--------|
| Комнатность | `/search/two-room` | `?rooms=-1,1,2` (студия = `-1`) | ✅ |
| Округ | `/search/two-room/zao` | `?districtCounties=9,6` | ✅ |
| Метро | `/search/two-room/m-aeroport-vnukovo` | `?metroStations=<GUID>,<GUID>` | ✅ |
| Район | (нет single-в-путь) — всегда query | `?districtLocations=520,203` | ✅ |
| ЖК | `/search/{жк-слаг}/two-room` (только со страницы ЖК) | `?blocks=1108,...` (как доп. фильтр) | ✅ single; multi (`blocks=id,id`) — ❔, см. «Сознательно не проверено» |

Обрати внимание на разницу форматов multi-значений: комнатность/округ/район/ЖК —
числовые id, метро — GUID. Соответствия «слаг ↔ id/GUID» лежат в локальных
JSON-справочниках (промпт 03).

## Query-параметры

Все параметры ниже подтверждены живыми кликами. ✅

| Параметр | Смысл | Пример |
|----------|-------|--------|
| `priceFrom` / `priceTo` | цена, руб | `priceFrom=10000000&priceTo=15000000` |
| `areaFrom` / `areaTo` | площадь общая, м² | `areaFrom=70&areaTo=100` |
| `areaKitchenFrom` / `areaKitchenTo` | площадь кухни, м² | `areaKitchenFrom=8&areaKitchenTo=12` |
| `floorFrom` / `floorTo` | этаж (диапазон) | `floorFrom=5&floorTo=20` |
| `notFirstFloor=1` | чекбокс «Не первый» | `notFirstFloor=1` |
| `lastFloor=1` | чекбокс «Последний» | `lastFloor=1` |
| `timeOnFoot` | время до метро пешком, мин | `timeOnFoot=15` |
| `timeOnTransport` | время до метро на транспорте, мин | `timeOnTransport=15` |
| `sortBy` + `orderBy` | сортировка: `sortBy=price\|area`, `orderBy=asc\|desc` | `sortBy=price&orderBy=asc` |
| `rooms` | комнатность (multi), comma-list; студия = `-1` | `rooms=-1,1,2` |
| `districtCounties` | округ (multi), числовые id | `districtCounties=9,6` |
| `metroStations` | метро (multi), GUID-ы | `metroStations=<GUID>,<GUID>` |
| `blocks` | конкретный ЖК, числовой id | `blocks=1108` |
| `districtLocations` | конкретный район (не округ!), id(-ы) | `districtLocations=203` |
| `settlementYearFrom` / `settlementYearTo` | год сдачи | `settlementYearFrom=2027` |
| `settlementMonthFrom` / `settlementMonthTo` | месяц сдачи (1–12) | `settlementMonthFrom=3&settlementMonthTo=8` |
| `currentBenefit` | программа покупки, слаг | `currentBenefit=rassrochka-na-12-mesyacev-7` |
| `optionGroups` | «Особенности планировки», comma-list слагов | `optionGroups=smartHomePIK,balcony` |
| `options` | «Вид из окна», слаг | `options=vidNaVodu` |
| `type` | `1` = только квартиры (без апартаментов); параметр отсутствует = показывать оба типа | `type=1` |
| `status` | `free` = «Не показывать забронированные» | `status=free` |

## Сортировка по умолчанию (решение открытого вопроса №1)

**Решение:** если пользователь не указал сортировку, `sortBy`/`orderBy` в URL
**не добавляются вовсе** — сайт применяет собственную дефолтную выдачу
(«рекомендуемые»). Никакого неявного `sortBy=price&orderBy=asc` по умолчанию.

Обоснование: любая навязанная сортировка искажает намерение пользователя;
отсутствие параметров — единственный способ получить «как на сайте по умолчанию».
Решение зафиксировано также в `CLAUDE.md`.

## Полный пример (эталон для теста url_builder)

Запрос: «2-комнатная, 10–15 млн, метро Аэропорт Внуково, сортировка по убыванию
площади»:

```
https://www.pik.ru/search/two-room/m-aeroport-vnukovo?priceFrom=10000000&priceTo=15000000&sortBy=area&orderBy=desc
```

Разбор:

- одна комнатность → путь `two-room` (single-путь);
- одна станция метро → путь `m-aeroport-vnukovo` (single-путь);
- цена и сортировка — всегда query.

## Маркер пустой выдачи (fallback для отладки)

На HTML-странице при нулевой выдаче отображается текст:

> «По заданным параметрам не удалось ничего подобрать» /
> «Попробуйте изменить настройки фильтров».

Основная валидация выдачи всё равно делается через **JSON backend-API** сайта
(pik.ru — SPA, HTML-страница рендерится клиентом), см. промпт 08. HTML-маркер —
только вспомогательная ручная проверка при отладке.

---

## Сознательно не проверено (не блокер; собрать на шаге 03)

- **Полный список слагов** `optionGroups` / `options` / `currentBenefit` —
  собрано по одному примеру на категорию; нужно пройтись по всем чекбоксам
  при сборке справочников. ❔
- **«Тип паркинга»** — поле рядом с «Время до метро»; поведение в URL
  не проверено. ❔
- **Выбор 2+ ЖК одновременно** — вероятно `blocks=id,id` по общей
  закономерности single-путь/multi-query, но вживую не подтверждено. ❔
- **Совместное использование** `finish` и `ready` в пути (делят один слот). ❔
- **Два локационных сегмента** в пути одновременно (округ + метро). ❔

## Data API (Backend-эндпоинт)

Сам сайт pik.ru является SPA и для получения списка/счётчика квартир под применённые фильтры делает запрос к backend-API. 
Единственным источником данных для выдачи служит эндпоинт:
`https://api.pik.ru/v2/filter`

Принимает те же query-параметры, что описаны выше для URL (например, `priceFrom`, `priceTo`, `rooms` и т.д.).
Отвечает JSON-объектом, содержащим список квартир и общее их количество (`count`).

Пример запроса:
`GET https://api.pik.ru/v2/filter?priceFrom=10000000&priceTo=15000000`

Пример ответа:
```json
{
  "count": 2231,
  "countBlocks": 15,
  "blocks": [...],
  "flats": [...]
}
```
В рамках проекта этот эндпоинт используется валидатором (`app/pik/validator.py`) для проверки того, что построенный URL не ведёт на пустую выдачу.
