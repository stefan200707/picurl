# Как текст делится на части и как оцениваются совпадения

Этот документ описывает **реализованный** детерминированный разбор запроса на квартиру.
Основной код: `app/parsing/parser.py`, `app/parsing/entity_match.py`,
`app/parsing/rules/`, `app/reference/loader.py`. Здесь «вес» — численная оценка
**совпадения фрагмента запроса с именем или алиасом из справочника**, а не вес
отдельного слова. Проект не режет слова на слоги и не обучает веса слов.

## От исходной фразы к фрагментам

1. Если в запросе есть цифры, `parse(text)` сначала вызывает
   `match_entities(text)` для предварительной защиты названий справочных
   сущностей с числами (например, `Руставели 14`).
   Затем `apply_rules(text, reserved=...)` извлекает комнаты, цену, площадь и
   другие структурные условия. Каждое правило возвращает диапазон символов
   `[start, end)` исходной строки (`Span`); защищённое число не становится
   частью числового фильтра.
2. Занятые правилами диапазоны заменяются пробелами **той же длины**. Так
   `match_entities(clean_text)` ищет названия метро, округов, районов, ЖК и опций
   без повторного разбора уже найденных условий, сохраняя позиции в исходном
   тексте.
3. Для поиска слов матчер использует шаблон
   `[A-Za-zА-Яа-яЁё0-9]+(?:-[A-Za-zА-Яа-яЁё0-9]+)*`: буквы и цифры образуют
   токен, внутренний дефис остаётся в нём (`мастер-спальня` — один токен).
   Пробелы и прочая пунктуация отделяют токены. Из последовательности токенов
   строятся все соседние окна длиной от **1 до 5** слов. Окно с запятой или
   точкой с запятой внутри отклоняется. Для конструкций с `и`/`или` добавляются
   специальные окна, соединяющие слова до союза со словом после него. У такого
   окна сравниваются все собранные слова, а его `Span` указывает только на
   слово после союза.
4. Окно из одних `STOP_WORDS`, окно с обычным стоп-словом на краю и одинокий
   маркер `метро`/`район`/`округ`/`жк` не считаются именем. Внутренние
   стоп-слова удаляются из `clean_window` для дополнительной проверки.
   Предлог и предметный маркер всё же могут подсказать тип сущности.

Например, из `у метро Сокол` получаются токены `у`, `метро`, `Сокол` и окна
`Сокол`, `метро Сокол`, `у метро Сокол` среди остальных. Для окна `Сокол`
предшествующее `у метро ` задаёт тип `metro`; если совпадение принято, его
`Span` включает и маркер. Это позволяет парсеру не считать `у метро` остатком.

Для сравнения строк `reference.loader.normalize()` приводит регистр, заменяет
`ё` на `е`, латинские буквы-двойники на кириллицу и схлопывает пробелы. Имена и
алиасы из локальных JSON-справочников проходят ту же нормализацию. Отдельная
посимвольная нормализация в regex-правилах сохраняет длину текста, чтобы `Span`
оставался корректным. **Морфологического анализатора здесь нет**: склонения и
опечатки обрабатываются нечётким сравнением и конкретными правилами.

## Как получается оценка

Для каждого окна `rapidfuzz.process.extract()` ищет до 100 лучших совпадений
с нормализованными именами и алиасами, используя `fuzz.WRatio`. Далее действует
последовательность проверок:

| Условие | Действие |
|---|---|
| Имя/алиас длиной не более 3 символов без пробелов | Только точное равенство нормализованных строк. |
| Обычное окно | `WRatio >= SCORE_THRESHOLD` (сейчас 80). |
| Окно с маркером нужного типа | `WRatio >= TRIGGERED_SCORE_THRESHOLD` (сейчас 75); очищенное окно также должно дать `WRatio >= 75`. |
| Окно без маркера или искусственное окно через союз | Дополнительно `QRatio >= STRICT_QRATIO_THRESHOLD` (сейчас 80). |
| Опция или группа опций | Дополнительно `QRatio >= OPTION_MIN_QRATIO` (сейчас 55); для однословной опции также нужен строгий `QRatio >= 80`. |

Маркер — например, `у метро`, `в районе`, `округ`, `жк`; для опций есть
подстрочные подсказки вроде `сануз` и `балкон`. Маркер снижает порог только
для подходящего типа, но не превращает несходное слово в совпадение.
`QRatio` сравнивает строки целиком и отсекает случай, когда `WRatio` высок
лишь из-за короткой общей подстроки. Для опций `_modifier_conflict()` также
сверяет основу различающих слов: `сквозным санузлом` может совпасть со
`сквозной санузел`, а `гостевой санузел` не должен стать `сквозным`.
Здесь «основа» — общий префикс минимум в 2 символа и минимум 60% длины
более короткого слова, а не лингвистический стеммер.

Прошедшие проверки кандидаты одного окна ранжируются отдельно. Берутся
совпадения, отстающие от лучшего `WRatio` менее чем на 5 баллов. Для
разрешения близких результатов к `WRatio` прибавляется `QRatio / 1000`,
затем `_adjust_score()` учитывает контекст:

| Контекст | Поправка |
|---|---:|
| Маркер `жк`, `район`, `округ`, `метро` или `вид`/`видом` при соответствующем типе | +10 |
| `на` при округе/районе или `в` при ЖК, если первое слово окна связано с именем | +5 |
| `на` при ЖК в таком же условии | −5 |
| Разрешение ничьей по типу: округ, район, метро, ЖК, опция, группа опций | +0.5, +0.4, +0.3, +0.2, +0.1, +0.0 |

Поправки служат **для выбора между уже допустимыми кандидатами**, не для
прохождения порога. Некоторые бытовые слова (`университет`, `аэропорт` и др.)
не становятся станцией метро без явного маркера. После поправок остаются
варианты в пределах 5 баллов от лидера или с тем же каноническим именем.
Среди перекрывающихся окон первыми идут окна с наибольшей итоговой оценкой,
при равенстве — более длинные. Совпадения одного типа на одном участке не
дублируются; неоднозначность разных имён или типов отражается в `warnings`.
`EntityMatch.score` содержит исходную оценку `WRatio` с небольшой добавкой
`QRatio / 1000`, **без** контекстных поправок; итоговый `best_score` окна
используется внутри матчера для сортировки.

## Что происходит с оставшимся текстом

После объединения занятых `Span` парсер находит незанятые куски. Он делит их
по `,`, `;`, точке вне числа и союзам `и`, `а`, `но`; точка в `1.5` не режет
число. Значимые фрагменты превращаются в `warnings`, а похожие на опции
короткие фразы дополнительно попадают в `option_candidates` для возможного
ИИ-разрешения. Ни один непонятый фрагмент не должен исчезать молча.

## Не путать с семантическим кэшем ИИ

В `docs/ai-enrichment-architecture.md` встречается ранняя идея `weights.json`
для ассоциаций «слово → фильтр». В текущем коде такого файла и расчёта весов
слов нет. Опциональный ИИ-слой кодирует **целую строку** локальной моделью в
вектор из 384 чисел (`app/ai/embeddings.py`), а `app/ai/memory.py` сравнивает
векторы по косинусному расстоянию. Это отдельная механика кэша; её численные
компоненты не являются оценками токенов из `entity_match.py`.
