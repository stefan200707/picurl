# Фронт на C++ для picurl: оценка возможности и варианты

Документ отвечает на вопрос «можно ли сделать фронтенд этого проекта на C++ и как именно».
Это **оценка и предложение**, а не принятое решение: кода на C++ в репозитории нет и
данный документ его не добавляет.

Все ссылки на файлы и строки **сверены с кодом 2026-08-21**. Строчные номера — самая
скоропортящаяся часть текста: если они разошлись, верить надо коду, а вывод §1 от сдвига
строк не зависит.

---

## 1. Краткий вердикт

**Технически — да, без единой строчки изменений в бэкенде.** Фронт здесь общается с
сервисом только по HTTP+JSON (две ручки данных + одна ручка здоровья), а весь контент
ответа уже структурирован pydantic-моделями. Любой язык с HTTP-клиентом и JSON-парсером
годится, C++ — тоже.

**Практически — выгода отрицательная в четырёх сценариях из шести.** Ключевой блокер не
в бэкенде, а в **Яндекс.Картах**: у них есть JS API (используется сейчас) и мобильные
SDK, но **нет desktop-C++ SDK**. Любой «настоящий» нативный C++-фронт либо тащит внутрь
себя браузерный движок (и тогда карта всё равно рисуется на JS), либо отказывается от
Яндекс.Карт в пользу собственного рендера тайлов.

Рекомендация по умолчанию — **вариант 0 (не делать)**. Если C++ обязателен как
требование, то по соотношению «цена/результат» побеждает **вариант E** (нативная
оболочка вокруг существующей веб-страницы, ~1-2 дня), а «честный нативный клиент» —
это **вариант B** (Qt/QML + свои тайлы, ~3-4 недели).

**Полная HTTP-поверхность приложения** (это всё, что фронту вообще доступно):

| Метод и путь | Где | Нужен ли фронту |
|---|---|---|
| `POST /build-url` | `endpoints.py:47` | **да** — единственный вход для текста запроса |
| `POST /api/geo/route` | `endpoints.py:128` | **да** — пересчёт маршрута при смене способа перемещения; отвечает `{route, all_modes}`, причём `all_modes` считается всегда для всех четырёх режимов |

существующий**. Это меняет планку приёмки: новый клиент сравнивается не с нулём, а с
работающей страницей на 744 строки.

## 3. Что фронт этого проекта обязан уметь

Список выведен из контракта, а не из вкусов — он же служит критерием приёмки для любого
варианта ниже.

1. Отправить свободный русский текст в `POST /build-url`.
2. Показать `url` — итоговую ссылку на pik.ru (и дать её открыть/скопировать).
3. Показать `criteria` — распознанные критерии (произвольный словарь, ключи меняются).
4. Показать `result_count` (может быть `null` — это «не проверяли», а не «ноль»).
5. **Показать `warnings_detailed`** — с различением `category`/`severity`. Это не
   украшение: инвариант 1 («ничего не отбрасывается молча») распространяется и на UI.
   Клиент, рисующий только `url`, тихо съедает потерянные фильтры — то самое, против
   чего построен весь warning-канал.
6. Показать `map_config`: точку А (ЖК), точку Б (назначение), маршрут `route` и список
   `all_complex_routes` — ЖК, отсортированные по времени в пути.
7. Нарисовать карту с маркерами и линией маршрута.
8. Переключить `travel_mode` через `POST /api/geo/route`. Значения enum —
   `pedestrian | driving | transit | bicycle` (`app/geo/yandex_maps.py:50-56`); ответ
   содержит и выбранный `route`, и `all_modes` со всеми четырьмя, так что вкладки
   режимов рисуются из одного вызова.

Пункты 1-6 и 8 на C++ делаются тривиально. **Вся сложность сосредоточена в пункте 7.**

### 3.1. Модели, которые придётся описать в C++

Полный состав контракта — чтобы объём работы оценивался по фактическому JSON, а не
по памяти. `RouteLeg` выписан отдельно в §4, `GeoPoint` — `lat: float`, `lon: float`,
`name: str?`, `address: str?`, `point_type: str` (`origin` | `destination`).

| Модель | Где | Поля |
|---|---|---|
| `BuildUrlRequest` | `schemas.py:43` | `text` (min_length=1) |
| `BuildUrlResponse` | `schemas.py:56` | `url`, `criteria: dict[str, Any]`, `result_count: int?`, `warnings: list[str]`, `warnings_detailed: list[WarningDetail]`, `ai_used`, `ai_failed`, `ai_cache_hit`, `ai_explanation: str?`, `map_config: YandexMapConfig?` |
| `WarningDetail` | `schemas.py:9` | `text`, `category`, `severity` |
| `YandexMapConfig` | `yandex_maps.py:116` | `api_key: str?`, `script_url`, `auto_load: bool`, `center: [lat, lon]`, `zoom: int`, `point_a: GeoPoint?`, `point_b: GeoPoint?`, `route: RouteLeg?`, `all_complex_routes: list[RouteLeg]`, `selected_travel_time_min: int?`, `travel_mode` |
| `RouteRequest` | `schemas.py:131` | `origin: GeoPoint`, `destination: GeoPoint`, `travel_mode` (по умолчанию `pedestrian`) — **`GeoPoint` обязателен целиком, `lat`/`lon` не опциональны** |
| `RouteResponse` | `schemas.py:142` | `route: RouteLeg`, `all_modes: list[RouteLeg]` |

Два следствия для клиента:

- Почти всё **необязательно** (`result_count`, `map_config`, `point_a`/`point_b`, `route`).
  Пустой `map_config` или `route: null` — штатный ответ (запрос без гео-контекста), а не
  сбой: рисовать карту по nullable-полям, не падать и не показывать «ошибка сервера».
- Гео-модели объявлены с `model_config = ConfigDict(extra="ignore")`: сервер добавляет
  поля не ломая старых клиентов, и обратная сторона того же — C++-парсер обязан
  **игнорировать незнакомые ключи**, а не считать их ошибкой схемы.

Что фронту делать **не** нужно (и нельзя): считать дистанции, ранжировать ЖК,
резолвить справочники, собирать URL pik.ru. Всё это — инварианты 3 и 13 из `CLAUDE.md`,
живут на сервере; клиент любого языка остаётся тонким по построению. Именно поэтому
вопрос «на чём писать фронт» здесь и решается свободно.

## 4. Единственный настоящий блокер: карта

- Яндекс.Карты для desktop — это **JS API**. Официального C++ SDK нет; мобильные SDK
  (Android/iOS) на десктоп не переносятся.
- Тянуть растровые тайлы Яндекса напрямую в свой рендерер **в обход JS API/официальных
  SDK условиями использования не предполагается** — этот пункт требует юридической
  проверки до начала работ, а не после. Технически возможно ≠ разрешено.
- Значит у нативного C++ ровно три исхода:
  1. **встроить веб-движок** (QtWebEngine / WebView2 / WKWebView) и оставить ymaps как
     есть — карта остаётся JS, «нативность» касается только рамки вокруг неё;
  2. **сменить картографию** на OSM-тайлы (QtLocation, MapLibre) — юридически чисто,
     но визуально это уже не Яндекс.Карты;
  3. **отказаться от встроенной карты** и открывать `RouteLeg.yandex_maps_url` во внешнем
     браузере.

**Смягчающее обстоятельство:** маршрут клиенту считать не нужно. Бэкенд уже отдаёт
готовую геометрию — `RouteLeg.waypoints: list[list[float]]`, плюс `distance_m`,
`duration_min`, `formatted_duration`. Нативному клиенту остаётся нарисовать полилинию по
готовым точкам, а не интегрировать маршрутизатор. Это и делает вариант B выполнимым.

Полный состав `RouteLeg` (`app/geo/yandex_maps.py`) — это и есть модель, которую придётся
завести в C++: `origin`, `destination` (`GeoPoint`), `travel_mode`, `distance_m: float`,
`duration_min: int`, `duration_sec: int`, `formatted_duration: str`,
`formatted_distance: str`, `waypoints: list[list[float]]`, `yandex_maps_url: str`,
`summary_text: str | None`. Ни одно поле не требует пересчёта на клиенте — только
отображения.

Оговорка про качество этих точек: при наличии ключа `waypoints` приходят из реального
Routing API (`app/geo/yandex_maps.py:226`, `api.routing.yandex.net/v2/route`), а без
ключа — из геометрической аппроксимации
кривой Безье (`_generate_waypoints`, строки 179-206). На карте с настоящими улицами такая
линия будет заметно «проходить сквозь дома» — на текущей ymaps-странице это не так
бросается в глаза, потому что там рисуется поверх схемы. Нативный вариант этот дефект
**подсветит**, а не скроет.

## 5. Что придётся (и что не придётся) менять в бэкенде

**Не придётся ничего** для вариантов A, B, D, E: нативный процесс не браузер, CORS на
него не распространяется, а данных в ответе уже достаточно.

Придётся, точечно:

| Случай | Изменение |
|---|---|
| Вариант C (WASM в браузере с другого origin) | Добавить `CORSMiddleware` — сейчас его в `app/` нет вообще |
| Любой вариант, если клиент раздаётся пользователям | Обдумать `YandexMapConfig.api_key`: он **реально заполняется** из `settings.YANDEX_MAPS_API_KEY` (`yandex_maps.py:440,507`) и уезжает клиенту в JSON. Для браузера с доменным ограничением ключа это норма; для native-бинаря ограничение по HTTP Referer не работает. Плюс: ключ не вшит в бинарь, отзыв/ротация остаются серверными |
| Вариант F (C++ вместо Python) | Переписывание всего ядра — см. ниже, отклонён |

## 6. Варианты

### Вариант 0 — не внедрять C++-фронт (базовый)

Оставить `app/templates/index.html`. Ноль трудозатрат, ноль второго тулчейна.

**Аргумент за:** ни одна из семи функций фронта не упирается в производительность или в
доступ к железу — это форма ввода, список и карта. C++ здесь не даёт ни скорости
(узкое место — сетевой вызов к pik.ru и ИИ), ни возможностей, ни безопасности. Зато
добавляет в репозиторий с одним `verify.sh` на четыре Python-команды вторую систему
сборки, второй линтер, второй набор тестов и матрицу платформ.

**Когда неверен:** если фронт нужен как оффлайн-десктоп-приложение без браузера, или
требование «на C++» внешнее и не обсуждается.

---

### Вариант A — Qt 6 Widgets/QML + QtWebEngine

Полноценное десктоп-приложение: нативные списки/поля на Qt, а карта — `QWebEngineView`
со страницей ymaps, связь C++↔JS через `QWebChannel`.

- **Стек:** Qt 6.6+, `QNetworkAccessManager` (HTTP), `QJsonDocument` (JSON), QtWebEngine.
- **Объём:** ~2-3 недели.
- **Плюсы:** карта остаётся полноценной Яндекс-картой; кроссплатформенно; зрелый UI-тулкит.
- **Минусы:** QtWebEngine — это встроенный Chromium: +150 МБ к дистрибутиву, долгая
  сборка, регулярные security-обновления. Лицензия Qt — LGPLv3 (динамическая линковка)
  либо коммерческая. **Внутри всё равно исполняется JS** — «C++-фронт» здесь во многом
  номинален.
- **Вердикт:** работает, но платит максимальную цену за минимальную нативность.

---

### Вариант B — Qt 6 QML + QtLocation/MapLibre, без веб-движка ⭐ «честный натив»

Настоящий нативный клиент: карта рисуется своим рендерером по растровым/векторным
тайлам (OSM/MapLibre), маршрут — полилиния по `route.waypoints` с бэкенда, маркеры —
`point_a`/`point_b`, список ЖК — по `all_complex_routes`.

- **Стек:** Qt 6 QML + QtLocation (плагин OSM) или MapLibre Native; HTTP/JSON — Qt.
- **Объём:** ~3-4 недели (основное — карта и её взаимодействие со списком).
- **Плюсы:** никакого JS и Chromium; компактный бинарь; полный контроль над рендером;
  весь маршрутный расчёт остаётся на сервере — инвариант «дистанции считает бэкенд» не
  нарушается.
- **Минусы:** это **уже не Яндекс.Карты** — другая подложка, другие подписи, расхождение
  с ссылкой `yandex_maps_url`, которую откроет пользователь. Аппроксимация Безье станет
  визуально заметной (см. §4). Лицензия Qt.
- **Вердикт:** единственный вариант, где «на C++» означает что-то содержательное.
  Выбирать, если готовы сменить картографию.

---

### Вариант C — C++ → WebAssembly (Qt for WebAssembly / Dear ImGui + Emscripten)

Фронт пишется на C++, компилируется в WASM и работает в браузере.

- **Объём:** ~3-5 недель.
- **Плюсы:** C++ в браузере; ymaps доступен через `EM_JS`-интероп.
- **Минусы:** бандл 2-20 МБ против нынешних 744 строк HTML; canvas-рендер убивает
  доступность, выделение текста, поиск по странице и мобильную раскладку; отладка
  тяжёлая; нужен `CORSMiddleware`, если раздача не с того же origin. Главное — **нет
  мотива**: WASM оправдан переносом существующей C++-логики, а в этом репозитории
  C++-логики нет вообще.
- **Вердикт:** отклонить, если нет отдельного внешнего требования.

---

### Вариант D — консольный/TUI-клиент на C++

Минимальный честный C++-артефакт: `picurl-cli "хочу двушку у метро до 15 млн"` печатает
ссылку, критерии, `result_count`, раскрашенные по `severity` предупреждения и таблицу ЖК
со временем в пути; по запросу открывает `route.yandex_maps_url` в системном браузере.

- **Стек:** `cpr` (libcurl) + `nlohmann/json` + `FTXUI` (все MIT) или вовсе голый
  `libcurl`. ~300-500 строк.
- **Объём:** ~2-4 дня.
- **Плюсы:** дёшево, без лицензионных ловушек, кроссплатформенно, скриптуется, отлично
  подходит для демонстрации интеграции и для ручных прогонов формата «запрос → ссылка →
  критерии → ЖК с дистанциями → warnings», которого требует QA-раздел `CLAUDE.md`.
- **Минусы:** карты нет; на Windows кириллица в консоли требует возни (UTF-8 codepage,
  wide-API).
- **Вердикт:** лучший вариант, если цель — «показать C++-клиент», а не «заменить UI».

---

### Вариант E — нативная C++-оболочка вокруг текущей веб-страницы ⭐ «дёшево и полезно»

Бинарь на C++ (~50-100 строк, header-only `webview/webview`) открывает окно с системным
webview (WebView2 / WKWebView / webkit2gtk) и грузит `http://127.0.0.1:8000/`. Опционально
сам поднимает `uvicorn` как дочерний процесс и глушит его при выходе.

- **Объём:** ~1-2 дня.
- **Плюсы:** существующие 744 строки UI и полноценные Яндекс.Карты сохраняются как есть;
  дистрибутив на порядок легче варианта A (используется системный движок, не свой
  Chromium); получается настоящее десктоп-приложение с иконкой.
- **Минусы:** «C++» здесь — оболочка, а не интерфейс; на Windows нужен установленный
  WebView2 Runtime; поведение слегка различается между тремя системными движками.
- **Вердикт:** максимум пользы на единицу трудозатрат, если задача формулируется как
  «нужно десктоп-приложение».

---

### Вариант F — переписать HTTP-слой/ядро на C++ (Drogon/Crow/oat++)

Формально «сервер на C++, шаблон отдаёт он же».

- **Вердикт: отклонить.** Это не фронтенд, а замена бэкенда. Ядро проекта — regex-правила
  парсинга, rapidfuzz-матчинг, JSON-справочники, ИИ-обогащение, оба QA-корпуса и пороги
  (`coverage≥0.91/0.92`, `crashes=0`) — всё на Python и всё покрыто `pytest`. Порт означает
  переписать парсер вместе с накопленной историей дефектов и потерять весь QA-харнесс,
  который эту историю удерживает. Промежуточный «C++-BFF-прокси» перед FastAPI тоже
  бессмыслен: лишний сетевой хоп без единой новой функции.

## 7. Сравнение

| | 0. как есть | A. Qt+WebEngine | B. Qt+свои тайлы | C. WASM | D. CLI/TUI | E. webview-оболочка |
|---|---|---|---|---|---|---|
| Трудозатраты | 0 | ~2-3 нед | ~3-4 нед | ~3-5 нед | ~2-4 дня | ~1-2 дня |
| Правки бэкенда | нет | нет | нет | +CORS | нет | нет |
| Карта | ymaps | ymaps | OSM/MapLibre | ymaps | нет (внешняя ссылка) | ymaps |

## 8. Требования к любому C++-клиенту (если делать)

Это не общие слова, а места, где клиент этого конкретного сервиса ломается молча.

1. **`category` и `severity` парсить как строку с фолбэком, не как строгий `enum`.**
   Разметка warnings внедряется порциями (реализованы 2 шага из 5), новые категории
   появятся. Строгий `enum` даст либо исключение, либо тихое отбрасывание предупреждения —
   прямое нарушение инварианта 1. То же касается `travel_mode`.
2. **`criteria` — открытый словарь**, не структура с фиксированными полями: набор ключей
   `to_public_dict()` меняется вместе с парсером. Рендерить обобщённо (ключ → значение).
3. **`result_count == null` ≠ 0.** Разные вещи: «не проверяли» и «выдача пуста».
   Отдельно: при локационных фильтрах `result_count` вообще ничего не доказывает
   (см. `CLAUDE.md`, раздел про два бэкенда ПИК) — не подавать его как истину.
4. **UTF-8 сквозняком.** Русский текст в запросе и в ответе; на Windows — `wchar_t`-API
   либо явный UTF-8-манифест, для консоли — codepage 65001.
5. **Таймауты и сеть.** `POST /build-url` внутри ходит в pik.ru и, возможно, в ИИ —
   ответ может занять секунды. `POST /api/geo/route` считает маршрут **четырежды**
   (все режимы для `all_modes`, `endpoints.py:147-160`) и потому тоже не мгновенный.
   Асинхронно, с таймаутом и понятной ошибкой; «сервис не поднят» отличать от «сервис
   ответил ошибкой» через `GET /health`, а не по тайм-ауту.
6. **`url` — не рендерить как HTML.** Открывать во внешнем браузере, экранировать при
   выводе (текст пользователя доезжает до UI в предупреждениях).
7. **Модели ответа — не писать руками с нуля.** `GET /openapi.json` отдаёт актуальную
   схему всех ручек; из неё генерируются структуры (или хотя бы сверяются глазами при
   каждом изменении `schemas.py`). Ручная копия контракта разъезжается молча — ровно тот
   класс дефекта, который в Python-части ловят два QA-корпуса, а у C++-клиента ловить
   будет нечем.
8. **Инфраструктура:** `cpp-client/` + `CMakeLists.txt`, зависимости через
   FetchContent/vcpkg, `.clang-format`, тесты на Catch2/GoogleTest и **отдельный шаг в
   `.workflow-ai/verify.sh`** — сейчас он гоняет только Python и C++-регрессию не увидит.
   Python-пороги QA при этом не трогать: они меряют парсер, а не клиент.

## 9. Рекомендация

1. **По умолчанию — вариант 0.** Существующая страница закрывает все семь функций,
   включая карту; C++ не даёт ни одной новой возможности, но добавляет тулчейн.
2. **Если нужен десктоп — вариант E** (1-2 дня): готовое приложение, UI и Яндекс.Карты
   сохраняются без изменений.
3. **Если требование «на C++» содержательное и картография может смениться — вариант B**
   (3-4 недели), предварительно получив ответ по тайлам (§4) и приняв, что подложка
   перестанет быть Яндексовой.
4. **Если нужен дешёвый C++-артефакт и/или инструмент ручных прогонов — вариант D**
   (2-4 дня); он же полезен независимо от судьбы UI.
5. **Варианты A, C и особенно F не рекомендуются:** A платит Chromium'ом за номинальную
   нативность, C решает задачу, которой в проекте нет, F — переписывание ядра под видом
   фронта.

**Предлагаемый первый шаг**, если решение положительное: сделать вариант D за 2-4 дня как
проверку интеграции (HTTP, UTF-8, разбор `warnings_detailed`, CMake в `verify.sh`). Он
даёт 80% ответа на вопрос «во что обойдётся C++ в этом репозитории» при 5% бюджета
варианта B, и его код (модель ответа + HTTP-слой) переиспользуется в B и E целиком.
