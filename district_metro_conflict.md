# Проблема: Конфликт сущностей "Метро" и "Район" при парсинге

## Описание проблемы

В вашем запросе возникла ситуация, когда названия локаций (например, «Строгино», «Митино») существуют одновременно в двух справочниках: как **станции метро** (`metro.json`) и как **районы** (`districts.json`).

В ответе сервиса (который вы привели в примере) эти сущности попали **только в массив `metro`**, а массив `counties` заполнился значениями ЗАО и СЗАО. При этом районы в критериях (`districts`) отсутствуют, из-за чего в итоговом URL параметры для районов (`districtLocations`) не сформировались.

### Почему так происходит?

В модуле `app/parsing/entity_match.py` применяется логика скользящего окна и нечеткого поиска (rapidfuzz). Когда парсер находит совпадение:
1. Он находит, что слово «Строгино» на 100% совпадает и с районом, и с метро.
2. Алгоритм корректирует итоговый балл (score) в зависимости от контекста. Если в тексте было слово «метро» (триггер), то категория `metro` получает бонус `+10` баллов.
3. Затем происходит **жесткая фильтрация пересекающихся спанов** (функция `_is_overlap`). Парсер берёт сущность с наибольшим баллом (например, метро «Строгино»), добавляет её в результат и **отбрасывает все остальные кандидаты**, пересекающиеся с этим же фрагментом текста.

В результате альтернативный вариант (район «Строгино») удаляется. Сервис генерирует предупреждение (warning) о неоднозначности, но в итоговом `Criteria` (и, соответственно, в URL) остается только один тип локации.

---

## Что с этим делать?

Поскольку на сайте `pik.ru` фильтры по метро и по районам независимы (и поиск по району может выдать больше квартир, чем поиск только по радиусу от станции метро), отбрасывать один из вариантов — значит потенциально терять часть подходящих пользователю квартир.

### Возможные варианты решения:

#### Вариант 1: Разрешить извлечение обеих сущностей (Рекомендуемый)
Нужно изменить логику проверки на пересечение спанов (`used_spans`) так, чтобы она разрешала брать **разные типы сущностей** на одном и том же фрагменте текста, если их скор одинаково высок (или разница минимальна).

**Как исправлять:**
В файле `app/parsing/entity_match.py`:
1. Вместо хранения просто координат в `used_spans = []`, хранить кортежи: `(span, type)`.
2. При проверке на пересечение проверять, совпадает ли еще и тип:
```python
if any(_is_overlap(c["span"], used_span) and c["matches"][0][1] == used_type for used_span, used_type in used_spans):
    continue
```
Таким образом, «Строгино» будет добавлено и в список `metro`, и в список `districts`. 
*Примечание:* Это приведёт к тому, что в URL будут добавлены как `metroStations=...`, так и `districtLocations=...`. Сайт ПИКа обработает такой запрос, расширив зону поиска (выдаст квартиры и в районе, и у метро).

#### Вариант 2: Жёсткое ограничение контекста (триггеров)
Сейчас бонус от слова «метро» может распространяться на всё перечисление («метро Строгино, Митино, Мякинино»).
Если мы хотим, чтобы без явного указания парсер предпочитал более широкую зону (район), то нужно:
**Как исправлять:**
1. Ограничить бонус триггеров: давать `+10` только первому слову после триггера.
2. Базовая иерархия (которая уже есть в коде: район `0.4` > метро `0.3`) автоматически выберет район для слова «Митино», если перед ним нет слова «метро».
*Минус:* Мы всё равно теряем вторую сущность (будет либо только район, либо только метро).

#### Вариант 3: Окно уточнения (Multi-match на уровне Schema)
Доработать `Criteria`, объединив метро, районы и округа в единый массив `locations`, где каждый элемент знает свои ID во всех справочниках.
**Как исправлять:**
В `app/parsing/schema.py` и `url_builder.py` реализовать логику, которая при наличии у локации `metro_id` и `district_id` добавляет их оба в итоговый URL-запрос.

## Итог и план действий

Оптимально применить **Вариант 1**. 
Для этого зайдите в `app/parsing/entity_match.py`, найдите цикл заполнения финальных результатов (строка ~340):
```python
    used_spans_with_type = []
    for c in candidates:
        best_matches = c["matches"]
        top_match = best_matches[0]
        score, etype, entry = top_match
        
        # Проверяем, был ли уже использован этот спан ДЛЯ ЭТОГО ЖЕ ТИПА сущности
        if any(_is_overlap(c["span"], used_span) and used_type == etype for used_span, used_type in used_spans_with_type):
            continue

        used_spans_with_type.append((c["span"], etype))
        # ... добавление в final_matches
```
Это позволит вашему сервису извлекать максимум фактов из текста пользователя, а URL Builder корректно добавит и `districtLocations`, и `metroStations` в ссылку.
