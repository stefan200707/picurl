# 03 — Справочники и скрипт обновления — Milestone 2

> Прочитай `_conventions.md` и `docs/pik-url-schema.md` перед началом.

## Контекст

Матчинг сущностей (метро/округа/районы/ЖК/программы) требует локальных
справочников. Из-за закономерности single-путь/multi-query **на каждую сущность
нужны обе формы**: человекочитаемый **слаг** (для одиночного выбора в пути) и
числовой **id/GUID** (для multi-select в query).

## Цель

1. Слой справочников: JSON-файлы + загрузчик `app/reference/loader.py`.
2. Скрипт `app/reference/refresh.py`, собирающий справочники перебором
   выпадающих списков на странице фильтра `pik.ru`.

## Формат справочников

Каждый JSON — список записей единого вида. Пример `metro.json`:

```json
[
  { "name": "Аэропорт Внуково", "slug": "m-aeroport-vnukovo", "id": "<GUID>",
    "aliases": ["Внуково", "Аэропорт"] }
]
```

Файлы:
- `metro.json` — метро (slug вида `m-...`, id = GUID).
- `districts.json` — районы (только id, поле `districtLocations`; slug может
  отсутствовать — район всегда уходит в query).
- `counties.json` — округа (slug вида `zao`, числовой id для `districtCounties`).
- `complexes.json` — ЖК (slug для пути + числовой `blocks` id).
- (опц.) `benefits.json`, `option_groups.json`, `options.json` — слаги
  `currentBenefit` / `optionGroups` / `options` (собрать заодно, см. ниже).

Поле `aliases` — заранее заготовленные разговорные варианты («Сокол» и т.п.),
помогают матчингу.

## loader.py

- Функции загрузки каждого справочника в память (с кэшированием, напр.
  `functools.lru_cache`), возврат типизированных структур (pydantic-модели
  записей или dataclass).
- Единая точка `load_all()` → удобный агрегат для матчера (шаг 05).
- Пути к JSON — относительно пакета (`importlib.resources` или `Path(__file__)`).

## refresh.py

- CLI-скрипт (`python -m app.reference.refresh`), который тянет данные с `pik.ru`
  (перебор выпадающих списков/справочных эндпоинтов) и **перезаписывает** JSON.
- Это **единственное место**, где допустим сетевой доступ вне валидатора; он
  запускается вручную/по расписанию, **не** в рантайме запроса.
- Заодно (открытые вопросы, мелкое): собрать полный список слагов
  `optionGroups` / `options` / `currentBenefit`, проверить «Тип паркинга».
- Идемпотентность и стабильная сортировка записей (чтобы диффы были читаемыми).

## Требования к результату

- Стартовые JSON заполнены хотя бы репрезентативным подмножеством реальных данных
  (как минимум записи, используемые в тестах: «Аэропорт Внуково», «ЗАО»/`zao`,
  «Бабушкинский»/`203`, «Мичуринский парк»/`1108`, «Сокол»).
- `loader` покрыт юнит-тестами (загрузка, кэш, поиск по имени/алиасу).
- `refresh.py` — сетевые вызовы замоканы в тестах; проверяется парсинг ответа в
  корректный формат записи, а не реальный поход в сеть.
