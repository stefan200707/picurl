# 16 — Гео-слой: координаты ЖК, «центр Москвы», POI (школы/сады/магазины/парковки/лес) — Milestone AI-1

> Прочитай `_conventions.md` и `docs/ai-enrichment-architecture.md` (промпт
> 15) перед началом.

## Контекст

Чтобы ИИ (промпт 18) не «придумывал» гео-факты, а ранжировал/интерпретировал
поверх реальных данных, бэкенду нужен детерминированный гео-слой:
координаты ЖК, эвристика «в центре ли это», и наличие рядом POI-категорий
(школы, детские сады, магазины/продуктовые, парковки, лес/парк). Часть таких
запросов («рядом лес», «нужна парковка») уже сейчас можно распознать regex-ом
как структурный факт — это и есть первая, самая дешёвая линия защиты от
лишних вызовов ИИ.

## Задача

### 1. Координаты ЖК

`app/reference/refresh.py` тянет `api.pik.ru/v2/block` с `metadata=1` — на
момент реализации проверить, отдаёт ли этот эндпоинт координаты (поле вида
`coordinates`/`lat`/`lng` в сыром JSON). Если да — добавить их в
`BlockPayload` и прокинуть в справочник. Если нет — задокументировать
альтернативный источник (например, карточка ЖК на `pik.ru/{slug}` отдаёт
координаты в структуре страницы/встроенном JSON, либо использовать открытый
геокодер по адресу ЖК) в `docs/ai-enrichment-architecture.md`.

Добавить в `app/reference/loader.RefEntry` два новых опциональных поля:
`lat: float | None = None`, `lon: float | None = None` (не ломает существующие
записи — pydantic-модель с дефолтами, `extra="forbid"` не задет, т.к. поля
теперь часть контракта). Расширить `complexes_from_blocks()` в `refresh.py`,
чтобы координаты подтягивались автоматически при `refresh`, но при этом мёрж
(`merge_entries`) не должен затирать вручную докуренные координаты, если
API их не отдаёт (тот же принцип, что уже применяется к `slug`/`id`/`aliases`).

### 2. Эвристика «центр Москвы»

Чистая функция в `app/geo/distance.py`:

- `haversine(lat1, lon1, lat2, lon2) -> float` (метры) — без внешних
  зависимостей (`math`), покрыть юнит-тестом на известных парах координат.
- `is_center(lat, lon, radius_m: float = ...) -> bool` — точка отсчёта и
  радиус вынести в константы модуля с комментарием, что это осознанная
  эвристика (например, центр — координаты Кремля, радиус — граница ЦАО/ТТК
  по прямой, а не по факту административных границ округов). Явно
  задокументировать в `docs/ai-enrichment-architecture.md`, что это
  приближение, и что финальное слово по спорным случаям (граница центра)
  может оставаться за ИИ/картой памяти (промпт 17), а не за этой эвристикой.
- Тесты: несколько реальных ЖК из `complexes.json` с известными координатами
  (после п.1) — часть внутри радиуса, часть снаружи.

### 3. POI-категории и источник данных

`app/geo/poi.py`:

- `class POICategory(StrEnum)`: `SCHOOL`, `KINDERGARTEN`, `SHOP`,
  `PARKING`, `PARK_FOREST`, `OTHER`.
- Функция получения POI рядом с точкой: `async def fetch_poi(lat, lon,
  category: POICategory, radius_m: int) -> POIResult` (count + ближайшее
  расстояние). Источник данных — решить на месте реализации между (а)
  собственными карточками `pik.ru` (инфраструктура ЖК на странице комплекса,
  если API её отдаёт) и (б) внешним открытым источником (Overpass API поверх
  OpenStreetMap — бесплатно, без ключа, но с лимитами на частоту запросов).
  **Это сетевой вызов, поэтому он не должен выполняться в рантайме на каждый
  HTTP-запрос** — он выполняется офлайн, как `refresh.py` (промпт 03) и
  `refresh_poi.py` ниже, результат кэшируется на диск/в БД.
- Локальный кэш `app/reference/poi_cache.json` (или таблица в БД — см. промпт
  17, если решено хранить факты сразу в Postgres, тогда отдельный JSON не
  нужен, использовать `ai_structured_facts` из промпта 17 с `source="geo"`).
  Выбрать один вариант и явно задокументировать — не дублировать источник
  правды.
- CLI-скрипт `app/geo/refresh_poi.py` (`python -m app.geo.refresh_poi`),
  аналог `app/reference/refresh.py`: проходит по ЖК с известными координатами,
  тянет POI по всем категориям, пишет в кэш. Сетевые вызовы в тестах —
  замоканы, как и везде в проекте.

### 4. Распознавание POI-требований в тексте (первая линия защиты от вызовов ИИ)

Новый модуль `app/parsing/rules/poi.py`, `extract_poi_requirements(text) ->
tuple[list[POIRequirement], list[Span]]` — по аналогии с остальными правилами
в `app/parsing/rules/`. Явные ключевые слова уже сейчас регексом сводятся к
категории без всякого ИИ: «школа/школы», «садик/детский сад», «магазин/
продукты/продуктовый», «парковка/паркинг», «лес/парк/зелень». Каждое
совпадение → `POIRequirement(category=..., raw_phrase=...)`, `consumed_spans`
как у прочих правил.

Добавить в `Criteria` (`app/parsing/schema.py`) новые поля:
`poi_requirements: list[POIRequirement] = Field(default_factory=list)` и
`center_requested: bool = False` (детектится тем же/соседним правилом на
явное «в центре»/«в центре Москвы»). `POIRequirement` — pydantic-модель
(`category: POICategory`, `raw_phrase: str`, `max_distance_m: int | None =
None` — если пользователь явно назвал расстояние, например «школа в 300
метрах»). Подключить `extract_poi_requirements` в `apply_rules()`
(`app/parsing/rules/__init__.py`).

**Важно:** это поле **не** обязано резолвиться в URL `pik.ru` (у сайта нет
фильтра «рядом школа») — оно используется только гео/ИИ-слоем (промпты 18–19)
для сужения `criteria.complexes`. `url_builder` (промпт 07) эти поля
игнорирует, они не должны попадать в `to_query_dict()`.

  на `extract_poi_requirements` (`tests/parsing/test_rules.py`, табличные,

  не нарушена, существующие тесты `tests/parsing/test_schema.py` не ломаются.
- `uv run pytest`, `uv run ruff check` зелёные.
