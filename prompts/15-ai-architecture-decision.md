# 15 — Архитектурное решение: ИИ-обогащение как ограниченный fallback — Milestone AI-0

> Прочитай `_conventions.md` целиком, включая раздел «Жёсткие архитектурные
> инварианты», ПЕРЕД тем как начинать. Этот промпт — не про код, а про
> проектное решение и живой документ, на который опираются все следующие
> промпты (16–21). Ничего не программировать по существу, кроме скелета
> конфигурации/директорий.

## Контекст и почему это меняет инвариант проекта

Исходный инвариант проекта (`_conventions.md`, п.1): «Никаких вызовов LLM/
внешних API в рантайме». Это было верно для v1 (детерминированный парсинг
структурных фактов — комнатность, цена, площадь, этаж, отделка, метро/округа/
районы/ЖК по точному матчингу и rapidfuzz). Открытый вопрос №6
(`_open-questions.md`) прямо резервировал «эмбеддинги/векторный поиск» как
отдельную фичу вне scope v1 — теперь она в scope.

Новая задача явно требует ИИ для класса запросов, которые принципиально не
решаются regex/rapidfuzz по справочнику имён: пользователь описывает
**желаемое окружение** («трёшка в центре, рядом продуктовые, детсады и школы»,
«у леса», «с парковкой»), а не структурный фильтр из URL-схемы `pik.ru`. Для
таких запросов нужно:

1. Понять, какие ЖК считаются «в центре», в каком они районе/округе/у какого
   метро — сопоставить со справочником `app/reference/complexes.json`.
2. Сопоставить это с данными о том, что реально есть рядом с ЖК (школы,
   детсады, магазины, парковки, лес/парк) — из карточек/карты на сайте `pik.ru`
   или из независимого гео-источника.
3. Ответить пользователю релевантным подмножеством ЖК, а не просто вернуть
   URL со слишком широким фильтром.

Это ИИ-обогащение **поверх** детерминированного бэкенда, не вместо него.

## Новый (уточнённый) инвариант — заменяет п.1 в `_conventions.md`

> **ИИ — это ограниченный fallback, а не источник истины.** Основной
> детерминированный пайплайн (`parse → build_url → validate`, промпты 00–14)
> остаётся полностью самодостаточным и не должен требовать сети/ИИ для работы.
> ИИ (Anthropic Claude, см. `docs/ai-enrichment-architecture.md`) вызывается
> **только** когда после детерминированного парсинга и справочного/гео-слоя
> остаётся нераспознанный семантический остаток запроса (POI-требования:
> школы/детсады/магазины/парковки/лес — или неоднозначное «в центре»,
> которые не сводятся к точному/нечёткому матчингу по справочнику). Каждый
> ответ ИИ **обязан** сохраняться в карту памяти (промпт 17) и по возможности
> дожиматься до детерминированного факта (промпт 20), чтобы **со временем доля
> запросов, требующих реального обращения к ИИ, снижалась**. ИИ никогда не
> является единственным способом ответить на регулярно повторяющийся вопрос —
> это явное требование задачи, а не опция.

Обнови текст инварианта №1 в `_conventions.md` (см. раздел «Обнови
`prompts/_conventions.md` и README» ниже) — не удаляй старый текст целиком,
дай ссылку «см. промпт 15» и кратко перескажи новое правило.

## Целевая архитектура (зафиксировать в `docs/ai-enrichment-architecture.md`)

Создать новый документ (по аналогии с `docs/pik-url-schema.md` — живой
источник правды для этой подсистемы). Он должен описывать:

### Поток запроса (текстово, схема ASCII/список шагов)

```
text
  │
  ▼
parse(text)                         # промпты 04-06, без изменений
  │  Criteria (структурные факты) + warnings + poi_requirements (промпт 16)
  ▼
нужно ли гео/POI-обогащение?        # criteria.poi_requirements непусты
  │                                 # ИЛИ criteria.center_requested
  │ нет ──────────────────────────────────────► пропустить блок целиком
  ▼ да
1. deterministic geo-слой (промпт 16)
   — координаты ЖК, is_center по фиксированному радиусу от центра Москвы,
   — уже ПРОМОУТНУТЫЕ факты из app/reference/*.json (промпт 20)
   если все нужные факты уже есть детерминированно → ai_used=False, ИИ не вызывается
  │ факты неполные
  ▼
2. карта памяти (промпт 17): structured facts (по subject+fact_type)
   и/или semantic cache (embedding нераспознанного остатка текста)
   если найдено с достаточной уверенностью → ai_used=False, cache_hit=True
  │ не найдено
  ▼
3. вызов Claude (промпт 18), c контекстом = короткий шорт-лист кандидатов
   ЖК + уже известные факты (ИИ не придумывает гео, а ранжирует/интерпретирует
   поверх данных, которые ему передал бэкенд — это и есть "запрос в ИИ после
   анализа бэком" из формулировки задачи)
   → структурированный JSON-ответ, провалидирован против справочника
   → записан в карту памяти (structured + semantic)
   ai_used=True
  │
  ▼
merge в Criteria (сузить criteria.complexes) → build_url → validate → ответ
```


### Ключевые решения, которые нужно закрепить в документе

- **Провайдер ИИ:** Anthropic Claude через официальный SDK (см. project skill
  `claude-api` — свериться с ним за актуальным списком моделей/цен на момент
  реализации промпта 18, не хардкодить здесь конкретный dated-снэпшот модели).
  Модель — конфигурируемая через `AI_MODEL_NAME` (env), с рекомендацией
  использовать наиболее дешёвую/быструю модель, способную на структурированный
  JSON-вывод для классификации/сопоставления (эскалация на более сильную
  модель — не в v2, оставить как будущее расширение).
- **Эмбеддинги для семантического кэша** — не через Anthropic (у Claude нет
  публичного embeddings API); использовать локальную модель без
  дополнительного платного вызова на каждый запрос (см. промпт 17) — это
  явно снижает частоту платных вызовов и соответствует требованию задачи.
- **Хранилище карты памяти** — PostgreSQL + расширение `pgvector` (project
  skills `postgres`, `pgvector-semantic-search`); это первая зависимость от
  внешней БД в проекте — задокументировать как осознанное расширение стека
  (см. «Стек» в CLAUDE.md, промпт 21 добавит туда пункт).
- **Не ломать v1.** Ни один из промптов 00–14 не переписывается по существу;
  новый функционал подключается через новые опциональные поля `Criteria`
  (`poi_requirements`, `center_requested` — промпт 16) и новый блок в
  `POST /build-url` (промпт 19), включаемый по фиче-флагу
  `AI_ENRICHMENT_ENABLED` (по умолчанию `false` в тестах/CI — реальные вызовы
  ИИ и БД в тестах всегда замоканы, как и `validator`/`refresh`).
- **Отказоустойчивость.** Как и `validator.py` (промпт 08), сбой ИИ-слоя
  (таймаут, ошибка сети, невалидный JSON, недоступна БД) не должен ронять
  основной пайплайн — деградация до best-effort с warning, тот же паттерн,
  что уже есть в `app/api/endpoints.py` для `validate()`.
- **Защита от галлюцинаций.** Ответ ИИ валидируется против переданного
  бэкендом шорт-листа справочника: если модель ссылается на ЖК/id, которых не
  было в контексте, — эта часть ответа отбрасывается с warning, а не
  прокидывается в URL как есть (это прямое требование «исправить опасную
  логику» — нельзя молча доверять свободному выводу модели).
- **Бюджет.** Максимум один вызов ИИ на один HTTP-запрос `POST /build-url`
  (никаких циклов уточнений в v2), с таймаутом и одной попыткой ретрая.

## Конфигурация (скелет, без бизнес-логики)

Завести `app/config.py` (или `app/ai/config.py`) с pydantic-settings классом,
читающим окружение: `AI_ENRICHMENT_ENABLED` (bool, default `False`),
`ANTHROPIC_API_KEY`, `AI_MODEL_NAME`, `DATABASE_URL`, `INTERNAL_REFRESH_TOKEN`
(из промпта 14 — консолидировать конфиг в одном месте, а не разбрасывать
`os.environ` по модулям). Ничего не хардкодить как дефолт для секретов.
