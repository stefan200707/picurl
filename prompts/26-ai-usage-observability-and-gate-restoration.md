# 26 — Наблюдаемость вызовов ИИ и возврат fallback-гейтов — Milestone AI-11

> Прочитай `_conventions.md`, промпт 20, `app/ai/enrichment.py` перед началом.
> Это финальный шаг серии 22–26 — переводит решение «когда ИИ снова только
> fallback» с даты/ощущения на измеримые цифры.

## Контекст

В `app/ai/enrichment.py:191-204` оба условия, которые должны ограничивать
вызов ИИ только реально нужными случаями, сейчас закомментированы —
`enrich()` вызывается на каждый запрос безусловно:

```python
# Пока что все запросы идут в нейронку
# if not criteria.poi_requirements and not criteria.center_requested:
#     return EnrichmentResult.noop()
...
# Пока что полностью все запросы идут через нейронку (полное обогащение)
# if fully_resolved(known, criteria, candidates):
#     return EnrichmentResult.from_deterministic(known)
```

Это осознанное временное состояние (комментарии явно это фиксируют), а не
баг — раскомментировать преждевременно, до закрытия пробелов из промптов
22–25, означало бы, что сложные запросы начнут просто терять смысл в
`warnings` вместо обработки. При этом промпт 20 обещал метрику «доля ИИ-вызовов
снижается» через таблицу `ai_call_log`, но по факту она не построена — в коде
только заглушка-комментарий (`app/ai/promotion.py`, конец файла:
«actual AI metrics would come from an ai_call_log table as suggested»).
Без этой таблицы решение «пора включать гейты» будет приниматься на глаз, что
и привело к нынешнему состоянию «пока что все запросы идут в нейронку» без
даты пересмотра.

## Задача

### 1. Таблица `ai_call_log`

Миграция (`app/ai/migrations/`, по аналогии с промптом 17) с полями как
минимум: `occurred_at`, `had_poi_or_center` (bool — сработал бы старый гейт 1),
`fully_resolved_deterministically` (bool — результат `fully_resolved()`,
**вычисляется и логируется всегда**, даже пока гейт 2 закомментирован и не
влияет на реальный ответ — это и есть измерение «что было бы, если включить»),
`cache_hit` (bool), `ai_called` (bool), `criteria_changed_by_ai` (bool —
отличался ли итоговый `criteria` после ИИ от того, что дал бы детерминированный
слой). Писать из `enrich()` при каждом вызове, не только при успехе.

### 2. Отчёт

`python -m app.ai.promotion --report` (или отдельная команда
`python -m app.ai.usage_report`, выбери одно место, не дублируй) — за период
показывает: всего запросов → % с `had_poi_or_center` → из них % где
`fully_resolved_deterministically` (это и есть кандидаты на «гейт 2 спас бы
вызов ИИ») → % `cache_hit` → % где `criteria_changed_by_ai` (реальная польза
от вызова, а не просто факт вызова).

### 3. Критерий возврата гейтов (зафиксировать, не только измерить)

В `docs/ai-enrichment-architecture.md` зафиксировать конкретное численное
условие для возврата обоих `if`-блоков в `enrich()`, например (числа обсуждаемы,
но должны быть числами, не «когда почувствуем») — «гейт 2 включаем, когда
`fully_resolved_deterministically` держится ≥ 90% над окном ≥ N запросов после
промптов 22–25» — и отдельно то же для гейта 1 через долю
`had_poi_or_center=false` среди `criteria_changed_by_ai=true` (если ИИ почти
никогда не меняет критерии для запросов без POI/центра — значит и общий
резолвинг опций из промпта 25 покрывает их без замены на гейт 1... уточни
взаимодействие с промптом 25 по месту, т.к. он добавляет третий повод звать
ИИ, не покрытый исходным гейтом 1 — гейт 1 в текущей форме нужно расширить
проверкой и на «есть нераспознанные опционо-подобные фрагменты», иначе его
включение сломает промпт 25).

### 4. Сам возврат гейтов

Только когда метрика по п.3 выполнена на реальных/тестовых данных —
раскомментировать оба блока (с учётом расширения гейта 1 под промпт 25) и
убрать комментарии-пометки «пока что». Это последний шаг, не делать заранее.

### 5. Предварительные условия из `AUDIT_REPORT.md` (2026-07-22, раздел 1) — закрыть ДО или ПАРАЛЛЕЛЬНО с п.1–4

Независимый аудит нашёл ту же проблему («гейты закомментированы, ИИ дёргается
всегда»), что и этот промпт, плюс три смежных несоответствия, которые метрика
из п.1–4 сама не увидит, потому что они либо про безопасность вызова, либо про
то, что конфиг молча не делает того, что должен:

- **Безопасность вызова `agy` (не было в AUDIT_REPORT — обнаружено при сверке
  рабочего дерева, важнее самой метрики).** `app/ai/client.py:call_antigravity`
  сейчас запускает CLI с флагом `--dangerously-skip-permissions`. `agy` —
  агентный CLI (не просто «однострочный» вызов модели), и промпт, который он
  получает, включает `system_prompt` + **полный исходный текст пользователя**
  (`user_query`, см. `docs/backend-ai-balance.md`, п.3a) без какой-либо
  санитизации. Это классическая поверхность prompt injection → RCE: значение
  `text`, введённое кем угодно через `/build-url`, попадает в промпт агента, у
  которого явно сняты ограничения на действия. Восстанавливать fallback-гейты,
  не убрав этот флаг, — чинить частоту вызова опасного пути, а не сам путь.
  **Убрать флаг (или заменить на явный allow-list разрешённых
  действий/read-only режим, если такой у `agy` есть) — обязательный шаг этого
  промпта, не отдельная задача на потом.**
- **`AI_PROVIDER`/`AI_MODEL_NAME`/`ANTIGRAVITY_MODEL` всё ещё рассинхронизированы
  (AUDIT_REPORT.md 1.4, уточнение).** В рабочем дереве `AI_PROVIDER` уже
  поменяли на `antigravity` (закрывает буквальную формулировку находки 1.4 —
  раньше был `claude` + модель Gemini), но `call_antigravity` читает модель из
  `settings.ANTIGRAVITY_MODEL`, а не из `AI_MODEL_NAME` — то есть
  `AI_MODEL_NAME: str = "gemini-3.5-flash"` по факту **не используется вообще**
  при дефолтном провайдере `antigravity` (он нужен только `call_claude`), а
  `ANTIGRAVITY_MODEL` по умолчанию `None` → `agy` запускается без `--model` и
  использует какую-то свою модель по умолчанию, не `gemini-3.5-flash`. Найденное
  несоответствие не устранено, а перевоплотилось: сейчас три поля отвечают за
  «какую модель звать» и явного соответствия «какое поле для какого провайдера»
  нет ни в коде, ни в `CLAUDE.md`. Привести к одному из двух вариантов: (а)
  `call_antigravity` читает `AI_MODEL_NAME`, `ANTIGRAVITY_MODEL` убрать; (б)
  задокументировать явно в `CLAUDE.md`/докстринге `Settings`, что `AI_MODEL_NAME`
  относится только к провайдеру `claude`, а `ANTIGRAVITY_MODEL` — только к
  `antigravity`, и оба имеют разумный ненулевой дефолт.
- **`README.md` всё ещё утверждает «никаких LLM в рантайме»** (AUDIT_REPORT.md
  1.3) — независимо от того, когда вернутся гейты, это предложение неверно уже
  сегодня (`AI_ENRICHMENT_ENABLED=True` по умолчанию). Поправить текст и
  добавить `ai_used`/`ai_cache_hit`/`ai_explanation` в пример ответа — не ждать
  завершения всей серии 22–26, это чисто документационная правка без риска.
