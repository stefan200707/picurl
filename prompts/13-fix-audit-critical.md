# 13 — Критические баги парсинга (аудит) — Milestone Hardening

> Прочитай `_conventions.md` перед началом. Источник этого промпта —
> `AUDIT_2026-07-18.md`, раздел «1. Критично»: три конкретных дефекта, которые
> реально искажают выдачу (не стиль, а неверный результат).

## Контекст

Независимый аудит (`AUDIT_2026-07-18.md`) нашёл три места, где regex/стоп-слова
слишком широкие или слишком узкие и молча портят критерии — то есть именно тот
класс «опасной/ошибочной логики», который просили исправить. Все три
воспроизводимы на реальных справочниках/текстах, без выдумывания кейсов.

## Задача

### 1. Реальные топонимы в `STOP_WORDS` блокируют матчинг сущностей

`app/parsing/stopwords.py` содержит `"люберцы"` и `"раменки"` в множестве
`STOP_WORDS` (строки ~127–128). Это не дискурсивный мусор, а реальные записи
справочников: `app/reference/districts.json` (район, алиас «Люберцы»/«Люберцах»)
и `app/reference/metro.json` (станции «Люберцы I», «Раменки»).

Эффект: `entity_match._is_stop_word_window()` отбрасывает однословное окно
целиком, если все токены — стоп-слова → «квартиру в Раменках» или «у метро
Люберцы» никогда не доходят до rapidfuzz. `bounds_stopwords = STOP_WORDS -
LOCATION_MARKERS` дополнительно исключает многословные окна, начинающиеся/
заканчивающиеся на эти слова.

**Исправление:** убрать `"люберцы"` и `"раменки"` из `STOP_WORDS`. Если
изначальная причина их добавления — ложный матч «молодая» → «Молодёжная»
(похожий кейс из `stress_test_queries.md`) — эта проблема должна решаться через
пороги/`_adjust_score` в `entity_match.py`, а не через глобальный стоп-лист,
который задевает несвязанные реальные топонимы. Добавь регрессионный тест:
запрос с «Раменки»/«Люберцы» должен успешно матчиться на соответствующую
сущность справочника.

### 2. `_ONLY_AVAILABLE` — избыточно широкий regex

`app/parsing/rules/misc.py` (константа `_ONLY_AVAILABLE`, ~строка 137) включает
голый `\bдоступн\w+\b` в альтернативах. Любое слово с корнем «доступн-» —
не только «только доступные квартиры», но и «доступная цена», «доступный
район», «доступно по деньгам» — выставляет `only_available=True`, что добавляет
`status=free` в URL и незаметно сужает выдачу вопреки намерению пользователя.

**Исправление:** убрать голый `\bдоступн\w+\b` из альтернатив. Оставить только
явные конструкции: «только доступные», «не бронь», «только свободные» и т.п.
(то, что уже есть в остальной части паттерна). Добавь тест: «квартира по
доступной цене» НЕ должен выставлять `only_available`.

### 3. `_FINISH_TRUE` — голые «отделка»/«ремонт» матчат отделку=READY

`app/parsing/rules/finish.py` (константа `_FINISH_TRUE`, ~строка 15) включает
`\bотделк\w+\b|\bремонт\w+\b` без привязки к «с»/«под ключ»/«готов». Фразы вида
«какая отделка есть в вариантах» или «ремонт делать сами не хотим» (частица
«не» стоит не рядом со словом «ремонт», поэтому паттерн отрицания её не ловит)
ошибочно интерпретируются как запрос готовой отделки.

**Исправление:** убрать голые `\bотделк\w+\b`/`\bремонт\w+\b` из `_FINISH_TRUE`
— отделка=READY должна матчиться только на явные конструкции («с отделкой»,
«с ремонтом», «чистовая отделка», «готовая отделка», «под ключ»), которые уже
покрыты остальной частью паттерна. Добавь тесты на оба false-positive кейса из
аудита плюс убедись, что позитивные кейсы («хочу с отделкой», «под ключ»)
по-прежнему работают.

## Требования к результату

- Все три фикса — точечные правки regex/множеств, без изменения контракта
  `Criteria`/сигнатур функций.
- Для каждого фикса — минимум один новый тест в `tests/parsing/test_rules.py`
  (п. 2–3) и `tests/parsing/test_entity_match.py` (п. 1), воспроизводящий баг
  «было» → «стало».
- Прогнать `uv run pytest` и `uv run ruff check` — всё зелёное.
- Перепрогнать запросы из `stress_test_queries.md` через `POST /build-url`
  (например, через Swagger UI), сверить, что вывод не деградировал. *(Пункт
  выполнен ранее; вспомогательные скрипты `run_stress_test.py` и
  `stress_test_output.txt` были одноразовыми dev-артефактами и удалены по
  итогам `AUDIT_REPORT.md`, раздел «Кандидаты на удаление».)*
