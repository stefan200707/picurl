# 25 — ИИ-резолвинг фраз под опции + самообучение алиасов — Milestone AI-10

> Прочитай `_conventions.md`, промпты 18 (клиент/пайплайн ИИ), 20 (промоушен
> фактов) перед началом. Важно: это не доработка существующего пути ИИ, а
> **новая способность** — сегодня ИИ его вообще не покрывает (см. «Контекст»).

## Контекст

Пример: «квартира с отдельным санузлом». Фильтр «Два и более санузла» в
`app/reference/option_groups.json` реально существует, но его алиасы —
буквальные («2 и более санузла», «несколько санузлов» и т.п.). rapidfuzz
(`app/parsing/entity_match.py`) матчит по строковому сходству — «отдельный» и
«два и более» не похожи по буквам, скор будет низким, матч не произойдёт.
Фраза уходит в `warnings` как нераспознанная.

**Важно понять, куда она уходит дальше — никуда.** Проверено по коду:
`app/ai/enrichment.py` вызывается с `(text, criteria, warnings, pool)`, но
внутри читает только `criteria.poi_requirements` и `criteria.center_requested`
(`app/geo/candidates.py`) — общий текст `warnings`/нераспознанные фрагменты
в промпт модели вообще не попадают. То есть заявленный в `_conventions.md`
инвариант 1 («ИИ вызывается, если после парсинга остаётся нераспознанный
семантический кусок») сегодня реализован только для двух узких, заранее
типизированных случаев (POI-категории, флаг центра), а не как общий fallback
«на весь необъяснённый остаток». Для фраз-синонимов фильтров общего fallback
просто не существует как кода — это не баг ИИ-резолвинга, это отсутствующая
функциональность.

Второе отличие от промпта 20 (промоушен гео-фактов): гео-факт объективен (ЖК
либо рядом со школой, либо нет). Соответствие фразы фильтру может быть
**неоднозначным** — «отдельный санузел» в разных запросах может по смыслу
значить и «раздельный санузел» (ванна/туалет не совмещены — фильтра под это
в справочнике сейчас может и не быть вовсе, тогда это уже промпт 24), и «свой
санузел на каждую спальню» (≈ «2 и более»). Порог наблюдений/уверенности из
промпта 20 (`AI_PROMOTION_MIN_OBSERVATIONS`/`AI_PROMOTION_MIN_CONFIDENCE`) сам
по себе не ловит эту неоднозначность — нужен отдельный, более жёсткий
критерий согласованности.

## Задача

### 1. Резолвинг нераспознанных фрагментов через ИИ

- `app/parsing/parser.py`: собирать не только `warnings`, но и структурный
  список фрагментов-кандидатов на «это может быть опция/группа опций,
  которую мы просто не сматчили» — эвристика для отсечения совсем не
  относящегося шума (даты, случайные слова) реши по месту (например: фрагмент
  короче N слов и не попал ни в одно предупреждение категории 24
  «неподдерживаемое»).
- `app/ai/enrichment.py`: новая ветка — если такие фрагменты есть, в контекст
  модели (`app/ai/prompts.py`, `build_context`) добавляется полный список
  `options`/`option_groups` (name+slug, без ограничения шорт-листом
  кандидатов ЖК — тут кандидаты не ЖК, а сами фильтры) и сами фрагменты.
  Модель отвечает: для каждого фрагмента — либо `slug` совпавшего
  option/option_group, либо `null` (не нашла соответствия — остаётся в
  `warnings` как есть, не выдумывать).
  `sanitize_against_shortlist`-аналог обязателен: ответ модели валидируется
  против реального списка slug'ов из справочника, как сейчас для кандидатов
  ЖК — не доверять слепо строке из ответа модели.
- Результат применяется к `criteria.options`/`criteria.option_groups` так же,
  как если бы это сматчил rapidfuzz.
- Заодно (AUDIT_REPORT.md 2.6): в `merge_enrichment` (`app/ai/enrichment.py`)
  `from app.parsing.schema import MatchedEntity` импортируется дважды в двух
  разных `if`-ветках одной функции — раз уж эта функция всё равно правится
  под новую ветку опций, поднять импорт один раз в начало функции.

### 2. Логирование сопоставлений для будущего промоушена

Каждое сопоставление «нормализованная фраза → slug» пишется в БД (переиспользуй
`ai_structured_facts` с новым `fact_type` — например `option_alias` —
subject_type/subject_id = тип и slug фильтра, `fact_value = {"phrase": "..."}`)
через существующий механизм карты памяти (промпт 17), с учётом
уже реализованной там логики конфликтов.

### 3. Промоушен алиасов — с защитой от неоднозначности

Расширить `app/ai/promotion.py`:
- Новый порог/проверка **до** применения обычного критерия наблюдений/
  уверенности из промпта 20: для одной и той же нормализованной фразы
  посмотреть **все** наблюдения за фразу (не только по конкретному
  `subject_id`) — если фраза стабильно (во всех/подавляющем большинстве
  наблюдений) ведёт к одному и тому же slug — кандидат на промоушен. Если
  наблюдения расходятся между разными slug — это конфликт по определению
  промпта 17, факт **не промоутится** никогда автоматически, независимо от
  числа наблюдений/уверенности.
- Расходящиеся фразы — не просто отбрасывать: сложить в отдельный отчёт
  (`promotion.py --report` или лог) как «неоднозначные, требуют ручного
  решения» — оператор сам решает, заводить ли под это два разных алиаса
  привязанных к более узкому контексту, или оставить на ИИ навсегда.
- При успешном промоушене — запись в `aliases` соответствующей записи
  `option_groups.json`/`options.json` тем же безопасным мёрж-паттерном, что и
  промпт 20 (не затирать кураторские правки, стабильная сортировка).

## Требования к результату

- Тесты `tests/ai/test_enrichment.py`: «отдельный санузел» без матча
  rapidfuzz → фрагмент уходит в контекст модели (мокнутый клиент) → ответ
  применяется к `criteria.options`.
- Тесты `tests/ai/test_promotion.py`: фикстура с **согласованными**
  наблюдениями одной фразы → промоутится в alias; фикстура с
  **расходящимися** наблюдениями той же фразы на разные slug → не
  промоутится ни при каком числе наблюдений, попадает в отчёт «неоднозначные».
- `uv run pytest`, `uv run ruff check` зелёные.
